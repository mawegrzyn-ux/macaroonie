# Outstanding: pepper

What is not built, known limits and follow-ups in this area (`docs/claude/areas/pepper.md`). Item numbers are the old CLAUDE.md numbering, kept so earlier references still work; a new item takes the next number after the highest in any file of this folder. Check the live code before calling anything here pending.

**15. Pepper (AI assistant) — follow-ups** *(the review of 17 Oct 2026 lists more ideas: memory, streaming, voice, help-button prompts)*
- The report tools (13 Nov 2026) are tested only against a stand-in Claude: first real use, ask a few questions about sales in a fresh chat ("which dishes sold best last week?", "save that as a report", "share it with managers") and check each goes to the right tool, the cards say what will happen, and a starter page's chip reaches the answer.
- Tool search and the new tools are tested only against a stand-in Claude API (exact block shapes from the SDK 0.133.0 types). First real use: ask something in each area in a fresh chat and check the search finds the tool; then check an old conversation still replays after a deploy that changes tools (since migration 242 a chat whose tool list changed sends its earlier replies without their thinking, `thinkingFor()`, so this should hold; that rule too has only run against the stand-in).
- Web search in the chat (migration 242) is tested only against a stand-in Claude (block shapes from the SDK 0.133.0 types and Anthropic's web search documentation). First real use: switch it on for a test group, ask something that needs the web, and check the searches, the sources and the month's Web searches figure; then switch it off, send another message in the same chat (that request goes without the earlier search blocks and citations: the documentation doesn't say whether a history with them is accepted without the tool, so check this is), and on again. Open chats send their earlier replies without thinking once, on their first message after the deploy (no tool list was recorded for them). Not built: where the person is (`user_location`), allowed or blocked sites per group, web fetch (reading one given page), the newer tool versions with dynamic filtering, a cap on searches per person or group other than the allowance, source markers inside the answer (sources are listed under it), web search in the guest website chat (on purpose) or for apps on the staff connector (they have their own). Search results are input tokens for the rest of the chat, so a chat with searches uses more than its searches' 2,500 units each and moves to the main model sooner (`LONG_CHAT_TOKENS`). When Anthropic refuses the tool, each API process finds out by itself (the 10 minutes are per process), and later messages in that time say nothing about web search being unavailable. The words Pepper searches for leave the app; "never search for a person's details" is an instruction to the model, not a filter. Local info search captures use more of the allowance than before (their searches weren't counted).
- Rota tools change one week per call and don't edit shifts, roles, rota setup or tip pot setup; Cash tools don't edit Cash Recon settings, unsubmit a day, upload receipts or edit / delete an expense; order tools don't change ordering setup or promotions' content; venue tools don't change sittings, slot caps, tables or combinations; website tools don't edit pages, blocks or the theme. Those stay on their pages (`open_page` links to them).
- The MCP tool list is filtered by area (migration 179: `SECTION_MODULES` + `toolAllowed()`), not per tool: a person with View on one of an area's modules sees all its reading tools, some of which may still refuse. Access tokens can't be limited to one venue: many tools act on a booking, order or person by id without naming a venue, so a venue scope couldn't be enforced honestly without route-level work.
- OAuth sign-in for the staff connector (migration 181) is tested against the spec's flow (registration, PKCE, the Connect page, the token on the connector) but not yet with claude.ai or ChatGPT themselves. First real use: add the address as a custom connector in claude.ai and check it lands on the Connect page and connects. There are no refresh tokens: when the chosen 30-365 days are up the app asks to connect again. Registered apps (`ai_oauth_clients`) are never deleted. The login-return fix (`appState.returnTo`) was only tried with the harness's stand-in login, not real Auth0.
- Browser-based MCP clients from other origins: the global `@fastify/cors` handles preflight before the MCP routes' own `OPTIONS` handler, and in production only allows `*.{root}` origins. Server-side clients (claude.ai, ChatGPT) are unaffected.
- AI bookings follow the widget's path, so like widget bookings they get no reminder email (`scheduleReminder()` only runs on `POST /api/bookings`; staff AI bookings use that route and do get one).
- Deposit venues can't be booked through AI (same as the public widget): the tools send the guest to the website or phone.
- H&S tools don't edit setup (fridges, check times, sessions, checklist templates), delete readings, add per-task checklist notes, or touch purchasing; those stay on their pages. A temperature reading is replaced only by logging the same check again.
- `override_limits` doesn't cover the booking window, the cutoff, blocked times or a specific table; those stay on the timeline.
- Menu tools don't change dish photos, meal deal contents, print designs or print options, till fields, the tag list or variant groups themselves, and don't delete menus; those stay on the Menus pages. A menu read from a photo or PDF is only as good as the reading (the card lists every dish to check). Not yet tried against the real Claude API with a real menu photo.
- Purchasing tools don't delete anything (items, prices, suppliers and lists are switched off), don't reorder lists or categories, and don't download PO files. An attached Excel file can't be imported (attachments refuse xlsx): save it as CSV, or the model reads it from a PDF. A price list read from a PDF or photo is only as good as the reading, so the import card's dry run is the check; not yet tried against the real Claude API with a real supplier PDF.
- Attachments: staff chats only (not the website chat; MCP clients send files through their own app). Word / Excel / PowerPoint aren't read (save as PDF / CSV). Files are kept in Postgres (`ai_attachments.data`, bytea) for as long as their chat exists (chats idle past the tenant's retention are deleted hourly, migration 174); unsent uploads go after a day. Move to `storageSvc` if chats with files become common. Not yet tried on a real iPhone (HEIC conversion, camera input) or against the real Claude API with a large scanned PDF.
- Fair use and erasure (migration 174): unit weights are hard-coded in `usageUnits()` (`CACHE_READ_WEIGHT`), so an Anthropic price change needs a code change; the website chat has no per-guest cap (only the per-IP rate limit and the monthly allowance). Erasure finds a guest's details only as written on their customer row, bookings and orders (a first name alone, a phone written another way, a typo aren't found), can't reach an MCP client's own history (the person's AI app keeps its copy) and closes every chat it edits. A process that dies mid-turn leaves its chat busy for up to 90 s.
- Help answers search the Help page's words only (no synonyms beyond simple plurals): a question in other words than the guide's may miss; the index ignores the Docs page on purpose. The page note covers six pages (Timeline, Bookings, Rota, Food safety, Online orders, Cash Recon); other pages send only their address. Neither is tried against the live model yet.
- The 5-minute nginx timeout exists only once a deploy has run `ensure-nginx-ai-timeout.sh` (check `sudo nginx -T | grep -n "api/ai"`); a streamed turn doesn't need it (the 15 s heartbeat keeps any proxy's read timeout from firing), a JSON one still does.
- Streaming and routing are tested against a stand-in Claude that streams the API's event shapes, and in Chromium through the Vite proxy, not yet against the live API or through the real nginx. First real use: watch an answer stream on the live site (nginx buffering off), and check a chat that moved to the main model mid-way still answers with its earlier reasoning (the main model is documented to read the everyday model's thinking blocks; not measured here). The `HEAVY_TOOLS` list and `LONG_CHAT_TOKENS` are first guesses; watch the `AI chat moved to the main model` log lines to tune them. Prices in `PRICES` are copied by hand: a price change needs a code change.

**28. New location with Pepper — follow-ups** *(shipped with migration 186)*
- Tested only against a stand-in Claude that returns the answer schema; not yet against the live model. First real use: describe a real opening and check the scope picks a sensible location to copy, asks few questions, and the brief matches the cards.
- Not copied: menus that belong to the template location only (the new one uses the company's menus; a venue-only menu has to be copied on the Menus page), promotions limited to venues (the new location isn't added to them), kiosk designs and menu screen boards (company-wide already), Loyverse and GloriaFood links (follow-ups), staff from the template (only people named in the plan are added), team members' access, past data of any kind.
- A copy is a snapshot: later changes to the template location don't reach the new one.
- Create is one transaction; a very large template (thousands of tables, caps or pars) has not been timed.
- The opening isn't linked to Pepper's chat history: a plan made in the chat and one made on the page are separate openings unless the chat names the opening.

**31. Venue wizard, Brand & theme page, menus from files — follow-ups** *(shipped with migration 196)*
- Menu reading is tested only against a stand-in Claude; not yet with the live model and a real menu (photos of a printed menu, a long PDF, a handwritten board). First real use: read a two-page menu and compare every price. A menu over about 32,000 output tokens is cut off (the reply asks for a few pages at a time); there is no way to read a long menu in parts and join them.
- Migration 196 replaced every group's menu: Navigation designer changes and launcher tiles made before it are gone (pre-prod, accepted by the user).
- The brand reaches the live website only after Publish; the admin's card headers and the designers' Use the brand use the saved draft at once, so for a while the admin can show a brand the guests don't see yet.

- The wizard's own-look kit applies to the venue's web page only (not its kiosk designs or boards, which are company-wide).
- The wizard has no undo for settings saved in earlier steps other than changing them again; deleting a draft is the reset.

**51. Measuring Pepper, step 0 follow-ups (Pepper-first, 22 Nov 2026; migration 271)**

Built (0b): `ai_requests`, one row per model call with what it was for, the model, tokens, units, an estimated cost in dollars and the time it took; report subject `pepper.requests` and the starter Pepper's cost by model. Not done:
- No median or percentiles: the report engine has sum, average, smallest, largest and counts, so "median response time" is the average and the longest for now.
- The cost is at the list prices in `PRICES` when the row was written: a price change later doesn't change old rows, and discounts (batch, an Anthropic agreement) aren't known. The time is the model call's only, not the whole chat turn (tools and the database are left out).
- The staff and guest connectors' calls (`addUsage()` with no model) aren't model requests and aren't kept: the model there is the other app's.
- Tool search hit rate (one of step 0's numbers) isn't recorded: it needs the tool search blocks of each turn counted (`server_tool_use` of `tool_search_tool_*` against the tools then called).

Built (0c): the evaluation set in `api/eval/` (27 tasks, harness, `npm run eval [-- --live]`), proven in CI against the stand-in model. Not done:
- **Second live run, after step 3's fixes: 23 Nov 2026, 27 of 27 passed, $0.06, 147 s, 73 requests** (`live-2026-11-23T18-54-06-756Z.json`). One trial per task: run `--trials 3` before trusting a pass rate.
- **First run against the live model: 23 Nov 2026, 23 of 27 passed, $0.12, 153 s** (`api/eval/results/live-2026-11-23T15-33-53-425Z.json` on the owner's computer, not committed). How to run it: `eval "$(scripts/test-env.sh eval)"`, then in `api/` `ANTHROPIC_API_KEY=... npm run eval -- --live`. The four failures and what changed (Pepper-first 3f, 23 Nov 2026):
  - `fridge_reading` and `delivery_check`: Pepper opened the form (open_form) and told the person to fill it, instead of logging the stated values with log_temperature / log_delivery (a Confirm card). open_form's description and prompt line, the H&S paragraph and the two logging tools' descriptions now say: stated values of one check go to its logging tool; open_form is for filling the form yourself or many values at once, and with values it is the fallback when no single tool fits.
  - `book_table`: Pepper checked availability, then wrote the booking out and asked "Should I create it?" instead of calling create_booking. The staff prompt (`prompts.js`) now says to call the change tool as soon as the details are complete, and never to ask in text whether to go ahead.
  - `holiday`: Pepper's questions were fair (Jo works at two venues; paid holiday or unpaid time off is a real choice), so the task now names the venue and says "unpaid time off" (`api/eval/tasks/people.mjs`).
  - Not re-run after these changes: the owner re-runs `--live` after the merge. Tasks that fail for the harness (a check too strict about words) rather than for Pepper still need the reply and the cards in the result file read first.
- The tasks were written from the tools and the notes, not from real chats (there are none yet): replace or add tasks from the first real failures once staff use Pepper.
- One message per task in all 27; multi-turn tasks (Pepper asks, the person answers) are supported (`say` returns a list) but none is written. A "nothing" task passes when Pepper asks the right question, but whether it asked is not checked.
- Each trial empties the whole test database, so trials run one after another (no parallel trials).
- No task covers reports (`build_report`, schedules), new locations, purchasing orders, tips or pay: their end states take longer setups; add them next.
- The result files stay on the computer that ran them (`api/eval/results/`, not committed): no history of runs to compare against yet.

**53. Filled forms, step 3 follow-ups (Pepper-first, 23 Nov 2026; migration 275)**

Built: one form list (`shared/forms.js`), Pepper's values checked and marked in the sheet, the saved line with Edit on the chat card, drafts on the server, and the order, corrective action, H&S action and booking forms. Not done:
- **Forms that take no values yet**: cooking checks, a checklist, the cash-up, the wages, sold out, the rota for a day and a booking's details (booking_change: Pepper's `change_booking` does that change with a Confirm card). The cash-up's counts are measured values, so filling them needs the same "only from the person's words" check as temperatures.
- **The saved line**: the rota for a day and sold out never report what was saved, so their cards get no line. The line is the browser's words of what its form saved (the routes did the saving); the server checks it is one line of the person's own chat, not what it says. A form saved while Pepper is still answering in that chat gets a 409 (busy), and the card says the line wasn't kept in the chat.
- **Measured values**: only digits (and "minus") in the person's message of this turn count; numbers in words ("six") and a reading said in an earlier message are left out, and Pepper says so.
- **The order form**: Pepper's items are matched by name on the list the person opens (exact, then starts with, then contains, one match only), in the browser; the server doesn't check the items exist, and Pepper can't pick the list. Names not on the list are listed above the lines.
- **Drafts**: only the five forms with `drafts: true`. A change typed in the last 800 ms before the tab is closed or the device sleeps may be lost (the draft is kept on the debounce or when the form closes in the app). A form for one record has its values used up after its first Save, so a second delivery or expense in the same sheet starts empty.
- **The step's measures are not recorded**: the strategy's "share of pre-filled fields saved unchanged", time per task through a filled form and changes reversed within 24 hours need a record of what Pepper placed and what was saved (the usage record or `ai_requests` don't hold it).
- **Checked in a browser at 1280 px only** (delivery: values, marks, OK, a change, the draft through a reload, Save, the line, reload, Edit; H&S action, order, corrective actions and a new booking opened with their marks). Not checked: booking_change's window, the phone's Today and the phone app at phone width, a touch screen (the grids' keypad with a Pepper reading).
- **Not run against the live model**: whether Pepper passes `values` well (and only what was said) is for the next live evaluation; no evaluation task covers `open_form` with values yet.

**54. Action registry, Undo and Done by Pepper, step 4 follow-ups (Pepper-first, 23 Nov 2026; migrations 276, 277)**

Built: a class on every tool (101 staff change tools: 24 reversible, 59 consequential, 18 destructive; 97 of them with a Confirm card), preconditions on 9 tools, allergen calls escalated to destructive; cards with before and after on 6 tools, fields changed in place on 6, a typed word for destructive cards and never a spoken yes; one write per card; Undo on 6 reversible tools for 10 minutes; the Done by Pepper page. Not done:
- **"Done, with Undo" without a card** (decision 4): every change still waits for Confirm. Moving a group's short list of reversible tools to run straight away needs the reversal figures from first customers, a per-group setting and the list chosen by the owner. Never money, pay, prices, allergens, deletions or anything about a person.
- **Reversible tools without Undo**: log_temperature, log_hold_check, log_cooking_check, log_delivery, add_corrective_action (a food safety record: deleting a reading needs Manage and leaves a hole in a compliance log; logging the check again replaces it), add_hs_action and complete_hs_action (deleting an action needs Manage; reopening one has no route), run_local_capture and reload_screen (nothing to put back), report_issue and request_feature (a ticket the platform sees at once), build_report, copy_report and export_report (Undo would delete a report or file: decide whether that is wanted), order_form and the three new-location planning tools (drafts with no card). Consequential and destructive tools have no Undo in this step.
- **Undo's limits**: set_sold_out's Undo puts a dish that was sold out "today" back to sold out until the end of the day it is undone on (the same day within 10 minutes, except across midnight). An Undo finds a change made since by someone else only where the route refuses it (a checklist task already unticked: Undo says so); the banner, the pause and a dish's sold-out state are put back as they were before Pepper, over anything changed on the page in between. Undo is offered only in the chat the change was made in and on Done by Pepper, to the person whose chat it is; a manager can't undo someone else's change from there (on purpose).
- **Before and after**: only on set_sold_out, pause_online_orders, set_website_banner, switch_promotion, change_booking and update_guest_details (update_customer and update_dish already said "from → to" in their lines). Prices (change_prices, update_supplier_price), the rota, booking rules and staff details would benefit next.
- **Editable fields**: only create_booking (time, party size, notes), change_booking (time, party size), add_booking_note, add_expense (what, amount), log_temperature (reading, what was done) and add_local_event (title, time). Lists (dishes, order lines, rota changes) are not editable on the card. A changed reading is the person's own, typed on the card.
- **The typed word** is the guest's or customer's surname (update_guest_details, update_customer, anonymise_customer) or CONFIRM. Staff tools use CONFIRM; a staff member's surname would be closer to the spirit of "a named sign-off". The word is a deliberate pause, not a secret: the card shows it.
- **Idempotency covers the chat only**: the card is the key. A staff connector (MCP) call has no card, so an app that retries a call runs it again; a key on the connector needs the MCP client to send one.
- **Done by Pepper**: 200 rows per view; no paging, no search, no filter by person (decision 8 is about ranking; a person filter for multi-site managers is in the strategy's For review and can follow). Rows from before migration 276 have no card, person or venue: they show under a person's own only when their email matches. The "Waiting" tab of For review (unanswered cards, drafts) is step 5. Checked in a browser at 1280 px only, not at 1015 or phone width, and not in the phone app.
- **The step's measures** (share of change tools with a working Undo, the mix of approved, edited and rejected cards) can be counted from `ai_pending_actions` (status, `card.edited`, `undone_at`) and `ai_actions`, but no report or starter shows them yet; the `pepper.actions` report subject doesn't have the new columns.
- **Not run against the live model**: whether Pepper still calls the change tools well with preconditions added to their descriptions is for the next live evaluation (`npm run eval -- --live`). The evaluation harness types a destructive card's word as the person would.
