## Mistakes to avoid

> Append-only: never delete an entry, only correct one that turns out to be wrong. New entries go at the end.

- **Auth middleware reconcile uses a 3s Promise.race timeout** — the user-row lookup in `requireAuth` races against `setTimeout(reject, 3000)`. If the DB hangs, the timeout rejects, the catch logs a warning, and the request continues with the JWT role — never produces ERR_EMPTY_RESPONSE for the upstream client. The `last_login_at` UPDATE is fire-and-forget (`.catch(...)` only), so the request never blocks on a write that nobody reads in this request.
- **The Edit tool can introduce curly/typographic quote characters (U+2018 `'`, U+2019 `'`) as string delimiters** — these are NOT valid JavaScript string delimiters. They cause two distinct failure modes: (a) in JSX/JS files, esbuild throws `Unexpected "'"` at build time; (b) in Eta `<% %>` server-side blocks, V8 throws `Invalid or unexpected token` at render time producing a 500 on every request. In the `<script>` HTML section of Eta templates they don't break server-side compilation but DO break browser-side JS execution. Diagnosis: `python3 -c "data=open('f','rb').read(); [(print(i,l)) for i,l in enumerate(data.split(b'\n'),1) if b'\xe2\x80\x98' in l or b'\xe2\x80\x99' in l]"` — U+2018 is `\xe2\x80\x98`, U+2019 is `\xe2\x80\x99`. Fix pattern for JSX: use double-quoted strings. Fix pattern for Eta templates: Python byte-level global replacement — `data = data.replace(b'\xe2\x80\x98', b"'").replace(b'\xe2\x80\x99', b"'")`. Do NOT use `content.replace(b'\xe2\x80\x98\xe2\x80\x99', ...)` (replaces adjacent pairs only). Replace each byte sequence independently. Bit us in `ReservationsWidget.jsx` (build-time, May 2026) and `reservations_widget.eta` (runtime 500, June 2026) — 153 curly quotes introduced during confirmation-page feature work.
- **An inventory item has no price: what it costs is its supplier quotes, picked by `chooseQuote()` in `shared/procurement.js`** — venue choice, then the company star, then the cheapest per base unit at that venue's price. Never add a price column to `inv_items` or pick a quote another way in a new report or page, or it will disagree with what an order is placed on. Anything reporting what was actually paid must read `purchase_order_lines` (prices are copied there at ordering time), not today's quotes.
- **Pars and pack sizes are stored in the item's base unit (g / ml / each), never in packs** — `order_list_pars.par_base`, `inv_quotes.pack_base_qty`. Show and enter them in packs through `packsToPar()` / `packBaseQty()`, so changing a supplier or pack size doesn't change the par. An item's base unit can't change while it has quotes or pars (the API refuses).
- **Purchase orders are emailed after their transaction commits** — `POST /orders/:id/submit` creates every PO first, then calls `emailPo()` per supplier, so a failed email never loses an order (the PO stays `to_send` with `send_error`). A new path that creates POs must do the same: never send an email inside the creating transaction.
- **A purchasing AI tool must show only what the purchasing routes return, and change only through them** — the routes strip prices for people without Purchasing setup view (`hideMoney()`, quote views), so a tool that read `inv_quotes` itself, or worked a total out from quotes, would show prices to ordering staff. The tools' cards use `order.show_prices` / `d.show_prices` from the route response before printing any money. The few direct reads in `tools/purchasing.js` (venues, PO number to id, supplier delivery settings, chat attachments) carry no prices and filter `tenant_id`.
- **`place_order` submits the venue's whole draft when Confirm is pressed** — the draft is shared (the Purchasing page autosaves into the same one), and the card shows the draft as it was when the model called the tool. Lines someone else adds before Confirm go too. `order_form` (and `update_order` / `place_order`) also make an empty draft when none is open, the same as opening the list on the Purchasing page; a viewer without Purchasing manage never makes one.
- **Receiving owns the delivery check it writes** — `POST /pos/:id/receive` upserts `fs_delivery_checks` by `purchase_order_id`. Editing that check on the Food safety page doesn't change the purchase order, and booking the PO in again overwrites the check. Use Correct the delivery on the PO.
- **A tool the model fills from a long file or photo needs a batch cap and a way to continue** — the tool input is written in one reply under `MAX_TOKENS` (16,000 in `chat.js`), so a whole menu or price list in one call is cut off (`CUT_OFF`). Keep a cap in the Zod schema (dishes 50, rows 100), say in the description and the prompt how to send the rest, and make a follow-up call work before the first card is confirmed when it builds on it (as `loadForAdd()` does).
- **Who may change an order is decided by `orderActions()` / `assertEditable()` in `routes/purchasing.js` (migration 180), never in the screen** — a draft by anyone with Purchasing manage, a request waiting for approval only by someone with Purchasing approval. The admin shows only the `can_*` flags the API returns. A new order action needs its flag in `orderActions()` and the same check in its route; a new route that changes what is ordered (placing, PO quantities, split, cancel) must use `canApprove`, or request-only staff get round the approval.
- **A purchase order with `amended_at` changed after the supplier had it**: anything that sends or prints POs must go through `poHtml()` / `poPdf()` / `poXlsx()` / `emailPo()`, which say Amended and Split off (`poChangeNotes()`). Never clear `amended_at` when resending; the copy then says it replaces any earlier one, which stays true.
- **The ordered price on a purchase order line never changes after ordering; the invoice's price is `invoice_price` beside it** (migration 197) — receiving, splitting and the price list update don't touch `price` or the PO totals. Code that reports what was actually charged must read `invoice_price` (falling back to `price`), and code that reports what was ordered reads `price`. A line `added_on_receipt` has qty 0 (the qty CHECK allows 0 only for these): sum ordered quantities over `qty`, received over `received_qty`, and leave added lines out of anything the supplier sees (`documentData()`).
- **Invoice prices are stored for everyone but shown only to people who see purchasing prices** — `invoiceView()` strips the reading's money and `poDetail()` strips `invoice_price` without `purchasing_setup` view; the receive route takes a typed `invoice_price` only from price viewers and otherwise uses the stored reading's price by `invoice_idx`. A new place that shows a reading or a line must go through these, and a new body field that carries a price from the browser must check `showPrices()` the same way.
- **A model's refs, not ids** — invoice reading sends the order's lines and the supplier's products to the model as `L1..` / `C1..` and `toInvoice()` turns them back into ids from those same lists; an unknown ref is ignored. Never ask a model to echo uuids back, and never trust one it returns: a misread id could point at another tenant's row.
- **Lines go onto a purchase order only through `PUT /pos/:id/lines` (`add`), which tops up a line already holding the same quote** — the supplier reads two lines of one product as two orders, so a new way of adding to a PO (an import, a route, a Pepper tool) must call it rather than insert `purchase_order_lines` itself. - **A purchasing order line with a quantity is pinned to its quote and must never fall back to another (migration 232)** — `PUT /orders/:id/lines` stores the given `quote_id`, else the stored one, else the venue's usual one at that moment; `orderLines()` reads only the pinned quote and refuses (422 `order_lines`) when it is gone. Code that reads a line's quote must not do `pinned || resolveQuotes()` pick: that was the bug (a switched-off price quietly became another supplier's, with the pack count kept). A new way of filling an order (an import, a basket, Pepper) should send the `quote_id` it showed the person (else the API pins the venue's usual one when it saves, which may not be what was shown), and a new way of switching a line's quote must convert the quantity with `convertQty()`, never keep the count.
- **A supplier price or supplier on an open order is switched off, never deleted** — `DELETE /inventory/quotes/:id` and `DELETE /suppliers/:id` answer 409 `on_open_order` while a draft or requested order has a quantity on it (`openOrderVenues()`), so the order can say the line needs another price. - **Whether a supplier can deliver on a day has one rule: `deliveryDayProblem()` (`shared/procurement.js`)** — the screens (`DayCheck`, `deadlineText()`), the API (`checkDeliveryDay()`) and Pepper (`dayCheck()`) all call it with the venue's `nowAt()`, and a shared test keeps `nextDeliveryDate()` the first day it accepts. Don't compare a date with today, `minutes_to_cutoff` or `delivery_days` by hand in a new route or screen: it misses the lead days and the cutoff of the day picked (not today's), which is how any day used to be accepted. Every route that sets a purchase order's delivery day takes `agreed` and refuses a past day whatever it says.
- **A purchase order line's quantity is stored as `fitQty()` against the quote's minimum and steps, and a split must pass `splitProblem()`** — `loadPoLines()` gives `min_qty` / `order_multiple` only while the quote is still for the line's pack (null otherwise: a minimum in other packs means nothing). A new route that changes PO quantities must round the same way, and one that moves part of a line must check both parts, or the supplier gets a quantity below their minimum.
- **A supplier's note on a new purchase order is the venue's driver instructions unless the notes key was sent (migration 233)** — the API decides with `hasOwnProperty(opt, 'notes')`: left out = the driver instructions, sent empty = no note. A purchase order can now hold lines from more than one restaurant order: list a restaurant order's purchase orders with `poList({ supplyOrderId })`, which includes `added_to_po_ids`, never with `supply_order_id` alone.
- **A purchase order marked sent by hand may say it went earlier: `sent_at` is checked against `created_at` floored to the minute, on the page and in the API** — the page's time box has minutes only, so comparing to the exact `created_at` refused "the minute it was made". Any new place that sets `sent_at` must keep both checks (not in the future beyond 5 minutes, not over `SENT_AT_DAYS` back, not before the order was made) and take the time in the venue's time zone (`zonedInstant()` in Pepper).

A new place that adds a product by a typed code must use the matched quote, or the line lands on another supplier's price.

A new report or widget must call it with the PO row's settings, not today's `minutes_to_cutoff`, which is about today's deadline, not the order's day.

There is no database constraint (codes shared before the rule must not block other saves), so a path that skips the check silently makes a code ambiguous, and two saves at once can both pass without the lock. Switched-off prices and items may keep a code; switching them on is what is checked.

- **A supplier's basket reaches an order only through `basketFromText()` / `basketFromSheet()` and `basketDiff()` (`shared/procurement.js`)** — they decide that a code is one live price of that supplier, that an order has one line per item, and that quantities go up to the minimum and steps. A new way of turning codes into order lines (another supplier's export, an email reader, a scheduled import) must go through them and `POST /orders/:id/reconcile`, which pins each line to the basket's price; writing `supply_order_lines` by code anywhere else can put a line on a switched-off price or on the wrong one of two products sharing a code.
- **Out of stock is judged against a delivery day, never "now": call `outOfStock(quote, date)` with the day the order is for** — the supplier's next delivery on the order form, the date picked when placing, the order's own `delivery_date` on a purchase order. Comparing `out_of_stock_until` with today alone flags orders that will arrive after it is back and misses ones for a day before it. A new screen or tool that shows a price for an order must read `out_of_stock_until` through `quoteView()` / `loadPoLines()` / `QUOTE_COLS` (selected as `::text`, or postgres.js hands back a Date) and pass the right day.
- **Deliveries are booked in only through `receiveInto()` (`routes/purchasing.js`), and a purchase order with `no_order` follows other rules** (migration 238) — its lines are what arrived (qty = received_qty, never `added_on_receipt`), a line at 0 comes off, only OK or damaged apply, its day can move and its totals are at the prices paid. A new way of booking a delivery in (Pepper, an import) must call `receiveInto()`, never write `received_qty` itself. - **A new way of sending a purchase order to its supplier must call `judgeFirstSend()` in the transaction that marks it sent** (migration 247) — Mark as sent and `emailPo()` do; a path that sets `sent_at` itself leaves the order out of Orders sent late for good (a later resend is no first send: an order already judged keeps its judgement, and a failed email judges nothing).
