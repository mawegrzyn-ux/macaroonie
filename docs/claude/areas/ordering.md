# Online ordering

Covers: online ordering (collection), promotions, payment gateways, Stripe Connect.

Key files and mistakes to avoid for this area: read it before changing code here. What shipped and when is in `docs/claude/history/ordering.md`; the index of all areas is in `CLAUDE.md`.

## Key files

Under **API**, `src/...` means `api/src/...`; under **Admin portal**, `src/...` means `admin/src/...`. Other paths are from the repo root.

### API

- `shared/orderPricing.js` (repo root) — web ordering prices: `itemChoices()`, `priceLine()`, `priceBasket()`, `vatIncluded()`. The server prices every order with it; the guest page loads the same file for display.
- `shared/promotions.js` (repo root) — online-ordering promotions (migration 131): `applyPromotions()` (the discount engine, called by `priceBasket()`), `isLiveAt()`, `covers()`, `promoSummary()`, `promoTerms()`, `promoLink()`, `promoRunning()`, `noticeText()`, `venueNow()`. Served to guests as `/order-api/promotions.js`. `api/src/services/promoSvc.js` loads rows and counts uses (`listPromotions()`, `venuePromotions()`, `findByCode()`, `lockUses()`); `routes/promotions.js` is the admin CRUD; `admin/src/pages/Promotions.jsx` the page; `blocks/promo_cta.eta` + `PromoCtaEditor.jsx` + `PromoCtaCanvas` the website block.
- `src/services/orderSvc.js` — Web ordering (migration 122): the one place orders are priced (via `shared/orderPricing.js`), created, moved through statuses (`TRANSITIONS`), paid (`applyPaymentResult()`, idempotent, refunds a duplicate payment automatically), refunded (`refundOrder()`) and expired (`expireStaleOrders()`, run by the hold sweep in `jobs/queues.js`). Also collection slots (`computeSlots()`, computed never stored) and venue-local time helpers (`zonedToUtc()`/`localParts()`). `routes/orderApi.js` (public, `/order-api`) and `routes/orders.js` (admin, `/api/orders`) only call into it.
- `src/services/paymentGateways/` — pluggable payment gateways for web ordering. `index.js` documents the interface (`start`, `confirmFromClient`, `parseWebhook`, `refund`, `cancel`, `isAvailable`) and holds the registry; ships `pay_at_venue`, `stripe` and `demo` (pre-prod pretend card payment); `paymentContext(venue)` is the only source of what `isAvailable()` / `start()` see. Webhooks: `POST /webhooks/payments/:gateway` (`paymentWebhookRoutes` in `orderApi.js`, raw body).
- Stripe Connect (migration 215; Docs.jsx → Web Ordering → Card payments with Stripe): `services/stripeConnect.js` (platform keys in `platform_secrets` (`platformKeys()`, `savePlatformKeys()`, `platformReady()`, `platformKeysInfo()`), `stripeCall()` (platform key + `Stripe-Account`), `verifySignature()` / `signPayload()`, the group's account: `tenantStripe()`, `paymentContext()`, `stripeView()`, `onboardingLink()`, `refreshAccount()` (also registers the site's domains for Apple Pay / Google Pay), `applyAccountEvent()`, `forgetAccount()`, `safeReturnUrl()`), `services/paymentGateways/stripe.js` (PaymentIntents on the group's account with the platform fee, `piStatus()`, the Connect webhook), `routes/stripe.js` (`/api/stripe` connect / refresh / unlink; `/api/platform/stripe` keys), `showStripe()` / `loadStripeJs()` in `views/site/shared/ordering.eta` (Payment Element, `?pay=` return on the status page), admin `components/orders/StripeAccountCard.jsx` (Ordering setup, Store tech card accounts) and `components/platform/StripeKeysCard.jsx` (Platform → Payments). Card machines on the connected account: `cardAccount()` in `services/cardSvc.js`, `settings.connect` on `pos_card_accounts`, `Stripe-Account` in `cardMachines/stripe.js`, `POST /api/pos/card-accounts/:id/locations` (`createLocation()`). Tests: `api/test/stripe-connect.test.mjs` with `api/test/support/fake-stripe-connect.mjs`.
- `src/routes/orderApi.js` — public web-ordering API (`/order-api`): venue menu + settings, slots, quote, place order, order status by public token, payment retry/confirm; also serves `shared/orderPricing.js` as `/order-api/pricing.js` for the guest page.
- `src/routes/orders.js` — admin web-ordering API (`/api/orders`): board list, detail, status/promised/mark-paid/refund, settings, pause, sold out (`ordering_item_availability`), report, transactions (`GET /transactions[.csv]`, from `services/onlineSalesSvc.js`). Modules `web_orders` / `web_ordering_setup`.
- `src/services/onlineSalesSvc.js` — the online sales transactions report: `onlineTransactions()` (own orders + `order_payments` and `gloriafood_orders` for a venue and range, each with a tender key: `ownTenderKey()` / `gfTenderKey()`, GloriaFood on the link's trading day via `tradingDay()`, totals by tender and source) and `transactionsCsv()`. Admin: `components/orders/TransactionsReport.jsx` (Online orders → Transactions).
- `src/views/site/shared/ordering.eta` — the guest ordering page (menu, dish options, basket, checkout, payment step) and order status page, vanilla JS module; each template's `order.eta` wraps it with the site header/footer. Site routes `/order`, `/locations/:slug/order`, `/order/status/:token` in `siteRenderer.js`.
- Online ordering hours later than usual today (migration 223): `dayWindows(settings, date)` (the one rule for a day's windows), `extensionFor()`, `todayHours()` in `services/orderSvc.js`; `POST /api/orders/hours/:venueId` (`{ until: 'HH:MM' | null }`, web_orders manage) and `ordering.hours_today` on the board in `routes/orders.js`; admin `HoursButton` / `HoursModal` / `HoursNotice` (+ `PauseButton iconOnly`, `OrderBoard` `tools` / `banner` for the phone's one row) in `components/orders/shared.jsx`. Tests: `api/test/ordering-hours.test.mjs`.

### Admin portal

- `src/pages/Orders.jsx` — Online orders (`/orders`, `web_orders`): live board per venue + day (New / In progress / Ready / Done), sold out, pause, report tab, transactions tab (`components/orders/TransactionsReport.jsx`). `src/pages/OrderingSettings.jsx` (`/orders/settings`, `web_ordering_setup`): per-venue ordering settings, one Save. `src/pages/mobile/MobileOrders.jsx` (`/mobile/orders`). All built on `src/components/orders/shared.jsx` (OrderBoard, OrderDetailModal, AvailabilityModal, PauseButton, `useRealtimeOrders`, `printTicket`).

## Mistakes to avoid

> Append-only: never delete an entry, only correct one that turns out to be wrong. New entries go at the end.

- **Web ordering prices have one implementation: `shared/orderPricing.js`** — the server prices every order with it against the live menu and never trusts the browser's totals; the guest page imports the same file only to display them. Items from the ordering API carry prepared `choices` (the raw `variants`/`variant_groups` are stripped by `publicItem()`), so `priceLine()` uses `item.choices` when present; a new pricing helper must do the same (`choicesOf()`) or it prices every dish with options as "no price" in the browser.
- **A payment gateway's `confirmFromClient()` must ask the provider, never trust the request body** — only the `demo` gateway trusts the browser, because no money moves. And `applyPaymentResult()` is the only place an order becomes paid: it is idempotent and refunds a second successful payment for an already-paid order (a retry plus a late earlier attempt) instead of counting it twice.
- **A nav-seeding migration must not assume the default nav shape** — 122 only added Online orders under a top-level section labelled "Service" and silently skipped tenants who had renamed it; 123 anchors on a route (`/customers`, then `/bookings`, then the end of the top level) instead. Anchor new links on a known route, never on a section label an operator can edit.
- **Newsletter consent is only ever given by the guest, and not ticking the box is not an unsubscribe** — `createOrder()` sets `customers.marketing_opt_in` only when `marketing_opt_in` is true and never clears it; only `POST /customers/:id/unsubscribe` and anonymise clear it. Don't add a staff "subscribe" action or a CSV-import opt-in: a newsletter needs the person's own recorded agreement (`orders.consent.marketing`), which staff can't supply. Any new place that collects guest data (the booking widget does not have these boxes yet) should reuse `loadPrivacy()`'s wording and record it the same way, and anonymise must be extended to any new table holding guest details.
- **A single-column grid on a phone must be `minmax(0, 1fr)`, not `1fr`** — `1fr` means `minmax(auto, 1fr)`, so the column grows to its widest child's min-content width. The ordering page's category tab strip (`overflow-x: auto`, many tabs) made the column ~1000px wide on a 390px phone, so the tabs never scrolled, `auto-fill` grids laid out several cards per row, and the site's `html, body { overflow-x: hidden }` clipped everything past the right edge (no margin, no scrollbar). Use `minmax(0, 1fr)` and `min-width: 0` on grid children whenever a child has its own horizontal scroll, and `minmax(min(280px, 100%), 1fr)` for card grids. Check a page at 390px in a real browser (`document.documentElement.scrollWidth` and each scroller's `scrollWidth`/`clientWidth`), since the body's `overflow-x: hidden` hides the symptom from a quick look.
- **A dish's ordering VAT has three levels: dish, section, venue** — `vatRateFor()` in `orderSvc.js` is the only place that decides; pass the section. Don't read `item.vat_rate_*` directly for a price or a report, or section rates are silently ignored.
- **The guest ordering page only knows what `publicItem()` sends** — it prices the basket for display with the same `shared/orderPricing.js`, so a field stripped there reads as 0/undefined in the browser with no error: stripping `vat_rate` meant "Includes VAT" never showed. When the guest page needs a new dish field, add it to the item in `loadOrderingMenu()` and check `publicItem()` doesn't remove it.
- **Every discount comes from `applyPromotions()` in `shared/promotions.js`, via `priceBasket()`** — the server (`createOrder()`, quote) and the guest page must call `priceBasket()` with the same `promos` + `promoCtx` (`at` = venue-local time from `venueNow()`/`localParts()`, `venueId`, `chosen`, `unlocked` ids), or the checkout total jumps. Never compute a discount in the page, a report or an email; read `orders.discount_pence` / `order_promotions`. Keep `subtotal_pence` the full price: the minimum order is checked on it, while VAT, tip and the platform fee use the discounted amount.
- **A code promotion's code must not reach the browser until the guest types it** — `GET /order-api/venues/:id` sends only non-code promotions (`publicPromotion()` without `withCode`); `/promo-code` returns the one matching promotion with its code. The Promo block is the deliberate exception (the operator publishes the code by placing it). Don't add codes to the venue payload, the sitemap, llms.txt or any public JSON.
- **Promotion uses are counted from orders, not stored** — a use is an `order_promotions` row whose order isn't rejected / cancelled / expired, so cancelling gives a use back. Any new path that creates orders with promotions (POS, table QR) must go through `createOrder()` or call `lockUses()` inside its transaction, or two guests can take the last use.
- **Promotion discounts that come out fractional per line must go through `settle()` in `shared/promotions.js`** — rounding each line's share on its own took 1p too many off a £15 meal deal (guest paid £14.99). `settle()` rounds the total once and splits it with `allocate()`. Any new kind that spreads a discount over units or lines must use it.
- **A sticky element on a tenant site must sit below the site's own sticky header, and that header's height varies by template and screen** — the ordering page's category bar stuck at `top: 0` and slid under the header block, hiding the search box. Don't hardcode a header height or make operators type one: measure it in the page (`findTopBars()` in `shared/ordering.eta`: sticky/fixed elements at the top, outside the component, wide and short) and re-measure on resize.
- **Anything in the ordering page's basket column has to leave the basket sticky** — the column (`.mo-basket-col`) is what sticks, sized to its content, so stacking the promo box above the basket made the column taller than the screen and cut off Checkout. With promos the column switches to `align-self: stretch` / `position: static` and the basket sticks inside it (`.has-promos`). Anything else added to that column needs the same treatment, and the promo box shows one card at a time so it never grows with the number of promotions.
- **Till discounts from Promotions are worked out on the till and stored as a `promotions.set` event** — reports and the server read the stored amounts; never re-run `applyPromotions()` on a closed check, or a promotion changed since would rewrite past takings.
- **Online sales and their tenders have one implementation: `onlineTransactions()` in `services/onlineSalesSvc.js`** — the Transactions tab and its CSV both read it, and the page only shows what the route returns. A new place that lists or totals online sales (a dashboard widget, Pepper, a Cash Recon line) must call it rather than query `orders` / `gloriafood_orders` itself, or it will disagree on which orders count, which day a GloriaFood order is on (the link's trading day, not the calendar day) and which tender it is. A new payment method needs a tender key there (`ownTenderKey()` / `gfTenderKey()`); an unknown one shows as `other:<raw>`, never silently as cash or card.
- **A base option's price is read only through `basePrice()` (`shared/orderPricing.js`)** — `o.price_pence ?? item.price_pence` treats £0 as a price, so a dish-price group whose options were left at £0 (flavours, sauces) made the dish free on the kiosk, till and online. A new place that prices or shows a base option must call `basePrice(o) ?? item.price_pence`.
- **A kiosk add that should fly needs a picture and a landing place: `addToBasket(entry, key, { flew: flyToBasket(picture) })`, and the button the order total is on must carry `data-fly-target="basket"`** — `flyToBasket()` (`pos/src/kiosk/fly.js`) quietly returns false without a visible target, and `addToBasket()` then bounces the order button at once as before, so a new add path or a new order button without these looks fine and simply never flies. Pass `flew` only from `flyToBasket()`'s result: true tells `addToBasket()` to leave the bounce to the landing, so a hard-coded true leaves the button still. Updates of an entry (a `key`) never fly.
- **A payment gateway sees the group only through `paymentContext(venue)` (`paymentGateways/index.js`)** — `isAvailable(ctx)` and `start(..., ctx)` read `tenant.stripe_ready` / `stripe_account_id` from it, so a new path that lists or starts payments (a retry, the venue's payment methods, a new channel) must load it, or Card (Stripe) is either never offered or started for a group that can't take payments. A new gateway that needs per-group setup reads it from the same context, never with its own query in the gateway.
- **Stripe's Payment Element must be mounted once per payment and never redrawn** — the ordering page redraws its checkout often (`draw()`), and remounting the element empties what the guest typed and can confirm a second element. `showStripe()` keeps it for the payment it was made for; anything new on the checkout must leave its host node alone. A decline must re-enable the button and show Stripe's message, and a `processing` PaymentIntent counts as done for the page (the webhook settles it).
- **Helpers a page script uses on more than one view must be defined at the module's top level** — `ordering.eta`'s `partsHtml` lived inside the checkout's function, so the order status page (another entry point in the same script) crashed on every order it drew for weeks. When moving or adding a helper in a shared page script, check every entry point that calls it.
- **Stripe idempotency keys decide what a retry makes** — the account creation key is per group per minute (a double click makes one account, connecting again after Unlink makes a new one), PaymentIntents use one per attempt, refunds one per payment, refunded so far and amount. A key fixed per group would hand back the old (unlinked) account for ever; a key without the amount would turn a second partial refund into the first one again.
- **A deposit is refunded on the account it was paid to (`payments.stripe_account`), never the group's current `stripe_account_id`** — a group can unlink and connect another Stripe account, and a refund on the new account fails or hits the wrong money. The hold carries its account too (`booking_holds.stripe_account`) for the same reason. Refund idempotency keys include what was refunded so far (a second part refund of the same amount is a new refund); count a Stripe refund once by its id (`refund_ids`).
- **A day's online ordering windows come only from `dayWindows(settings, date)` (`services/orderSvc.js`), never from `settings.hours` directly** — it applies the day's extension from the board's clock button (migration 223); code that reads `hours` itself (slots, ASAP, a guest page's opening times, a report, Pepper) ignores a later close the staff set for tonight, so guests can't order in it or are told the wrong time. An extension is tied to its date and never cleared: compare dates, don't delete it the next day.
- **A guest's basket holds only the guest's own dishes; what order flows put on is worked out from it every time** (the kiosk's `flowsNow()` / `kioskFlows()`, the ordering page's `priceBasket(..., { flows })`). Never push a flow's dish into `state.basket` or the stored basket (`maca_basket_<venue>`): it would count as the guest's own (setting off prompts, counting towards the minimum order, never coming off when the order stops matching) and go to the server without its flow mark. What the guest took off and the prompts answered are kept beside the basket (`flowsOff`, `flowsAsked`) and cleared with it.
- **Online, only the server decides what flows put on an order** — `createOrder()` and the quote work the flows out again from the guest's own lines (`basketFlows()` + `priceBasket(..., { flows })`); a flow mark sent on a line is ignored, `flows_off` keeps only removable keys of this order's flows, and the minimum order counts `own_subtotal_pence`. A new ordering path (table QR, delivery) must go through the same two calls, or guests can drop the bag or get the minimum met by a fee.
- **A bare `<button>` on a tenant site page has no size of its own** — the ordering page's fee row had `<button>&times;</button>`, about 16 px, beside the cola's 48 px cross (found only by looking at the phone screenshot). Every tap target on `ordering.eta` and the other site templates needs a class with a 48 px minimum (`.mo-flow-x`, `.mo-btn`); check new ones in a screenshot at 390 px, not only by their test ids.
- **Running the API suite by hand needs CI's env for the Stripe files** — `stripe-connect.test.mjs` and `booking-deposits.test.mjs` assert the platform key comes from the env (`STRIPE_SECRET_KEY=sk_test_ci`, as `.github/workflows/ci.yml` sets) and hard-code `office.macaroonie.com` return addresses checked by `safeReturnUrl()` (so leave `PUBLIC_ROOT_DOMAIN` unset — it defaults to macaroonie.com). With `PUBLIC_ROOT_DOMAIN=macaroonie.test` or no Stripe key, 13 tests fail that CI passes: the suite's env, not the code.
- **A bill paid after midnight gets the promotions of the date it was paid on** — `checkOffers(..., { at })` judges a promotion at the time given, so the late tables of the day before a one-day promotion get it, as they should. A test that a promotion is *not* on a day must compare with a day well away from it (the till test uses 15 days back), never the day before.
