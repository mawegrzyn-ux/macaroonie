# Pepper (AI)

Covers: the staff AI assistant, its tools and chat loop, the MCP connectors, the AI readers (menus, invoices, receipts), new locations with Pepper and the venue wizard.

Key files and mistakes to avoid for this area: read it before changing code here. What shipped and when is in `docs/claude/history/pepper.md`; the index of all areas is in `CLAUDE.md`.

## Key files

Under **API**, `src/...` means `api/src/...`; under **Admin portal**, `src/...` means `admin/src/...`. Other paths are from the repo root.

## Mistakes to avoid

> Append-only: never delete an entry, only correct one that turns out to be wrong. New entries go at the end.

- **An AI tool that changes a booking must call the admin (or widget) route through `callApi()`, be `confirm: true` with a `describe()`, and `audit()` its outcome** — writing bookings with the tool's own SQL skips the route's role checks, emails and timeline push, and a write tool without `confirm` runs the moment the model calls it in a chat, with no Confirm card. Read tools filter `tenant_id` explicitly. Guest tools must never return `manage_token` (the AI would hold the guest's master key); changes go through the emailed code in `ai/codes.js`.
- **Never edit stored `ai_messages` or a conversation's `system_prompt`, and don't put anything that changes (today's date, the venue list) into a system prompt** — the chat replays the stored history to the model unchanged each turn; editing an earlier message or re-rendering the system prompt invalidates the earlier thinking blocks (a 400 on accounts where that is enforced) and breaks the prompt cache. Tools give the date (`list_venues`, `get_restaurant`). New information goes in as a new appended message, as the Confirm notes do.
- **Personal access tokens (`mcp_...`) are accepted only by routes with `config: { allowAccessToken: true }` (the staff MCP) and by in-process calls carrying `INTERNAL_CALL_SECRET`** — don't add `allowAccessToken` to an admin route: a leaked token would then reach the admin API directly instead of only the booking tools. A token stands for its `users` row (role, custom role), so revoking the user (is_active false) also stops their tokens.
- **The Anthropic key comes from `activeKey()` in `src/ai/apiKey.js`, never from `env.ANTHROPIC_API_KEY` directly** — a key saved on the Platform page (`platform_secrets`) wins over the env var, so code that reads the env var ignores it, and `chatConfigured()` is async (an unawaited call is a Promise, always truthy, so a "no key" check silently passes). Each PM2 process caches the key for 15 seconds, so a save reaches the other processes within that time; a new place that calls Anthropic must take its key from `activeKey()` per call (or rebuild its client when the key changes, as `chat.js` does), and must never log or return the key.
- **Never store file bytes in `ai_messages`; a stored attachment block carries only `_attachment` and gets its data from `withFileData()` at send time** — the history is replayed on every request, so data in the rows would be re-read (and kept) every turn, and anything that rewrites or re-encodes a stored block breaks the replay and the prompt cache. A new kind of user content block with a marker must be handled in `clean()` (strip / fill it before sending) and in `displayItems()`, or the marker reaches the API (400) or the file never shows in the chat. Files are served and sent only to their uploader (`user_sub`) within the tenant, and an upload is claimed by a message once; keep both checks in any new route that touches `ai_attachments`.
- **A chat turn that Claude rejects because of an attached file must leave nothing behind** — `runTurn()` stores the user message before the first model call, so a 400/413 then would leave a message every later request replays and fails on, locking the chat. `withdrawMessage()` removes it (only while it is still the last row) and frees its files; any new early-failure path after `appendMessage()` (a new validation, a new pre-call check) must withdraw the same way or throw before appending.
- **Every staff AI tool needs a `section` from `SECTIONS` in `tools/index.js`, a chat label and an Activity label** — the registry throws at start-up without a known section (older files get theirs from `withSection()` by file), and a new area must be added to `SECTIONS` and to the area list in `staffInstructions()` (`prompts.js`), or tool search won't find it from the words staff use. Read tools need a `TOOL_LABELS` line in `chat.js` (else the step shows the raw tool name); change tools need `TOOL_LABELS` + `changeDetail()` in `AiAssistant.jsx` for Activity. Only add a tool to `CORE_TOOLS` when it answers an everyday question: each one is sent in full in every staff chat request. (Corrected 22 Nov 2026: `SECTIONS` is built from each tool file's `sections` export, a tool without a `section` takes its file's only area, and `withSection()` is gone; a new area goes in its tool file's `sections` and its words in that file's `promptLines` / `promptNotes`, not in `prompts.js`; the chat line is the tool's own `activity` (`TOOL_LABELS` in `chat.js` is gone, `ACTIVITY` is built from the tools); a change tool's Activity tab words are still `ACTION_LABELS` in `shared/pepperActions.js` (imported as `TOOL_LABELS` in `AiAssistant.jsx`) and `changeDetail()` there; a core tool is marked `core: true` on the tool.)
- **Never answer, strip or rewrite `server_tool_use` / `tool_search_tool_result` blocks** — they are the API's own tool search, answered by the API in the same response. `clean()` must pass them through, `handleToolUse()` must answer only `tool_use` blocks, and the whole assistant message is stored and replayed as returned. A `tool_result` for a `srvtoolu_` id, or a reply missing the search blocks, is a 400 on the next request. `stop_reason: 'pause_turn'` means call again with the conversation as it is, not "finished".
- **A confirm tool whose input defaults to "now" must return `pin` from `describe()`** — a chat card is run up to 30 minutes later from the stored input, and `run()` re-plans, so today / this week / the check due now / "order 12" (a day's number) would resolve again at Confirm: a cash day submitted at 23:55 and confirmed at 00:05 would submit the wrong day. `pin` holds the resolved values (`date`, `week`, `from` / `to`, an id for an order, check time or session, a refund amount); `handleToolUse()` merges it into the stored input and re-validates it, so every pinned value must be accepted by the tool's own schema (ids go through `pickByName()`, which matches ids first). MCP calls `run()` straight away and needs no pin.
- **Anything that writes to a chat's history or settles its cards must run inside `withHold()` (`ai/chat.js`)** — a turn, a Confirm and a Cancel each hold `ai_conversations.running_until`; a new path (another route, a job that carries a chat on, a retry) that appends to `ai_messages` without it can land between a tool call and its result, and every later request in that chat fails. The hold is a lease in Postgres because the API runs several processes: never replace it with in-memory state.
- **A chat with `closed_at` set has had its history edited and must never go to the model again** — erasure (`eraseFromAi()`) replaces text and drops thinking blocks, so a replay would fail or be wrong. `runTurn()` refuses it; any new way of running or continuing a chat (another channel, a job) must check `closed_at` first. Don't add a "reopen" action.
- **New places that keep guest details from AI chats must be covered by `eraseFromAi()` and `cleanUpAi()` (`ai/erase.js`)** — a memory, summary or transcript table (or a new jsonb column on cards / the audit) that isn't scrubbed there leaves an anonymised guest in Pepper's records, and one that isn't cleared there is kept for ever. Erasure must stay inside the anonymise transaction, so it either all happens or none of it does.
- **Every model call for a tenant is counted with `addUsage()` with its `model` and, for staff, its `person`, and checked first with `chatUnitsLeft()` / `personUnitsLeft()`** — a call without `model` is weighted as if it were the default model, one without `person` doesn't count towards (or respect) the person's daily share, and one without the checks can spend past the allowance. The allowance (`monthly_token_limit`) is in units (`usageUnits()`), never compare it with raw token counts.
- **Every Pepper model call goes through `callModel()` in `ai/chat.js`, and nothing on its stream listener may throw** — the listener runs inside the SDK's event emit, so an exception there errors the whole stream and fails the step. Don't switch it to the stream's async iterator either: leaving a `for await` early (an error in the loop body) aborts the model call. Send what the browser should see through `emit` / `streamEvents()`, which swallow their own errors.
- **A chat stream opens with its first event, so anything that refuses a message must run before `turn()` emits `start`** — up to then an error is a normal JSON reply (status code, composer keeps the text); after it, it is an `error` event inside a 200, and the composer only puts the message back when the event says `withdrawn`. A new early check belongs before the user message is stored.
- **A chat only moves up a model, and only `modelOf(conv)` decides which** — `upgradeChat()` sets `model_tier = 'main'` for good; the main model reads the everyday model's thinking blocks, the reverse drops them. Never pick a model per request elsewhere. A new model needs a `PRICES` row in `ai/context.js` (else it counts at default ratios) and, if it has no server-side fallback, a match in `NO_FALLBACK()`.
- **A message Claude refuses must not stay in the chat history** — it would be sent again merged with the next message (back-to-back user rows are merged) and most likely refused again, stalling the chat. `turn()` withdraws it when nothing of the turn's reply was stored; a new path that ends a turn on a refusal must do the same.
- **The chat's parents key `ChatView` by conversation id, so it remounts when a new chat gets its id** — anything from a new chat's first turn that must still show afterwards (a notice, an error) goes through the module-level `carried` map in `ChatView.jsx`; component state alone is lost at that moment.
- **A Help page subsection heading (`<H3>`) must be plain text** — the page gives an H3 its anchor id only when its children are a string, and Pepper's `how_do_i` links answers to `/help#<helpSlug(heading)>`; a heading with markup inside (`<H3>Tips {' '}...</H3>`, a `<Mono>` in it) gets no id, so Pepper's link lands at the top of the page. `api/test/pepper-help-briefing.test.mjs` fails on one. Two H3s with the same text link to their section instead, so keep headings distinct. Help sections need `<section id="..." data-help="">` exactly as the others, or the index skips them.
- **A `day_briefing` part must call an existing reading tool's `run()`, never query tables itself** — the parts run as the person asking and rely on each tool's own permission check (a 403 becomes `not_included`). A part with its own SQL would show a role figures it can't see on their page and skip the tenant checks the tools already have. Pass the venue to those tools by id (`v.id`), not its name: two venues can share a name.
- **The page note is information from the browser: only `pageNote()` turns it into words** — it takes the page's name from `ROUTE_CATALOG` and the venue's from the tenant's own venues, never a label the browser sent; keep it that way for anything else the drawer starts sending (a selected booking, a filter). The `_page` block is stored with the message and replayed; never rewrite it later, and never show it as the person's own words (`displayItems()` skips it).
- **A path that finds its tenant itself must use system mode, then filter by what it found** — public pages and APIs reached by a slug, token or id, device and webhook routes, MCP and access tokens, auth's membership look-ups, background jobs and sweeps, the platform pages. On the bare `sql` pool they find nothing (a 404 or an empty list, never an error). Keep system mode to the look-up and switch to `withTenant(found.tenant_id, ...)` for the rest where you can. Add such a path to `api/test/system-paths.test.mjs`.
- **A new staff tool's area must name every module the tool checks in `SECTION_MODULES` (`ai/tools/index.js`; since 22 Nov 2026 the `modules` of the area in its tool file's `sections` export)** — the staff connector lists a tool only when the person has View (Manage for a change tool) on one of its area's modules; a tool that checks a module the map leaves out is hidden from people who could use it. Over-including is safe (the tool still refuses), under-including isn't. Start-up throws when an area has no modules or a module key doesn't exist.
- **Pepper's model has no clock: the date reaches it only through the `[Now: ...]` line `nowNote()` puts before every staff message** — never put the date in the system prompt (stored once per chat and replayed with the cache), and don't make a tool's date required when today is the obvious default (a required date made the model guess one, then blame "the app's clock"). A new channel that runs the staff model (another screen, a job that carries a chat on) must add the line too; a new hidden block before a message needs a marker that `clean()` strips and `displayItems()` skips, as `_context` is.
- **The staff connector's OAuth sign-in gives out ordinary access tokens (`ai_access_tokens`)** — so revoking, expiry, read only and the MCP tool list work the same for a signed-in app as for a token made by hand. Don't add a second kind of token for OAuth apps, and keep `/oauth/` and the `.well-known` metadata paths in platformSite.js's `PASS_PREFIXES`, or the apex hook sends apps to the office site. `GET /oauth/authorize` must never redirect to an address the app didn't register (a page instead), and a code must stay single use.
- **A new per-venue setup table must be added to `services/storeSetup.js`, or New location silently leaves it out** — `createStore()` copies only the tables its `AREAS` functions name. A table whose rows other rows point at by id (a station, a section, a printer) must also be in `OWNED_TABLES`: `copyTable()` drops any id the template venue owns that wasn't copied, and a table missing from that list keeps its id, so the new location's copy points back at the template's row (the store-opening test scans for exactly that). Copy children through `copyTable()` with `parentCol` / `parents` after their parent, in `AREA_ORDER`, never with your own INSERT ... SELECT, which skips the id remapping.
- **What a new location gets is decided by `normalisePlan()` in `shared/storeOpening.js`, never by the AI's answer directly** — every step merges the answer with the person's own overrides through it, and `createStore()` reads only its output. Don't read `opening.ai` in the create path or the page, or a field the person changed by hand reverts to Pepper's guess. A new area needs an entry in `OPENING_AREAS` (its modules decide who may set it up), its plan fields in `normalisePlan()`, a function in `AREAS`, a link in `AREA_LINKS` and the answer schema in `storeOpeningAi.js` (all properties required, empty values for unset: structured outputs refuse optional fields).
- **Store-opening routes live under `/api/ai/` for the 5-minute proxy timeout** — a Pepper step can take over a minute; mounted anywhere else, nginx answers 504 at 60 s while the step carries on and its answer is lost. A new long AI route must be under `/api/ai/` too.
- **A device's `card_reader` is a `pos_card_readers` id of its own venue, or `'none'`** — `checkDeviceSettings()` refuses another venue's machine, and a new location's copied devices get `'none'` (`storeSetup.js`). Code that writes device settings another way (a migration, an import, the installer) must keep that, and must never write the old `'test'` value (migration 193 turned those into Test card machine rows).
- **What the venue wizard set always wins over Pepper's plan** — `normalisePlan()` reads each area setting through `pick()` (`overrides[key]` before the AI's raw plan), so a describe step after the person filled in hours or tables can't change them. A new wizard setting needs its key in `SETTING_KEYS` (else the PATCH refuses it), its cleaner in `normalisePlan()`, and its use in `storeSetup.js`. Wizard drafts carry `overrides.wizard = true` and may be created without a ready plan; other openings still need one.
- **Pepper's structured-output readers share `askForJson()` (`services/aiJson.js`)** — it checks the monthly allowance and the person's daily share first and counts the usage after; a new reader (a document, a photo) must use it rather than a fourth copy of the Anthropic client, or it skips those checks. Its route goes under `/api/ai/` for the proxy timeout and checks Pepper is on (`pepperOn()` in `routes/documentRead.js`).
- **Code that looks something up per catalogue page's module must skip pages with none** — a `ROUTE_CATALOG` entry without a `module` (Today, since migration 227) is open to everyone signed in. Pepper's `open_page` asked `staffPermissionLevel()` for every entry's module, `undefined` included, and that lookup threw for everyone who isn't a platform admin (they return before the query), so Pepper couldn't give any page link from 31 Oct to 12 Nov 2026. No test called the tool. Filter the modules (`.filter(Boolean)`), treat no module as visible (`!p.module || ...`, as `navItemVisible()` does), and test a Pepper tool on the staff connector as an ordinary owner and as a role without the area (`api/test/nav-search-ai.test.mjs` does for `open_page`), never only as a platform admin, who skips every permission check.
- **A chat's tool list can change between two messages, and replies' thinking is only valid with the list it was written under** — the web search switch (migration 242), and any deploy that adds, removes or changes one of Pepper's tools. This refines "Never edit stored `ai_messages`..." above: the stored rows still never change, but what is sent may leave blocks out, by a recorded rule so every later request leaves out the same ones. A new thing that changes what `toolDefs()` returns for a chat that already has replies (a tool per role, per venue, per plan, a new server tool behind a switch) needs nothing more than going through the turn's `thinkingFor()` / `keepToolList()`, which compare `toolsKey()` with `ai_conversations.tools_key`; never pick tools per request (within one turn the list must not change: the retry without web search works out a new `era` for that reason), and never move `thinking_from_seq` back. Blocks that only make sense with a tool (`server_tool_use` / result blocks, citations into its results) are left out in `apiMessages()` while the tool isn't sent, never deleted.
- **What the model was last told about a switch is read from the chat's stored messages, never kept in a column** — `webSearchTold()` finds the latest hidden `_web` line. A column would be wrong after a message is withdrawn or a turn fails before the model read it (the chat would count as told while the history says otherwise, and the model would be promised a tool it doesn't have, or never told it lost one). A new hidden line of this kind needs a marker `clean()` strips and `displayItems()` skips (as `_context` does), a place in the staff prompt saying such lines come from the app, and the same read-back.
- **Web search stays in the staff chat, behind the group's switch, with every change still behind a Confirm card** — a web page is text from strangers. Don't add the tool to the guest website chat (a public page that could be pointed at a page written to steer it, at the group's cost), don't run a change tool straight from a turn that searched, and don't render links from a model's text as outside links: the only links that leave the app are an answer's `sources`, which come from the API's own citations (`addSources()`: http / https only) and are drawn by `Sources` with `rel="noopener noreferrer nofollow"`. Anthropic's web search documentation says answers shown to end users must come with their citations, so a new place that shows a chat's answers (an export, an email of a chat, another app) must show `sources` too.
- **Every model call that can search the web must pass `searches: searchesIn(usage)` to `addUsage()`** — a search costs $10 per 1,000 whichever model asked (2,500 units), on top of the tokens its results add, and `usage.server_tool_use.web_search_requests` is the only place it is reported. Local info's `searchForJson()` counted only tokens until migration 242. And a request that carries a server tool can be refused for the tool alone (web search can be switched off for an Anthropic organisation: a 400 on every request that carries it), so anything that adds one must still answer without it, as the chat's second try does, or it stops working for everyone the day the setting changes.
- **A settings save must show what was saved from the PATCH reply, and a figure another screen changes must be invalidated there** — the Pepper Settings switches flicked back to their old places for a moment after Save (the draft was cleared before the refetch landed) until both saves put `res.settings` into the `['ai-settings']` query with `setQueryData()`; and the month's usage on that tab stayed up to 30 s old after a chat (the app's `staleTime`) until `ChatView`'s `apply()` invalidated `['ai-settings']`. A browser check that watches the control while saving (a MutationObserver on `aria-checked`) catches the first; reading a figure straight after the action that changes it catches the second.
- **Over the staff connector a confirm tool's `run()` is called without `describe()`, so every refusal must be in `run()` too** — in the chat the card comes from `describe()` and Confirm runs `run()`; an app on the connector calls `run()` straight away. `change_report` refused an empty change only in `describe()`, so over the connector it answered as if it had saved (`somethingToChange()` now runs in both). A new change tool must check in `run()` everything its card checks.
- **Pepper's run limit counts `report_runs` rows marked `via: pepper`, so a report route Pepper calls must call `limitPepperRuns()` before running and `recordRun()` with `via` after** — a route that runs a report without recording it is a way round the 20 a minute. A run that fails is recorded (and counts); a plan that names nothing runs nothing and isn't.
- **Fields of a request that only give context must never refuse the request** — the chat body's `page` and `page.report` are dropped when they don't fit (`.catch(undefined)` in `routes/ai.js`). The page's address was checked by a regex without `:`, so from the day reports shipped every Ask Pepper message sent from a starter report page (`/reports/starter:till_sales_by_day`) was refused with a 400 until 13 Nov 2026. Context is a nice-to-have: drop what doesn't fit and answer the message.
- **A report's name reaches Pepper's page line only from the report route called as the person (`reportNote()` in `ai/chat.js`), on one line (`oneLine()`)** — the page's `label` (what the drawer's chip shows) is never sent, so a name can't be made up by the browser or shown to someone who can't open the report, and a name a group typed can't add a line to a hidden note. A new page that tells Pepper what is on screen sends ids, never names.
- **Browser checks: two traps met on the report pages' Pepper drawer** — a selector that matches a hidden button as well as a visible one (the sidebar's Ask Pepper and the touch rail's on a phone) waits on the hidden one with `.first()`: add `:visible`; and a card that shows a report's first rows shows none when the report's period doesn't hold the seed's days (the test seed sells on today, so "last 7 days" is empty): pick a period that holds them, as with the `Today` entry above.
- **What Pepper learned from flags reaches a search only through `learnedLine()`, and is data, never instructions** — the findings it learned from are text from web pages, so `LEARN_SYSTEM` says they are data, the phrases are clipped (`LEARN_MAX`, `LEARN_PHRASE`) and the line goes after the operator's own words, never in their place or into a system prompt; while `learn_auto` is off it isn't used at all. A new place that uses `learned` (another kind of capture, Pepper's own searches, a report) must read it the same way.
- **A card of a tool's own (`display()`) is built from the tool's stored result, never from the model's words** — `handleToolUse()` streams it and `displayItems()` rebuilds it from the `tool_result` block (`DISPLAY_TOOLS`), with no tool context, so `display(out)` must work from the JSON alone and must not hold anything the person may not see (the tool checked that when it ran).
- **A spoken yes confirms only `VOICE_CONFIRM_TOOLS`, and only with `ai_settings.voice_confirm` on** (migration 261) — the confirm route checks both whatever the client says (`voice_ok` on a card is only a hint). Adding a tool to the list is the user's decision: money, orders, bookings, the rota and anything deleted keep a tap.
- **Speech recognition can end by itself at any moment (a pause), so a hold must keep it going while the button is down** — the chat's mic decides tap or hold after `MIC_HOLD_MS`, and a recognition that ended in those first milliseconds used to stop the hold as if it were a tap, sending half a sentence. `micListen()` restarts on every end while `mic.down` is true, and sends only after the release; a new press-and-hold control must judge by the press, not by whether the hold time has passed.
- **Android's speech recogniser reports some endings as errors: `client` ("Other client side errors.") after a stop() with nothing new said, `no-speech`, `speech-timeout`, `aborted`.** Showing them, or treating them as a failure, threw away a held message's words in the Office app. `office-app/speechCore.js` keeps them quiet; only real failures reach the page. Holds ask for `continuous` listening (one listening through pauses, no restart beeps); a browser still ends on a pause, so the page's restart-while-held stays.
- **A press-and-hold button in a web view needs `touch-none` (touch-action: none), not `touch-manipulation`, plus `setPointerCapture`:** with manipulation the web view may take a slightly moving finger for a scroll and send pointercancel mid-hold. Pepper's mic (`MicButton`, the only talk button) is `touch-none`; a pointercancel keeps the words in the box and sends nothing.
- **Pepper's microphone has one implementation: `useMic()` / `MicButton` in `admin/src/components/ai/mic.jsx`** (ChatView's box and the phone home's AskPepperBar). A new place to talk to Pepper uses it, never its own copy of the tap / hold / restart-while-held logic. A question asked somewhere else goes to the Pepper page in the address's state (`{ ask: { text, voice } }`, ChatView's `ask` prop): it continues the remembered chat, so read aloud and the spoken yes run in a mounted view; and it is taken off the address at once, or a reload sends it again.
- **A model the tenant can be routed to needs a row in `PRICES` (`api/src/ai/context.js`)** — a model without one is weighted as `OTHER` (input 1 unit, output 5, cache read 0.1, cache write 1.25), which undercounts a dearer model (Claude Fable 5.2 is $8 / $40, twice that). Cache reads are not a fixed tenth of input: $0.20 on Opus 5.5 and Fable 5.2, $0.10 on Sonnet 5.5. Take the four figures from the price list when a model id is added to `AI_MODEL` / `AI_MODEL_FAST` or the settings.

- **A staff tool file must never import `tools/index.js`, `chat.js` or `prompts.js`, nor anything that imports them** (22 Nov 2026) — the registry is built while `tools/index.js` loads, so a tool file that leads back to it sees it half-built.
