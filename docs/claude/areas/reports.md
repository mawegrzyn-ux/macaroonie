# Report builder

Covers: the report definition, catalogue, engine, builder, drill-downs, charts, print, files, schedules, data links, the smart builder and Pepper report tools.

Key files and mistakes to avoid for this area: read it before changing code here. What shipped and when is in `docs/claude/history/reports.md`; the index of all areas is in `CLAUDE.md`.

## Key files

Under **API**, `src/...` means `api/src/...`; under **Admin portal**, `src/...` means `admin/src/...`. Other paths are from the repo root.

## Mistakes to avoid

> Append-only: never delete an entry, only correct one that turns out to be wrong. New entries go at the end.

- **Trust but verify (session summaries)** — never reference session-summary items as "still open" without checking the actual code. Session summaries go stale between runs. Always grep / check live code before claiming something is pending.
- **A report's SQL takes its names only from the catalogue and its values only as numbered parameters** — `compileReport()` (`api/src/reports/compile.js`) looks every subject, field, measure and link up in `api/src/reports/catalogue/` and adds everything a person gave (a filter's value, a period, venues, a top N) through its parameter list; `$1` is the tenant id, on the base rows and on every joined row. A new operator, bucket, sort or drill step must keep both rules: never build SQL from a definition's own words, never store SQL on a report, and never give a catalogue template a value from a definition (templates know `{t}`, a link's name and `{tz}` only). The catalogue is checked when the API starts (a link to nothing, a template naming a link the subject lacks), so a mistake there stops the start, not a report.
- **A report builder table or column needs a decision, or the catalogue test fails** — `api/test/reports-catalogue.test.mjs` compares the catalogue with `information_schema`: a new table needs a subject or one line in `decisions.js` (`PLANNED`, `SETTINGS` or `LEFT_OUT` with a reason; since 22 Nov 2026 the line goes in the `decisions` export of the catalogue file of the area that owns the table, never in `decisions.js`, which only gathers them), and a new id column on a table the catalogue reads needs a field, a link or a `skip` entry on its subject. `skip` means left out on purpose, with the reason beside it: don't use it to quiet the test for a column a report should be able to follow. A column whose name looks like a secret (`SECRET_COLUMN` in `coverage.js`) may never be read by a template.
- **A measure must leave out what doesn't count by its own `where`, not by a starter's filter** — a starter that filters to closed checks hides a `net_sales` that would otherwise add open and cancelled ones, and the next person who builds a report without that filter gets a wrong figure. Test a measure by running it with no filter beside the page's own figure (the reconciliation tests do). And a money field whose rows mix what adds and what takes away (a payment beside its refund, `till.payments.amount`) is `adds: false`, so a list doesn't total it; the subject's measures add it up the right way round.
- **A summary's subtotals and totals come from the one statement's GROUPING SETS, never from adding rows up afterwards** — an average, a ratio or a count of different things isn't the sum of its parts (two days' "different guests" share guests). `shape.js` only arranges what the database returned. For the same reason a figure reached through a `one` link may only be how many different, smallest or largest (a sum would count a check once for each of its lines), and one through a `many` link is added up per base row in a LATERAL subquery before anything is grouped.
- **A report shows each person only what their role may see, decided at every run, never stored on the report** — `runReport()` compiles against the runner's own module levels: a subject needs its module, a field or link marked `needs` that module too, and counting another subject's rows through a `many` link needs that subject (looking one row up through a `one` link, a server's name on a check, doesn't). A list column the role can't see is left out with a note; grouping, filtering or sorting by one is refused (403), because a filter on a hidden field tells by its row count what the field holds. Don't add a "run as its owner" mode or keep rows with a shared report.
- **Who may open a saved report is written twice, as `rightsOn()` (one report by id) and as SQL in `openTo()` (the list): change both, and test both** — a rule changed in one lets a report be opened by its address while missing from the list, or the other way round; `reports-api.test.mjs` asks the list and `GET /:id` for each case. A definition or a run that names a venue must go through `refuseOtherVenues()`: the app-wide `refuseOtherTenantsVenues` only sees keys named `venue_id(s)`, and a report's venues sit in `params.venues` and in filter values.
- **A run's record never holds what a person typed** — `recordRun()` keeps the period and venues, any other choice as a number or yes / no, typed words only as `{ set: true }`, and a drill as the fields it went through without their values (a drill into one guest would otherwise keep their name in `report_runs` for 400 days). A new kind of parameter must be added to that rule before it is recorded.
- **postgres.js through `tx.unsafe(text, params)` (the report engine's statements) is not the tagged template** — an array of true / false is sent as one boolean ("cannot cast type boolean to boolean[]": send `'y'` / `'n'` words in a `text[]`), a null inside an array arrives as the string NULL (keep a second array saying which are empty), and a jsonb-typed parameter is encoded twice (send native arrays, `$n::uuid[]` / `$n::text[]`; in tagged queries jsonb goes in with `tx.json()`). And any postgres.js result is an Array subclass, so `assert.deepEqual(rows, [])` fails on an empty one: compare `rows.length`.
- **Every pool must be ended where the others are** — `reportSql` (the report builder's) is closed with `sql` and `systemSql` in `server.js`'s shutdown and in the tests' `closeApp()`; a new pool left out keeps the process alive after its work is done. For the same reason a script that imports the catalogue, the engine or anything else that imports `config/db.js` needs the API's env and must end with `process.exit()` (`api/scripts/report-catalogue.js`).
- **A starter report is checked when the API starts and must come through `normaliseReport()` unchanged** — one the check would change (a part that doesn't fit its kind, a default it would drop) or that has a problem stops the start, so a starter can never be a report that half works. A definition's kind is worked out from its parts (columns: a matrix; else values: a summary; else a list) and a part that makes no sense with the rest is dropped without a word, so a test that sends `kind: 'list'` with values gets a list without them. A starter's description must say which day its rows sit on when that isn't obvious (a deposit on the day paid), and a date field labelled for its day keeps its words when grouped ("Day paid" becomes "Week paid").
- **A file streamed from a database cursor must stop when the reader does** — `csvExport()` writes a list a thousand rows at a time from a cursor on one of the report pool's few connections. Its stream needs an `'error'` listener, and the wait between batches must end on `'close'` as well as `'drain'`: a download cancelled half way never drains, and without both the cursor and its connection stay taken for good (a few cancelled downloads would stop every report). In a spreadsheet a date is written as a serial number with a date format, never as a JS `Date` (SheetJS converts it through the server's time zone); reading a file back in a test needs `XLSX.read(buf, { type: 'buffer', cellNF: true })` to see the formats.
- **Report results are kept for a minute per person, definition and choices, in each API process** — a test or a screen that changes data and reads the report again must send `fresh: true` (Refresh does) or call `forgetReportResults()`; without it the old figures come back and look like a bug in the change. Fixtures that add rows other tests count take an option to leave them out (`fillTenant(..., { reports: false })`, as `reports-api.test.mjs` starts).
- **A query for something that can be refused must not retry the refusal** — the admin's QueryClient retries a failed query once, so "Your role doesn't have access" or "Report not found" showed only after a second of "Loading". The report pages pass `retry: retryUnlessRefused` (`components/reports/shared.jsx`: no second try for a 4xx, one for anything else). A new page whose first query can come back 403 or 404 needs the same, and a browser check should time how long the refusal takes to show.
- **Words that say "you" must check the row is the viewer's own** — someone with Manage sees other people's private reports, and the list said "Only you" on them. `sharedName()` in `Reports.jsx` says Not shared unless `r.mine`. The same goes for any "your" / "only you" / "you made this" wording on a list a manager can see more of.
- **A pinned (sticky) cell needs the same opaque fill as the rest of its row, and a date, a time or a number in the pinned first column must not wrap** — `ResultTable`'s first column stays put as a wide table scrolls sideways: a subtotal row whose pinned cell had another fill looked two-tone, and a width cap meant for long names (a dish, a reason) broke "Mon 19 Oct 2026" onto two lines at every width. Only text and choice columns wrap (`firstWraps`); the rest are `whitespace-nowrap`. Same family as the sticky header entries above: the pinned cell is what everything else scrolls under.
- **What the report builder offers and what the engine runs are kept together by one test, not by care** — `shared/reports/build.js` (`pathUses()`, `dataTree()`, `filterOps()`) decides what the screen offers, `api/src/reports/compile.js` what runs. `api/test/reports-build.test.mjs` runs every grouping, column, value and way of filtering the Data panel offers, for every subject, and checks that what the builder leaves out is refused by the engine. A new offer (another way of adding up, another operator, links walked deeper), a new field type or a new subject must keep it passing; a new field type also needs `filterOps()`, `filterValueKind()` and an input in `ValueInput.jsx`. The first run of that test found a real fault: a time filtered by is empty.
- **A statement parameter that is added and then not used is an error to Postgres ("could not determine data type of parameter $n")** — in `conditionSql()` (`api/src/reports/compile.js`) a moment's day was worked out before the operator was looked at, and working it out adds the group's time zone as a parameter (`st.tz()` through `tzOf()`); "is empty" and "isn't empty" then returned without the day, so the statement carried a parameter nothing used and every such report failed. Take a parameter (`st.p()`, `st.tz()`) only on the path that puts it in the SQL: look at the operator first.
- **Which figures can be added up through a list of rows is one list: `ACROSS_AGGS` / `worksAcross()` in `api/src/reports/catalogue/index.js`** — the engine's `measureFigure()` refuses by it and `catalogueView()` marks those measures `across`, which is what `pathUses()` reads. Don't write the rule again in the builder (an `agg !== 'avg'` of its own): the two would drift, and the builder would offer a figure the engine refuses, or hide one it runs. A ratio works across only when both of its parts do and the role may see both.
- **A condition inside a "has" filter is a path from the linked rows, not from the report's own** — `{ has: 'payments', where: [{ field: 'tender', ... }] }`: `tender` is a field of a payment. Anything that reads a filter's field (its words, its input, its parameter) must resolve it against that subject: `walkFilters()` in `shared/reports/build.js` hands it over, `paramInputs()` returns it as `subject`, and `paramWords()` / `ValueChoice` use it. Resolved against the report's subject, the field isn't found and a choice the report asks for shows no input.
- **`catalogueView()` lists every subject, also ones the role can't report on (so a server's name on a check still resolves): "can build a report on it" is `subject.base`** — the picker filters by it and `ReportBuilder.jsx` refuses `?subject=` and `?from=` on a subject without it. A list drawn from `Object.values(catalogue.subjects)` alone offers subjects whose preview the API answers with a 403.
- **The builder changes a report only through the edits in `shared/reports/build.js`, and reads what the report is after each one** — every edit returns `normaliseReport()` output (or the same object when nothing changes: compare with `===` to say "it is in the report already"), and that drops parts that no longer fit: a top few goes with its last grouping or its last shown value, a subtotal with its grouping, a parameter with the last filter that asks for it, the comparison when a column goes across the top. Never keep a copy of such a part in component state and write it back, and never build a definition by hand in a component. The one deliberate memory is `stash` in `ReportBuilder.jsx` (what a summary and a list each had, while the page is open).
- **A box bound to the definition loses what is being typed: every edit trims** — `normaliseReport()` trims labels and drops what isn't valid, so an input fed straight from `spec` loses the space at the end of a word and can't be emptied on the way to another number. The builder's windows keep their own state until Apply; boxes that change the report as you type keep the typed text while they have the focus (`WordsBox`, `CountBox` in `builder/SetUp.jsx`, `NumberBox` in `ValueInput.jsx`). A run's `delivery` record holds counts and masked addresses (`maskEmail()`), and Pepper's audits counts only: never a whole address.
- **Outside addresses, and people's details going to them, need an owner or admin, decided by the server when a schedule is saved and again at every send** — the routes refuse an outside address from anyone else, and `deliver()` holds people's details back from outside addresses unless `personal_outside` is on (`PII_HELD`). The schedule window only shows what the server's dry run said. A new setting that widens who gets what must be refused in the route the same way, never only hidden in the window.
- **A report's venues and the time zone its schedule runs on come only from `venueScope()` (`shared/reports/spec.js`)** — the run, the schedule routes and the schedule window's next send all call it (the first venue in scope, venues in the order they were made). A copy of the rule in a component or a route shows one next send and runs at another for a group with venues in two time zones.
- **`sweepSchedules()` writes a schedule's next regular time before it sends, and holds the schedule by a lease in Postgres (`running_until`, FOR UPDATE SKIP LOCKED)** — so a crash after sending never sends a run twice, and two API processes never run one schedule at once. A new step in the sweep comes after the claim and never moves `next_run_at` back; a retry is a nearer `next_run_at` with the time the run was first due kept in `retry_of`; and the run's "today" is that due time (`ctx.at`), so a report sent an hour late still covers the day it was meant for.
- **A page of reports drops a page break that comes first, follows another break or ends the page (`normalisePage()`): an editor that lets someone add one must say so** — the page editor first let a break be added at the end with nothing to say it would be left off, so it vanished on save. - **A key that opens data without a login is kept only as its hash, shown once, and must never reach a log** (migration 256) — a data link's key (`mrd_`) is compared as sha256; the public route takes it from a header first and is logged at warn (`logLevel: 'warn'`), since a key in `?key=` would otherwise sit in every request log line. A new public route that takes a secret in the address needs the same, and a new link kind must run as its maker loaded afresh at every call (`ownerPerson()`), never as a role stored on the link.
- **A post to an address someone typed must check every address its host resolves to, at the time of the post, and connect to the address it checked** (`services/webPush.js`) — checking only when saved lets a name be pointed at the server's own network later, and resolving twice (once to check, once to connect) lets it change in between. Never follow redirects from such a post, and keep https only.
- **A schedule's `delivery.today` is stored only when true, and only scheduled sends may carry it** — `normaliseDelivery()` adds the key only when it is on (a `today: false` on every delivery broke every test comparing a delivery), and `prepareSend()` deletes it for Email it now, so a one-off send never raises a task on Today. A run counts as an alert only when it recorded `delivery.today` and no error; the alerts route still checks, for the person asking, that the report runs (`runsFor()`) and that the venue is in its scope (`venueScope()`). A new way of raising a Today task from a report must go through the same run record and route, never write tasks of its own.
