# Local info

Covers: weather, traffic, events and incidents around each venue: captures, flags and learning, merging, bulk delete.

Key files and mistakes to avoid for this area: read it before changing code here. What shipped and when is in `docs/claude/history/local-info.md`; the index of all areas is in `CLAUDE.md`.

## Key files

Under **API**, `src/...` means `api/src/...`; under **Admin portal**, `src/...` means `admin/src/...`. Other paths are from the repo root.

## Mistakes to avoid

> Append-only: never delete an entry, only correct one that turns out to be wrong. New entries go at the end.

- **A `date` column sent back in a PATCH must go through `dayOf()` (or `::text` in the SELECT), never `String(v).slice(0, 10)`** — postgres.js returns `date` columns as JS `Date`s, and `String(aDate)` is `Sun Nov 09 2026 ...`, whose first ten characters Postgres parses as a date in year 2009, so a local info item PATCH that round-tripped the stored day would silently move events seventeen years back. `dayOf()` in `routes/localInfo.js` takes a Date or a string and gives `YYYY-MM-DD`. Third shape of the date-column trap (see the map-key `::text` and `delivery_date` entries above): it bites whenever a date column read from one query is written back in another.
- **Captured local info items are hidden, never edited or deleted** — a capture's upsert (`ON CONFLICT` by `external_key`) rewrites an item's details on every run and deliberately never touches `hidden` or `title`, so hiding is the only change that survives the next capture; the routes 422 edits of captured items and DELETE takes typed events only. A new surface that changes items (a widget action, a Pepper tool) must offer hide, not edit, for captured ones.
- **A link someone typed, a capture found or a client sent is checked and drawn only through `webLink()` (`shared/links.js`), never `z.string().url()` alone** — Zod's `url()` only checks that the string parses as an address, so `javascript:alert(1)`, `data:text/html,...` and `ftp://` all pass, and a page that puts the stored value straight into `href` makes a link that runs code in the admin of whoever taps it (a Local info event's link and a recorded review's source page did, until 14 Nov 2026; the review's comes from a page a browser client read, so from strangers). Refine the field with `webLink()` in the route (and in any Pepper tool that takes it, so the model hears the reason), and draw `webLink(value)`, never the value: rows stored before the rule still hold the old values. Test with a stored `javascript:` value, not just by trying to save one.
- **A capture's `flags_at` changes only when a flag on one of its own findings really changes, and from the same clock as `learned_at`** (migration 248) — `hasNewFlags()` compares the two to decide whether the next run learns first, which is a paid model call. The feedback PUT stamps it only when its write returned a row (the same flag again writes nothing: `WHERE relevant IS DISTINCT FROM EXCLUDED.relevant`) and only for an item of the capture's own kind; both columns are set with `new Date()` in the API (Forget sets `learned_at` too, so the capture isn't learned again until flags change). A new way of flagging, or a job that changes flags, must do the same, or every run pays to learn the same thing again; a database `now()` beside the API's clock can put a flag and a learning in the wrong order.
- **Learning before a capture's run must never stop the run** — `learnBeforeRun()` keeps a failure in `learn_error` and searches with what was learned before; anything new added before a search must fail the same way, or a refusal or a bad answer from Pepper leaves the venue with no fresh local info. Learn now (a person pressing it) also checks `pepperOn()`, like the other Pepper buttons; the scheduled path checks only the allowance, like the capture's own search.
- **A hidden captured local info item is what keeps its finding off the calendar: never delete one to tidy up** — a capture's upsert (`ON CONFLICT (source_id, external_key)`) updates a row it finds again but never un-hides it, so deleting a hidden finding lets the next run add it back as new. Bulk delete (`deleteAction()` in `routes/localInfo.js`) keeps hidden findings and hides flagged ones instead of deleting them (their flags teach the capture); a new way of clearing entries (a job, another tool, a capture deleted) must make the same choice, or say plainly that its findings can come back.
- **A local info finding with `merged_into` set is a report inside another entry, not an entry: every reader must leave it out (`merged_into IS NULL`) unless it shows an entry's other reports** (migration 249) — a list, a count, a widget, a report subject or a Pepper tool that reads `local_info_items` without it shows each event once per report again (the duplicates merging removed) and counts them twice. Copies are kept, never deleted to tidy up: like a hidden row, a copy is what stops its capture adding the same finding again (the upsert finds it by `external_key` and only updates it). A copy can't be changed, flagged or deleted on its own (the routes answer 422); flags live on the entry, so anything that reads a finding's flags must read its entry's (`COALESCE(merged_into, id)`). A new way of putting findings together must go through `foldInto()` under `lockMerges()`, which moves flags and stamps `flags_at`.
- **A flag's note belongs to its flag: the feedback PUT keeps it only when `note` is left out and the flag is the same** (migration 252) — a caller that sends a flag again must leave `note` out (`note: ''` or null takes the note off), a flag that turns the other way clears its note, and anything that moves flags between rows (`foldInto()`) must move the note with the flag it belongs to. A note change is a flag change: it stamps `flags_at` like one (so the capture learns again), from the API's clock. Notes reach the model only through `why()` in `learnFromFlags()`: clipped, on one line with `|` and `;` taken out (they are the line's own separators), and as data, never instructions (`LEARN_SYSTEM` says so). A new place that sends staff notes to a model must do the same.
- **A weather capture merges each day into what its row already holds (`mergeWeatherDay()` in `shared/localInfo.js`), never writes the day from the read alone** (22 Nov 2026) — a recorded day's `forecast` and each recorded hour's `forecast` exist only in the row (Open-Meteo no longer has them), so an upsert built from the read alone would throw away what was forecast. Readers take the day's top-level figures as the day as known (recorded once it is over, else the forecast) and `recorded` / `forecast` / `hours` for the rest; a new writer of weather days (a backfill, an import) must merge the same way, and a new reader must not treat the top-level figures as a forecast.
