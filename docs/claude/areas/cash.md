# Cash reconciliation

Covers: Cash Recon days and weeks, wages, expenses, the cash dashboard widgets, Loyverse and GloriaFood.

Key files and mistakes to avoid for this area: read it before changing code here. What shipped and when is in `docs/claude/history/cash.md`; the index of all areas is in `CLAUDE.md`.

## Mistakes to avoid

> Append-only: never delete an entry, only correct one that turns out to be wrong. New entries go at the end.

- **SC `included_in_income` XOR variance** — the two SC flags (`included_in_income` + `included_in_takings`) are independent booleans. The variance formula is `totalIncome + scAdjustment - totalTakings` where scAdjustment is the signed XOR sum. When both flags are on, the adjustment is 0 (not doubled). When only income is on, the SC is subtracted from the expected-till figure. When only takings is on, it's added. **Superseded by migration 096** (kept for history, per the append-only rule) — these two booleans were replaced by `takings_effect`/`income_effect` (`'none' | 'add' | 'subtract'` each), since a fixed always-add-on-takings/always-subtract-on-income direction couldn't express every scenario an operator needed (e.g. deducting from takings). See the newer entry below and Docs.jsx's Cash Reconciliation section.
- **Migration 027 number collision** — both `027_cash_reconciliation.sql` and `027_per_venue_websites.sql` exist. They have different version strings in `schema_migrations` so the runner applies both. Confusing but not broken. Do not renumber — would cause re-application on servers that already ran them.
- **`cash_wage_entries.total` is the full wage cost; `cash_wage_entries.cash_amount` is only the cash-paid portion** — the two are independent and legitimately differ (part or all of a wage paid by bank transfer instead of till cash). Any net-cash-position calculation in cash recon must subtract `cash_amount`/`wages_cash_total`, never `total`/`wages_total` — using the full total silently overstates the cash shortfall whenever staff are paid other than in cash. Both wage-total SQL queries in `cashRecon.js` (`week-detail` and `week` routes) return both sums; don't add a third query that only selects one.
- **`cash_wage_defaults` only stores entries with a `staff_id`** — ad-hoc wage entries (typed name, no `cash_staff` row) have no stable identity across weeks, so "Set as default" silently drops them from the saved list. This is intentional, not a bug — surfaced via a `title` tooltip on the button rather than a popup per Standard Design Rule #4. If you ever need ad-hoc entries to persist as defaults too, you'd have to give them a durable identity first (e.g. auto-promote to a `cash_staff` row), not just store the free-text name.
- **A component's own margin and a parent's `space-y-*` are two competing spacing mechanisms — don't use both for the same gap** — `CashRecon.jsx`'s daily-declaration page wrapped its `SectionCard`s in `space-y-0` while `SectionCard` itself carried `mb-4`, apparently on the assumption the two wouldn't conflict. In production the visible gap between stacked cards was zero (colour-matched header/footer accent bars touching directly, no seam) — whatever the exact cause, the practical lesson holds regardless of the precise CSS mechanics: don't split responsibility for one visual gap across a child's own margin AND a parent's spacing utility. Pick one (usually the parent's `space-y-*`, since it's visible at the call site and doesn't require reading the child's internals) and remove the other.
- **`POST` endpoints that require an id the frontend doesn't have in scope will 400 forever, silently, if the catch block is empty** — `POST /:venueId/cash-recon/expenses` required `report_id`, but its only caller (`ExpensesSection.handleAdd()`, which only has `venueId`/`date` as props) never had one to send and sent `date` instead. Zod validation failed on every call; the `catch {}` around it meant no operator ever saw an error, so "Add expense" just silently did nothing from the button's perspective while the row visibly appeared to have been added optimistically nowhere (it wasn't — `setExpenses` inside the `try` block never ran). Caught only when a second, independent caller (the mobile Expenses page) was built against the same endpoint and needed to understand its actual contract. Never wrap a mutating API call in a bare `catch {}` in new code — log the error at minimum, ideally surface it, so a broken contract like this doesn't go unnoticed indefinitely.
- **A reconciliation variance's sign convention should match the standard accounting one (Actual − Expected), and it's easy to accidentally write the reverse** — Cash Recon's variance was computed as Income (expected) − Takings (actual) in every one of its three independent implementations (`SpreadsheetView`'s `variance(date)`, the day-view's `const variance`, and `WeekView`'s per-day-card recompute). That reads backwards from what an operator expects: taking in MORE cash than declared showed as a NEGATIVE number, and less showed positive. When adding any "did the actual figure match the expected one" calculation, write it as `actual − expected` from the start and sanity-check the sign against a simple story ("I took in more than I declared — should this be positive or negative?") rather than just whichever order felt natural to type.
- **A value duplicated across 3 independent call sites can each drift differently — `WeekView`'s day-card variance referenced a field, `total_sc_in_takings`, that was never actually in its API response** — `parseNum(undefined)` silently returns `0`, so the missing field just meant "no SC adjustment ever applied here," not a crash or a visible bug — it took a deliberate read of the `/week/:week_start` route (which already computed its own, correctly-signed `variance` field) to notice the client was ignoring it and recomputing its own, wrongly-signed version from partly-nonexistent inputs. When a figure is computed in more than one place from what should be the same inputs, check whether the backend already computed it correctly before re-deriving it client-side — the duplication itself is usually the bug, independent of which copy turns out to have the wrong sign.
- **`cash_payment_channels.type` (`'cash'|'card'|'voucher'|'online'|'other'`) was never actually used to decide what counts toward Net Cash — it only drove the tooltip/icon selection** — every active channel fed `Net Cash`/`Cash to bank` regardless of type, so a venue with a "Card machine" channel had card takings silently inflating its cash total. Fixed with an explicit `counts_as_cash` boolean (migration 097) rather than inferring it from `type` at read time, because an operator may want a channel's cash-contribution to diverge from its display type (e.g. a "Cash app" channel that's technically `type: 'online'` but should still count as cash). Don't assume an existing categorical field already gates a calculation just because the categories would make sense for it — grep the actual formula.
- **`DayView` in `CashRecon.jsx` was already mobile-ready — no rework needed to reuse it in `MobileCashUp.jsx`** — its inputs are `flex-1 min-w-0` labels next to fixed `w-28` amount fields (never a wide multi-column grid), it already has its own sticky header with a back button (`onBack` prop), and `ExpensesSection` inside it is the same component `MobileExpenses.jsx` already reuses independently. This is the same "check whether the desktop body already reflows before rebuilding it" step the Order Sheets mobile module needed — DayView is the second confirmed case (Order Sheets was the first). Contrast with `WagesView` in the same file, which does NOT reflow: its 8-column staff grid (Staff/Type/Hours/Rate/Total/Cash paid/Notes/Remove) only survives narrow viewports via `overflow-x-auto` + `min-w-[760px]`, i.e. horizontal scrolling, not real responsiveness — so `MobileWages.jsx` is a genuine rebuild (card-per-entry, Name/Total/Cash-paid only) rather than a reuse, unlike `DayView`. Check both possibilities before assuming either.
- **When passing render-time state from a reused child component up to a host header via a callback prop, pass the state setter directly rather than wrapping it inline** — `DayView`'s `onStateChange` prop is called from a `useEffect` whose dependency array includes `onStateChange` itself; `MobileCashUp.jsx` passes its raw `setDayState` (a `useState` setter, referentially stable across renders) rather than an inline arrow function, so the effect's dependency array doesn't see a "new" callback every render and doesn't refire needlessly. Passing `state => setDayState(state)` instead would have created a new function on every render of the host, causing DayView's effect to refire every render too — not an infinite loop here (the object it computes doesn't feed back into its own inputs), but pure waste. The same applies to `useHideMobileHeader()`'s internal effect: it depends on `setHidden` pulled from a `useMemo`-stabilised context value in `MobileShell.jsx`, not a fresh object literal each render, for the same reason.
- **Wages inputs are never disabled once a report is `submitted`, so any edit there autosaves straight into a 422 and shows "Save failed" with no explanation** — the whole-tree `PUT /:venueId/cash-recon/wages/:week_start` in `cashRecon.js` rejects any save once `report.status === 'submitted'` ("unsubmit first"), but neither `CashRecon.jsx`'s desktop `WagesView` nor (until the mobile "Paid" checkbox work) `MobileWages.jsx` ever disabled their inputs to reflect that — an operator could type into "Cash paid" on an already-submitted week, watch the debounced autosave silently fail, and lose the edit with only a small "Save failed" text as a clue. Fixed on the mobile page: `RowAmountField`/add/remove are disabled and hidden respectively while `isSubmitted`, with a one-line explanation ("Amounts and staff are locked while submitted — unsubmit to change them"). **Desktop `WagesView` still has the original bug** — its `AmountInput`/`TextInput` fields for hours/rate/total/cash_amount/notes and the add/remove controls are not gated on `isSubmitted` at all; see Outstanding items. If you see "Save failed" anywhere in Cash Recon with no other explanation, check whether the report/day is already submitted before assuming it's a network or validation bug.
- **Marking a wage entry "Paid" is a different lifecycle step from editing its amount, and locking both the same way breaks the normal workflow** — submitting a wage report is meant to finalise the computed totals (hours × rate, fixed amounts), but an operator typically ticks staff off as actually paid in cash AFTER that point, sometimes days later. Locking `cash_amount` behind the same submitted-report guard as `total`/`hours`/`rate` (the original behaviour, still true of the desktop `PUT`) meant there was no way to record "paid" once submitted without unsubmitting first — which also re-exposes the locked amount fields to accidental edits. Fixed via a narrow, purpose-built escape hatch (`PATCH .../entries/:entryId/paid` in `cashRecon.js`) that updates only `cash_amount` and explicitly does not check submitted status, rather than loosening the whole-tree `PUT`'s guard. When a "mark as done" action is conceptually decoupled from the data it's attached to, prefer a small dedicated endpoint for it over relaxing a broader lock — the broader lock is usually protecting something else (here, the computed amounts) that should stay protected.
- **Card-paid expenses (`cash_expenses.paid_by_card`) are excluded from `total_expenses`, so any new expense total must filter them too** — the week-detail route sums only `!paid_by_card` rows into `total_expenses` (card sum returned separately as `total_card_expenses`), and the day view, `SpreadsheetView` and `MobileExpenses.jsx` all filter the same way. A new report, export or tile that sums `cash_expenses.amount` directly without `WHERE NOT paid_by_card` will silently overstate cash spent from the till and understate Cash to bank. VAT is unaffected either way (it is informational only).
- **Cash reconciliation figures have one implementation: `reconCalc()` in `CashRecon.jsx`** — the week grid (`SpreadsheetView`) and every Cash Dashboard balance widget call it, the grid with its override-aware cell reader and the widgets through `useReconWeek()` with saved values. Don't recompute variance, Net Cash or Cash to bank inside a widget or a new report. Add or change the formula in `reconCalc()`, or the dashboard and the Cash Recon page will quietly disagree (the same failure as the three drifting variance implementations fixed earlier).
- **A new week's wage entries come from `defaultWageEntries(config)` / `wageEntryForStaff()` in `CashRecon.jsx`, not from per-page code** — `WagesView`, `MobileWages.jsx` and the Cash Dashboard's `cash_week_staff` widget each used to carry their own copy of the "default list, else active roster" fill logic, and all three hard-coded `entry_type: 'fixed'` for the roster fallback. With `cash_staff.pay_type` that would have meant three places to update. Change how a week is filled in the helpers only. Also: any editor that saves through the whole-tree `PUT /wages/:week_start` must carry each entry's saved `cash_amount` over (by entry id), or saving a rate change silently un-ticks everyone the Wages paid widget marked Paid.
- **Staff CRUD lives in `routes/rota.js`, not `cashRecon.js`** — the old `/cash-recon/config/staff*` endpoints and Cash Recon's Staff settings tab were removed in migration 106's change. `GET /cash-recon/config` still returns `staff` for the wages pages; after a staff edit, invalidate both `['rota-staff', venueId]` and `['cash-recon-config', venueId]`.
- **Cash Recon variance adds back cash paid out of the till: day = Takings + cash expenses − (Income + SC adjustment); week = sum of days + `wages_cash_total`** — staff pay expenses and cash wages before counting, so counted cash is what is banked. There is no Net Cash / Cash to bank figure any more. The rule lives in `reconCalc()` and is mirrored in two places that must match: the day view's `const variance` and the `GET .../week/:week_start` route's per-day `variance` (WeekView cards, MobileCashUp, which adds `wages.total_cash_wages` for the week). Cash wages have no day, so a day whose till paid the wages shows short by them and only the week balances. Also: never sum two child tables in one LEFT JOIN + GROUP BY (the old `/week` query did, multiplying income by the number of takings rows); use one subquery per total.
- **Every whole-list `PUT /cash-recon/wages/:week_start` caller must send `paid_date` for each entry, or saving wipes it** — the PUT deletes and re-inserts every entry. `WagesView`/`MobileWages` send it from their state; the Cash Dashboard's week staff widget carries the saved one over by entry id, same as `cash_amount`. Rota fill-wages updates rows in place and never touches it. `GET .../week` counts wages paid on a day with no daily report as unassigned (week only), because that route has no variance for unreported days; `reconCalc()` instead adds them to that day, so an empty day with wages paid shows a surplus until its takings are entered.
- **Wages have one editor (`WeekWagesEditor`) and one write route (the whole-list PUT)** — don't bring back a per-entry paid PATCH or a page-specific wages grid. A new wages surface renders `WeekWagesEditor`; a new wage field goes into its `toRow()`/`toPayload()` (and `WageEntrySchema`), or the whole-list PUT drops it on every save from every surface.
- **A wage row's cash due is `total - bank_amount`, not `total`** — since migration 140 part of a week's wage can go by bank transfer. Anything that asks "was this paid in full", "what is left to pay" or "what carries to next week" must subtract `bank_amount` first (`cashDueOf()` / `unpaidOf()` in `WagesTable.jsx`, the carried-owed query and fill-wages' fully-paid check in `rota.js`). Cash Recon variance still uses only `cash_amount`. The bank/cash split of rota pay comes only from `splitPay()` in `shared/payMethod.js`.
- **Loyverse figures come only from `summariseReceipts()` / `sumTerms()` in `shared/loyverse.js`, and a fill re-reads Loyverse on the server** — never compute a Loyverse figure in a page or accept amounts from the browser in `/apply`; the preview and the fill would then disagree with each other or with Loyverse. A new figure kind goes into `TOTAL_KINDS` / `REF_KINDS` and `summariseReceipts()` / `termValue()` together, or `isValidTerm()` silently drops it from saved mappings. Receipts are placed by `receipt_date` in the trading day (`day_starts_at`, venue time zone), not by `created_at`.
- **The day `PUT /cash-recon/daily/:date` changes the note only when the body has a `notes` key** — the week grid saves a day without its note. Any other caller that means to clear the note must send `notes: null` explicitly. The PUT also rewrites every expense from the body, so a caller must send `vat_amount` and `paid_by_card` with each expense (the grid didn't, and reset them on every cell save).
- **Cash Recon income, takings and SC amounts can be negative** (a Loyverse day where refunds beat sales; the Zod schemas have no `min(0)`). Code that sums or displays them must not clamp to 0 or treat a minus as invalid; `fmt()` shows −£x. Expenses and wages are still 0 or more.
- **A GloriaFood order reaches us once: store it before anything else can fail, and never delete `gloriafood_orders` rows to tidy up** — GloriaFood has no history to read back, and its poll is a pop (each order is handed over once). `pollVenue()` pops and stores in one transaction and logs what it popped if storing fails; a new caller of `popOrders()` must do the same. Cleanup only clears guest details (`pollAll()`), never the row: the amounts are the only record Cash Recon has.
- **What counts as a GloriaFood sale is decided only by `summariseOrders()` in `shared/gloriafood.js`** (status `accepted`, source not `admin`). A new report, widget or AI tool must go through it (or `countsInRecon()`), or it will include cancelled orders and GloriaFood's menu-preview test orders. Figures must come from the stored pence columns, which `orderFromPayload()` works out once; don't re-derive them from `payload`.
- **A GloriaFood order on the board is not an `orders` row** — its id is a `gloriafood_orders` id, and only `POST /api/orders/gloriafood/:id/status` may change it (`board_status`). Board code must check `isGloriaFood(o)` before calling any own-order action (status, mark paid, refund, promised time), and a new board action needs the same branch.
- **The fill window and mapping editor are shared by Loyverse and GloriaFood (`reconShared.jsx`)** — a change there changes both. A source-specific figure or summary row goes into that source's own `summary` / `notices` props, never into `ReconFillModal` itself; the preview's per-field value key comes from `source.valueKey` (`loyverse` for Loyverse, `source` for GloriaFood).
- **Imported GloriaFood orders (`received_via = 'import'`) are records of past days, never live orders** — corrected: they were first kept off the board entirely; now `boardOrders()` takes them only with `includeImported`, which `GET /api/orders` passes for days before today (venue time), and they are view only (the status route 422s them, the board shows no actions or print). The settings tab's latest orders and the Orders received count still say `received_via <> 'import'`, and a new live list, count or chime must too; a list of past orders may include them but must mark them (`imported`) and must not offer actions. An import may only write rows that are still `import` (its ON CONFLICT has that WHERE); a pushed or polled copy of the same order replaces the imported one. Don't relax the `after_live` cutoff in `importExport()` to import "just a few more days": the export's ids may not match the API's, and the cutoff is what stops a day counting twice.
- **A new system that fills Cash Recon must add an entry to `LINK_SOURCES` (`services/reconLinks.js`)** — the Cash Recon settings tabs show which fields are filled from elsewhere only from that list; a filler left out (writing through `fillReconDay()` but not listed) makes its fields look typed in, and an operator edits a figure the next fill overwrites. Map by the same groups (`income`, `takings`, `sc`) and field ids as the others, and give `where` a route or a settings tab so the box can open it.
- **Cash Recon figures come only from `shared/cashRecon.js`** (since phase 3b) — this corrects "Cash reconciliation figures have one implementation: `reconCalc()` in `CashRecon.jsx`" and the variance entry after it: `reconCalc()` is now a thin caller of `reconSetup()` / `cashDay()` / `cashWeek()`, and the `/week` route, `services/cashReconSvc.js` and the report builder call the same functions. The advice stands with the new address: never work a variance, a service charge adjustment or a week's wages out anywhere else, or the page, the week route and reports disagree.
- **A host that draws its own header for a reused form must wait for the form to say it has loaded before offering its actions** — `DayView` (`CashRecon.jsx`) reports its state through `onStateChange` from the first render, while the day is still loading, and its Submit saves the form first: the phone's Cash Up page showed Submit at once, so a quick tap saved an empty day over its real figures. `DayView` now reports `ready` and its `canSubmit` includes it; a new host (Today's sheet, a dashboard widget) must show nothing that writes until `ready`, and a new reused form with its own Save must report the same. Test it with the form's load held back (a delayed route), not on a fast local API where the window can't be seen.
- **A sheet or window that hosts an editor with an explicit Save must ask before closing while it has changes** — `WeekWagesEditor` keeps its changes in a draft until Save (Standard Design Rule 5), so a host whose Done, X or backdrop just unmounts it throws a payment away without a word. The editor reports `{ dirty, saving, save }` through `onStateChange`; Today's `FormSheet` asks (Keep editing / Close without saving / Save and close, closing only when `save()` resolves true). Every way out must go through the same check (the backdrop and the X too, not only Done). Forms that save as they go (`DayView`) need no question: their pending save still runs after the sheet closes.
- **Every fill of Cash Recon goes through `fillReconDay()`, which writes `cash_fill_values`** (migration 260) — the scheduled fill keeps a field whose amount differs from the last fill's (`changedByHand()`), so a fill that writes the entries itself leaves no record and the next scheduled fill takes its figure for one typed by hand and never fills it again. Zero counts as empty: the day view saves every field, so an untouched one holds 0.
- **`PATCH .../cash-recon/settings` keeps every field left out** (COALESCE in one UPDATE after an insert of the row). An upsert that writes `body.x ?? default` resets the other settings to their defaults whenever one is changed, which the old route did to `allow_bulk_submit`.
- **At a weekly venue (migration 259) a day with figures is done until the week is submitted** — the Today feed, the phone and Pepper must not call a draft day missing there; the week is the task (`cash_week:<monday>`). And a day can only be submitted through `submitWeek()`: the day route answers 422.

- **The route's schema is also a form's** (24 Nov 2026, Pepper-first 8A3) — `ExpenseBody` (`routes/cashRecon.js`, POST and PUT of an expense) is the expense form (`api/src/forms/cash.js`), drawn by the plain renderer and used to check Pepper's values. A new field in the schema must be drawn, given or left out (`leave`, with why) in that file, or the API won't start; a renamed one renames the form's field.
- **Money from another till goes through `toPence()` (`shared/externalSales.js`) and is never worked out again** (24 Nov 2026, sales import 1) — `Math.round(v * 100)` turns 1.005 into 100; `toPence()` reads the digits. Store a receipt's totals as the till sent them (a refund keeps its own sign, `kind` says which it is); don't rebuild a check's total from its lines, and add up item lines only (an item line's money already includes its modifiers).
- **A connector strips personal data before anything is stored** (decision D3) — `stripPersonal()` on every document, and for Loyverse receipts also `order` (the ticket name), `note` and the card details but the brand. A new connector or a new document kind must do the same before `storeDocuments()`: the raw store is kept 400 days and the test looks for names, emails and phone numbers in every `ext_*` table.
- **The sales webhook never trusts its body** — `POST /webhooks/loyverse/:token` only finds the connection by the token's sha256 and asks for a sync; the sync reads the other till with our own token. Don't take receipts from the body to save a request: anyone with the address could write sales.
- **Never sync a connection outside `syncConnection()`** — it claims the connection (`sync_claimed_until`) so two PM2 processes don't read and write the same pages at once, and keeps the high-water marks and the history cursor. A request handler only marks (`markRequested()`) and queues (`requestSync()`, not awaited); the Loyverse token check and the store list are the only calls to Loyverse in a request.
- **`pos_connection_venues` is for every system now** — code that means Loyverse must join `pos_connections` with `system = 'loyverse'` (as `loadLink()` and `ownConnection()` in `routes/loyverse.js` do), or a Square venue later reads as a Loyverse one. The store column is `location_id` / `location_name`; the Loyverse routes still answer `store_id` / `store_name`.
- **The venue link and the Cash Recon mapping have separate routes** (`PUT /api/loyverse/venues/:id/link` and `/mappings`): each keeps the other's part. A new caller that saves the store must not send a mapping, and the mapping editor must not send the store.
- **A BullMQ job id may not hold a colon, and a refused add is only a warning** (24 Nov 2026, sales import 1) — `requestSync()` first used `sync:<id>` and BullMQ answered "Custom Id cannot contain :"; because the add is fired and forgotten (rule 17), Sync now looked fine and only the minute sweep ever ran the sync. Ids are `sync-<id>-<5 s bucket>` now (a fixed id would also swallow an ask made while that job is still running), and `api/test/sales-import.test.mjs` checks the job is really on the queue.
