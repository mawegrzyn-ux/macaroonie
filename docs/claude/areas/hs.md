# Health and safety

Covers: food safety logs, checklists, the H&S action log, H&S settings, H&S test data.

Key files and mistakes to avoid for this area: read it before changing code here. What shipped and when is in `docs/claude/history/hs.md`; the index of all areas is in `CLAUDE.md`.

## Key files

Under **API**, `src/...` means `api/src/...`; under **Admin portal**, `src/...` means `admin/src/...`. Other paths are from the repo root.

### API

- `src/services/openDays.js` — `resolveOpenDaysForWeek(tx, tenantId, venueId, dates)`: which dates a venue is open (exception → date override → weekly template). Shared by Cash Recon's week-detail and the Rota's `GET .../weeks/:week` (`open_dates`).
- `src/routes/hsSettings.js` — tenant-wide H&S settings (`/api/hs-settings`, migration 124): `GET ?venue_id=&date=` → `{ follow_opening_days, closed }`, `PATCH { follow_opening_days }` (owner/admin). With the setting on, `openDays.js`'s `hsClosedDates()` drives `checklists.js` `/due` (`not_required` on daily templates) and `dashboardTiles.js` `computeHsStatus()` (closed venue-days expect no daily checklists or fridge/hold/cooking checks; status `closed`).
- `src/services/hsTestDataSvc.js` — test data for H&S (migration 139): `generateHsData()` fills a past date range for one venue (fridge/freezer temps per check time, hold checks, cooking checks with random published-menu dishes, past purchase orders from the venue's order lists on each supplier's delivery days, one delivery check per received purchase order matched by `purchase_order_id`, checklists/audits completed with every task ticked) and `clearGenerated()` deletes only `is_generated` rows. Routes `POST /api/venues/:venueId/test-data/hs/generate|clear` in `routes/testData.js`; UI in `TestData.jsx`.
- `src/routes/foodSafety.js` — SFBB food-safety logging (migrations 076, 077, 090, 142). Equipment (fridge/freezer) temp checks + capture times, deliveries, hot/cold hold checks + stations + capture times, cooking/reheat checks + sessions, cooking items (`/cooking-settings`, `/cooking-items`, picker `GET /cooking/items`), plus `GET /defaults` for built-in target/min/max per equipment type.
- `src/services/cookingItems.js` — `loadCookingPicker(tx, tenantId, venueId)`: the cooking-check dish tabs from published menus, the venue's own list (`fs_cooking_items`) or both (`fs_cooking_settings.item_source`). Used by `GET /food-safety/cooking/items` and `hsTestDataSvc.js`. Mounted at `/api/food-safety`, gated by the `food_safety` module.
- `src/routes/checklists.js` — Operator-defined recurring checklists (migration 083): template CRUD + item CRUD/reorder, `GET /due` (what's due for a venue/date), `GET`/`PUT /instance` (lazy-created tick state per template per date; status `completed` exactly when every active task is ticked, no separate complete step). Mounted at `/api/checklists`, gated by the `checklists` module.
- `src/services/legacyImportSvc.js` — one-off import of the legacy CAFE_MANAGER workbook (checklist sheets incl. the "Monthly Audit" H&S sheet, fridge/freezer, hot food, deliveries) into existing checklist templates and food-safety logs. Used by `routes/legacyImport.js` (Legacy data import page) and `scripts/import-legacy-checklists.js`. Never creates templates; see Docs.jsx's Checklists section for the sheet-to-table map.
- `src/routes/hsActionLog.js` — H&S Action Log (migration 092): a general facilities/compliance to-do list per venue, migrated from the legacy spreadsheet's "ActionLog" tab. Category CRUD + reorder (`hs_action_categories` — tenant-managed reorderable list, same pattern as `fs_hold_stations`, not a fixed enum), entry CRUD, dedicated `PATCH /entries/:id/complete` that sets `completed_by`/`completed_at` server-side from the caller's JWT email. Mounted at `/api/hs-action-log`, gated by the `hs_action_log` module.
- `src/utils/checklistPeriod.js` — `periodStartFor()`/`mondayOf()`/`monthStartOf()`, factored out of `checklists.js` so `dashboardTiles.js`'s hs-status aggregation can never drift from what `checklists.js` itself considers a template's current period.

### Admin portal

- `src/pages/FoodSafety.jsx` — SFBB food-safety logs (`/food-safety` route), recording only. Tabs: Today (fridge/freezer grid + counts), Deliveries (entry form + current-week list, click any item to load it back into the form for editing), Holds (hot/cold hold grid), Cooking (till-style category tabs + dish buttons; `bg-muted/60` fill so tiles read as distinct from the page background). "Corrective actions" button cycles every out-of-range reading for the day still missing a note. All setup lives in H&S settings (`components/hs/HsSetup.jsx`).
- `src/pages/Checklists.jsx` — Operator-defined recurring checklists (`/checklists` route). Two tabs: Today (tick off what's due) and Checklists (template builder — name, department, frequency daily/weekly/monthly, ordered tasks).
- `src/components/foodSafety/shared.jsx` — Shared panels reused by both `FoodSafety.jsx` tabs and `HSDashboard.jsx` widgets: `TempChecksTable`, `DeliveryChecksPanel`/`DeliveryChecksBoard`, `HoldChecksTable`, `CookingChecksPanel`, `EndOfDayReview`. One implementation of each check type, never two. Since 23 Nov 2026 (Pepper-first step 3): `useUnresolvedReadings()` (the day's readings out of range with no corrective action, the one list `EndOfDayReview` and `CorrectiveActionsPanel` (the form sheet's corrective form) work through); the grids, `DeliveryModal` and `CorrectiveActionsPanel` take Pepper's values in a form sheet (`useFormFill()`, `components/forms/fill.jsx`; a grid cell's `proposed` reading saves only on OK or a change); `DeliveryChecksPanel` sends its own day as `delivery_date`. `TempKeypadModal` is the shared IS_TOUCH-gated custom keypad used by `TempCell`, `HoldCell`, and `CookingEntryModal`'s core-temp field in place of the native keyboard.
- `src/pages/HSActionLog.jsx` — Standalone H&S Action Log page (`/hs-action-log` route) — venue picker + `HSActionLogPanel`.
- `src/components/hsActionLog/shared.jsx` — `HSActionLogPanel`, reused by `HSActionLog.jsx`, the H&S Dashboard's `action_log` widget and the form sheet's hs_action form (`startNew`, `day`; `EntryModal` takes Pepper's values, category by name, since 23 Nov 2026). Open/Completed/All status tabs, category filter, add/edit modal (task, category, priority, assigned-to, due date, notes, photo attachment via the Media library picker), category-management modal (drag-reorder, same pattern as Food Safety's hold-stations manager).
- `src/components/hs/HsSetup.jsx` — all food safety setup as H&S settings sections (`SETUP_SECTIONS`, `HsSetupSection`): Fridges & freezers and Hold stations (drag-sortable), Fridge check times (`/capture-times`) and Hold check times (`/hold-capture-times`, kept separate), Cooking sessions (`CookingSessionsSettings` from `foodSafety/shared.jsx`, drag-sortable via `PATCH /food-safety/cooking-sessions/reorder`), Cooking items (`CookingItemsSettings`: item source menus/own/both with explicit Save, own-item list drag-sortable). Inline confirm on remove; invalidates every `fs-*` query after a change.
- `src/components/checklists/shared.jsx` — `ChecklistRunPanel`, the tick-list UI shared by `Checklists.jsx` and the H&S Dashboard's checklist widget (Tick all button). Accepts `hideHeader` + `onStateChange` (`{ isCompleted, isPending, hasItems, tickAll, untickAll }`) so the host renders `ChecklistHeaderAction` (Tick all, then All done with a confirmed Untick all) in its own header.
- `src/components/hs/HsSettings.jsx` — `HsSettingsButton({ venueId, section, label })`: the H&S settings window, General (Follow restaurant opening days switch, owner/admin, explicit Save) plus the food safety setup sections from `HsSetup.jsx` (food_safety manage), with its own venue picker; and `ClosedDayNotice` (banner when `/hs-settings` says the venue is closed that date). Used by Food safety, Checklists, the H&S Dashboard (`DashboardPage` config `HeaderExtra` / `Notice`, both optional) and `MobileHSDashboard.jsx`.

## Mistakes to avoid

> Append-only: never delete an entry, only correct one that turns out to be wrong. New entries go at the end.

- **`provisionTenantOrg` skips steps 6 + 7 of the manual checklist** — when auto-provision is on, the API creates the org and enables Username-Password + Google connections with `assign_membership_on_login: true` in one call. Steps 1–5 + 8 (M2M scopes, env vars, SPA URIs, app-level connection toggles, role-claim Login Action) are still one-time tenant-wide setup that the platform admin does before the first auto-provisioned tenant. Auto-provision is enabled by default in the Platform → New Tenant card; uncheck if you want to manually paste an existing `org_…`.
- **"Who completed this" fields are plain `text` storing an email, not a `uuid` FK to `users(id)`** — `checklist_instances.completed_by` set the precedent (`req.user?.email`), and `hs_action_log.completed_by`/`created_by` follow it. This was nearly gotten wrong building the Action Log (drafted as a `users(id)` FK before checking the existing convention) — a FK would also be wrong in practice since not every JWT-bearing caller (e.g. a platform admin with no local `users` row) can be resolved to a local user id, while `req.user.email` always exists. Check `checklist_instances` before inventing a new "who did this" column shape.
- **`hideHeader` mode on a shared panel can silently drop functionality the full-page mode already has** — `ChecklistRunPanel`'s `hideHeader` mode (used by the H&S Dashboard's checklist widget) re-derives its own compact header affordance from `onStateChange`, which only exposed `markComplete`, not `reopen` — even though the full-page mode's own footer already had a complete, working double-confirm reopen flow. When adding a `hideHeader`/compact-mode branch to a shared component, diff its exposed capability against the full mode's — a host-rendered compact header is easy to under-build relative to what the component itself can already do.
- **An enum of allowed values can live in three places — DB `CHECK` constraint, API Zod schema, and the UI's own list — and adding a value to only two of them looks finished but isn't** — migration 092 added `action_log` to `hs_dashboard_widgets`' `CHECK` constraint and `HSDashboard.jsx`'s `WIDGET_TYPES` offered it in the Add widget picker, but `hsDashboards.js`'s `WidgetBody` Zod `widget_type` enum was never updated, so every attempt to add an Action log widget was rejected with a 400 before it reached the database. When adding a new value to any enum-like column, grep the value's siblings (e.g. `'cooking_checks'`) across `migrations/`, `api/src/`, and `admin/src/` and update every hit.
- **Delivery checks feed the Overview H&S status tiles' "unresolved" count only, never expected/completed** — deliveries arrive ad hoc with no schedule, so there's no expected number to measure against (unlike fridge/hold/cooking checks, which have configured capture times/sessions). `computeHsStatus()` in `dashboardTiles.js` counts a delivery as unresolved when it failed any check (`NOT (packaging_ok AND damage_ok AND quality_ok AND temp_ok AND accepted)`) and has no `corrective_action`, and adds a `delivery` category (with a `summary` string, "3 logged · 1 issue") only on days with at least one delivery. Don't add deliveries to expected/completed — any count you'd put there would be invented, and it would dilute the real completion ratio of the scheduled checks.
- **iPad home-screen (standalone) web apps have no Fullscreen API, and iPad Safari only has the webkit-prefixed one** — `el.requestFullscreen?.()` silently did nothing on an iPad, so the H&S Dashboard's Full screen button looked broken. Try `requestFullscreen ?? webkitRequestFullscreen`, listen to both `fullscreenchange` and `webkitfullscreenchange`, and fall back to a CSS pseudo full screen (`fixed inset-0 z-50`) when the API is absent or its promise rejects.
- **A user-configured grid layout must shrink to fit, not reflow to fewer columns** — the H&S Dashboard's `column_count` is a layout the operator deliberately built (e.g. two half-width checklist widgets side by side). An attempt to stop the 4-column grid overflowing on a portrait iPad by computing fewer "visible" columns from the container width made those widgets stack, which the user reported as broken. The fix for overflow is `minmax(0, 1fr)` tracks, which always fit, plus letting wide content scroll inside its own card. Automatic responsive reflow is right for a fixed, app-defined layout (the Overview grid's breakpoint classes). It is wrong for a layout the operator arranged by hand.
- **"Is the venue open on this date" has one implementation: `resolveOpenDaysForWeek()` in `api/src/services/openDays.js`** — Cash Recon and the Rota both call it. Don't write another closed-day check from `venue_schedule_templates` alone; it would ignore date overrides and exceptions and the two pages would disagree. It returns every template-open day, so the Rota treats a venue with no templates at all as `open_dates: null` (hide nothing) rather than "closed every day".
- **A `date` column sent straight to the frontend arrives as `"2026-09-23T00:00:00.000Z"`, and code that appends `'T12:00:00'` to it crashes the whole page** — postgres.js turns `date` into a JS `Date`, which serialises as a full timestamp. The Food safety Deliveries week list did `format(new Date(d.delivery_date + 'T12:00:00'), ...)`, got an Invalid Date, and date-fns threw, blanking the page as soon as a week with a delivery was shown (a week with none never reached that line). Fixed by returning `delivery_date::text` from `GET/POST/PATCH /food-safety/deliveries` and reading it through `deliveryDay()` in `foodSafety/shared.jsx`. Any route returning a `date` column the UI treats as `YYYY-MM-DD` needs the `::text` cast.
- **"Is this H&S check needed today" has one answer: `hsClosedDates()` in `services/openDays.js`** — `/checklists/due` and `computeHsStatus()` both call it, and the admin only shows what `/api/hs-settings` returns. A new H&S report or tile that counts expected checks must go through it too, or it will flag closed days red while the Overview shows them Closed. Keep an unscheduled venue (no `venue_schedule_templates` rows) as open every day, as `openDatesOrNull()` does; `resolveOpenDaysForWeek()` alone would call it closed every day and silently switch off every check.
- **Food safety setup has one home: H&S settings (`components/hs/HsSetup.jsx`)** — the check panels in `foodSafety/shared.jsx` (used by Food safety, the H&S Dashboard and its mobile version) only record readings. Don't add a gear, "Manage" button or add/edit list back into a panel or the Food safety tabs; add a section to `SETUP_SECTIONS` instead. Fridge check times (`fs_capture_times`) and hold check times (`fs_hold_capture_times`) are separate tables and separate sections on purpose. Setup changes must invalidate the `fs-*` query keys (`FS_KEYS` in `HsSetup.jsx`) so a check page open underneath refreshes.
- **Generated test rows are marked `is_generated`; anything that bulk-writes demo data must set it and clear by it** — the H&S generator never overwrites a slot that already has a reading, and completing a checklist someone started leaves that row `is_generated = false`, so Clear can't undo it. Don't clear demo data by date range alone or by a notes marker: that would delete real readings.
- **A checklist's completion is derived from its ticks in `PUT /checklists/instance`, never set on its own** — there is no complete or reopen request any more. Anything that writes `checklist_instances` (the H&S test data generator, the legacy import) must set `status = 'completed'` only when every active task is ticked, or the dashboards and Checklists page disagree with what a later save computes. A template gaining a new task does not reopen existing completed instances until their next save.
- **The cooking-check dish list has one source: `loadCookingPicker()` in `services/cookingItems.js`** — menus, the venue's own `fs_cooking_items`, or both, per `fs_cooking_settings.item_source` (no row = menus). Don't query `menu_items` for cooking checks anywhere else (the generator used to), or a venue set to own items gets menu dishes. A reading points at `menu_item_id` or `cooking_item_id`, never both; `dish_name` is the durable record.
- **The food safety and action log POST routes default their date to the server's UTC date** (`new Date().toISOString().slice(0, 10)`) — around midnight that is the wrong day for a UK venue. Any caller that isn't the admin page (the AI tools, imports) must send `log_date` / `check_date` / `delivery_date` / `logged_date` itself, in the venue's time zone (`localParts()` in `ai/tools/util.js`).
- **`PUT /checklists/instance` replaces every tick, every task note and the instance notes** — a caller that changes a few ticks must send the whole active task list with the current notes (as `tick_checklist` in `ai/tools/hs.js` does), or it unticks everything it left out and wipes the notes.
- **The everyday work on a module that offers Use is gated at `use`, its setup at `manage`** — a new route that records a check, ticks something or adds an action on checklists, food_safety or hs_action_log takes `requirePermission(module, 'use')` (or `workLevel(module)`), and the admin control that does it shows on `canUse`; deleting, setting up and anything that changes what others are asked to do stays `manage` / `canManage`. Offering Use on another module means a `use` text in its `MODULES` entry (that's what `levelsOf()` reads) and deciding, route by route, which writes are everyday work. A new Pepper change tool that is everyday work carries `needs: 'use'` and checks `use`, or the staff connector hides it from Use.
- **A report figure that copies a page's rule must copy it exactly, and be held to the page by a test that reads the page's own route over the same rows** (`api/test/reports-areas.test.mjs`) — the Overview's H&S tiles count any corrective action written as put right (`!l.corrective_action` in `computeHsStatus()`), so a catalogue rule that trimmed the words first (`btrim()`) disagreed with the tile on an action of a space. A rule tidier than the page's is a wrong rule: change both together (the page's in its shared function) or neither. A rule too long to copy safely (the H&S day's status colours, `deadlinePassed()`) waits for a stored result (plan 5.4) instead of being written a second time.
- **`computeHsStatus()` counts a reading as done only for a fridge, hold station and check time still set up** — a reading of one taken out since made past days look done, or more than done, on the Overview tiles, Pepper's hs_status and the day briefing until phase 3b. A new kind of check it counts must be looked up by venue and day (`byVenueDay()`) and matched against what is set up now, and anything that changes what a day expects changes the Overview, Pepper and reports together (one function).
- **The readings' and checklist routes are the ones a till PIN may use on a shared device: keep `config.sharedDevice: CHECK` on them, and record the person with `whoDid()`** (24 Nov 2026, migration 280) — `POST` / `PATCH` of `/api/food-safety/temp-logs`, `/holds`, `/cooking`, `/deliveries` and `PUT /api/checklists/instance` carry `CHECK`; set-up routes (equipment, capture times, templates) and deletes don't. `recorded_by`, `completed_by` and the action log's `created_by` come from `whoDid(req, body.recorded_by)`, which on a shared device is the person whatever the body says.
