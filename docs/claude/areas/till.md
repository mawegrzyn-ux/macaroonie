# Till (POS)

Covers: checks, events and the sequencer, PINs, till layouts, charges, discounts, order flows, the order prompt, order types and revenue streams, card machines, device addresses, the installer app, Store tech, test till sales.

Key files and mistakes to avoid for this area: read it before changing code here. What shipped and when is in `docs/claude/history/till.md`; the index of all areas is in `CLAUDE.md`.

## Key files

Under **API**, `src/...` means `api/src/...`; under **Admin portal**, `src/...` means `admin/src/...`. Other paths are from the repo root.

## Mistakes to avoid

> Append-only: never delete an entry, only correct one that turns out to be wrong. New entries go at the end.

- **A check changes only through an event and `applyEvent()`; never write `pos_checks`, `pos_check_lines` or `pos_payments` directly** — they are projections of `pos_events`, rewritten by the sequencer after each accepted event. A new check rule goes in `shared/pos/checks.js` only: the till and the server both run it, and a rule that exists on one side only makes every offline change of that kind come back refused (or lets the till show something the server will never accept).
- **A till's PIN check uses the venue's `pos_settings.pin_salt`; changing it, or hashing a PIN any other way than `hashPin()`, locks every person at the venue out of the till** — PINs are unique per venue because the PIN alone finds the person. Anything that changes what a till needs offline (menus, staff, roles, tables, printers, settings) must call `configChanged(venueId)` in `posSetup.js` (or broadcast `pos.config`; menus and promotions do it through the `notifyTillsOnWrite` onResponse hook from `services/posNotify.js`), or open tills keep the old config for up to 10 minutes (their refresh interval). Staff and table edits outside Till setup don't notify yet.
- **A till only knows what its last config download held (PINs, staff, menus, prices)** — it gets a new one on a `pos.config` push, on reopening, or every 10 minutes. Anything that changes what the till checks offline must call `configChanged(venueId)` (or broadcast `pos.config`), and a check that fails because the till may be behind (an unknown PIN) should fetch the config and try again, as `staffForPin()` does.
- **Sold out is written only by `setSoldOut()` + `announceSoldOut()` (`services/soldOut.js`)** — a route that writes `ordering_item_availability` itself leaves tills and screens showing the dish (no `pos.config` / `screens.sold_out` push) until their next refresh.
- **`pos.seq` carries `kinds`; a till pulls only on `checks`** — anything new that broadcasts `pos.seq` for a venue must say which kinds changed, or every till pulls on every kitchen tap.
- **Changing a check's order type or revenue stream must carry the re-rated lines** — `check.order_type_set` / `check.stream_set` take a `lines` map `{ lineId: { vat_rate, tax_rate_id } }` built by `rerateLines()` on the till, and `applyEvent()` writes it. An event without it leaves every line at the old type's tax. The till computes the rates (it is the one that showed the price), so the server never re-rates on its own.
- **Don't key list rows by their label** — two rows can share a name (a revenue stream kept for its old sales next to a new one of the same name), and React then warns and can mix the rows up. Key by id or position (`Rows` in `PosReports.jsx`).
- **A device runs the copy of the till app its service worker kept until a reload, so a new device kind or a new screen must never assume the copy is current** — the till app decides what a device is from the kind saved at pairing; a copy that doesn't know a kind ran it as a till (a kiosk on the PIN screen). Routing goes through `openOtherApp()` in `pos/src/lib/store.js`: a new kind gets a branch there and in `App.jsx`, and anything unknown waits for an update rather than falling through to the till. New copies arrive through `pos/src/lib/appUpdate.js`; a new full-screen app or mode must register its own quiet moment with `whenSafeToReload()` (or it inherits the till's rule), and pages that must never reload by themselves (previews, the bench) must not call `startAppUpdates()` (`pos/src/main.jsx`). Don't turn the plugin's `injectRegister` back on: two registrations would race, and the plugin's own autoUpdate reload doesn't wait for a quiet moment.
- **Tills, kitchen screens and kiosks run one build on three addresses, and the address decides the app** — `HOST_APP` in `pos/src/lib/appHost.js` (pos. till, kitchen. / kds. kitchen screen, kiosk. kiosk; any other address takes any kind). Browser storage is per address, so a device paired on one address knows nothing on another: never move a device by copying its secret into a link; use `POST /pos-api/move` (a one-time code in `#pair=`, removed from the address at once). A new device kind needs its own subdomain in `platformHost.js` (`DEVICE_KIND_OF_HOST`, `RESERVED_SUBDOMAINS` in `siteRenderer.js`), `APP_HOSTS` / `APP_NAMES` in `posSite.js`, `HOST_APP` / `SUBDOMAIN` in `appHost.js` and `DEVICE_APPS` in `posApi.js`, or its codes are refused everywhere but a test address. Links the admin makes for a device app (previews, the kitchen test bench, pairing instructions) must use `deviceOrigin(kind)` / `deviceUrl(setup, kind)`, never the till's address.
- **A code a device shows (link code) must never be live in `pos_pairings` and `screen_pairings` at once** — the installer finds a code's device by its hash alone (`findLinkCode()`), so both pairing routes check `linkCodeTaken()` before inserting. - **A record id typed into an address must be checked for its shape before it reaches the database or a schema** — `/pos/reports?check=abc` showed "Validation error" until `GET /api/pos/checks/:id` answered 404 Check not found for anything that isn't a ULID (check ids are ULIDs, not uuids, so a uuid parser is the wrong check too). Code that looks for `kind === 'till'` finds no tills and quietly does something else (the till sales generator first made stand-in tills for every venue that way). - **A ULID's time must be a whole number of milliseconds** — `ulid(at)` in `shared/pos/ids.js` encodes `at % 32` as a letter, so a time with a fraction (worked out from a random minute, `dayStart + rng() * span`) puts `undefined` into the id, and the check rules refuse every event carrying it. Floor any computed time before making an id from it (`clamp()` in `tillSalesGen.js`).
- **Rows made for testing must stay out of real trading: a new table read or a new path over `pos_days` / `pos_checks` must say `NOT is_generated` (migration 245)** — the sequencer's `loadChecks()`, the device routes and Cash Recon fill all do, so a test day is never on a till, a venue hub, a Z or Cash Recon. - **`dayFigures()`' lists follow the order of the checks it is given** — a test that compares a stored day's figures with `dayFigures()` of the same checks read back in another order fails on order alone; compare lists as sets (`sorted()` in `till-test-data.test.mjs`), or read the checks back in the order they were made.
- **Something a generator makes busy (a table, a till) must be freed by the event that ends its use, never after a guessed length** — the till sales generator marked a table busy for its party's stay plus ten minutes, but a bill split three ways can take longer, so a second party sat down a minute or two before the first had paid (found only when a test checked that each table's next check opens after the one before it closed). It now frees the table `TABLE_TURN_MS` after the bill is paid or the order cancelled, and holds every event inside the trading day. A new simulated resource must do the same, and its test must look for the overlap itself: counts and totals don't show it.
- **A check that something rare happens in made-up data needs a sample where missing it can't happen by chance** — the till sales generator's seed includes the venue's id, which is random in every test run, so on a 700-order day a refund (0.4% of orders) was missing about one run in seven. Work the chance of none out first ((1 - p) to the power of the number of tries) and size the day for it: the rare-event checks run on a 3,000-order day. Something rarer still (an optional charge taken off: 5% of the few checks that have one) isn't checked, and the fault run lists it as missed for that reason.
- **A void made by Cancel order carries no mark on its line: tell such voids apart by the check (`c.cancelled`)** — the Cancel order batch flags its `line.voided` / `line.deleted` events with `cancel: true`, but `applyEvent()` only adds the line's value to `c.cancelling`: the line's `voided` record looks the same as a void made by hand. A new place that offers guests, seat numbers or courses (a layout zone, a window, a swipe action) must ask these, and must also respect `counterTill()`: a counter till has no floor, tables, Fire or guests at all.
- **A course that waits by default (`hold_by_default`) waits only behind an earlier course on the check (`defaultHeld()`)** — a check with only mains sends the mains at once.
