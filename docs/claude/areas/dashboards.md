# Dashboards and the Overview

Covers: the dashboards engine and its widgets, the Overview tiles.

Key files and mistakes to avoid for this area: read it before changing code here. What shipped and when is in `docs/claude/history/dashboards.md`; the index of all areas is in `CLAUDE.md`.

## Key files

Under **API**, `src/...` means `api/src/...`; under **Admin portal**, `src/...` means `admin/src/...`. Other paths are from the repo root.

### API

- `src/routes/hsDashboards.js` — Customisable dashboards (migrations 086–088, 101, 152): dashboard CRUD + reorder, widget CRUD + reorder, per-widget `col_span`/`height_px` resize. Registered four times in `app.js` — `/api/hs-dashboards` (`kind: 'hs'`, `hs_dashboard`), `/api/cash-dashboards` (`'cash'`, `cash_dashboard`), `/api/rota-dashboards` (`'rota'`, `rota_dashboard`) and `/api/custom-dashboards` (`'custom'`, `custom_dashboard` core module, the blank Dashboards page); each mount filters every query by `hs_dashboards.kind`. Since migration 152 every mount accepts every widget type (`WIDGET_TYPES`, keys of `WIDGET_MODULE`, which maps each type to the module whose data it shows); adding a widget needs view on that module (`permissionLevel()`). A widget is a thin pointer (`widget_type` + optional `checklist_template_id`) at the food-safety/checklist data — no separate per-widget data model. Mounted at `/api/hs-dashboards`, gated by the `hs_dashboard` module.
- `src/routes/dashboardTiles.js` — Overview page tile system (migration 093). `TILE_CATALOG` (static, same "only real known tiles" idea as nav.js's ROUTE_CATALOG) + CRUD + `PATCH /reorder` on `dashboard_tiles`, gated by `requirePermission('dashboard', …)`. `GET /hs-status?from=&to=&today=` returns the combined Checklists + Food safety status per venue per day for the `hs_today_status`/`hs_week_status` tiles, computed by `computeHsStatus()` in `src/services/hsStatus.js` (shared with the staff AI's `hs_status` tool) — see Docs.jsx's Overview Tiles section for the full expected/completed/unresolved derivation and the status-colour rules.
- `src/config/defaultDashboardTiles.js` — `DEFAULT_DASHBOARD_TILES` + `seedDefaultDashboardTiles(tx, tenantId)`, used for brand-new tenants (`POST /api/platform/tenants`), same "one seed function, called from two places" pattern as `defaultNav.js`.

### Admin portal

- `src/pages/Dashboard.jsx` — "Overview" (home page, `/` route). Tile-based layout (migration 093) — quick_access / stats_today / upcoming_bookings / venues_status / hs_today_status / hs_week_status, rendered via a shared `TileCard` shell mirroring `HSDashboard.jsx`'s `WidgetCard` (header with icon/title, edit-mode reorder/resize/remove controls, scrollable body). Non-managers see `me.dashboard_tiles` (server-filtered by role); an owner/admin's "Customise layout" mode fetches the full unfiltered list from `GET /api/dashboard-tiles` and can additionally set per-tile `hidden_role_ids` via a small "Visible to" modal. The `Shortcuts` component (per-user quick-access picker, `maca_dashboard_shortcuts` localStorage) is unchanged — it's nested inside the `quick_access` tile, a separate customisation axis from tile layout.
- `src/pages/HSDashboard.jsx` — Customisable H&S dashboards (`/hs-dashboard` route). Any number of named dashboards (tabs), each holding any number of widgets (checklist / temp_checks / delivery_checks / hold_checks / cooking_checks) behind one date navigator. "Edit layout" adds/removes/reorders/resizes (width in grid columns, height in px) widgets. Checklist widget's "Complete" action lives in the widget's own card header. Container is full width (`w-full`; it was `w-[90%] mx-auto` until it left a visible empty strip on tablets). The grid is always exactly `column_count` columns (`repeat(column_count, minmax(0, 1fr))`), shrinking to fit a narrower screen so the operator's layout is kept; wide content scrolls inside its own card. Full screen uses the Fullscreen API (webkit-prefixed on iPad) and falls back to a `fixed inset-0 z-50` pseudo full screen where the API is missing (iPad home-screen apps). Date navigator: fixed-width label (doesn't reflow between "Today" and a full date string), 44px outlined prev/next arrows, native `input[type=date]` overlay for the calendar picker. The dashboard-name tabs render in the same row as the date navigator (`flex-wrap sm:flex-nowrap`; from `sm` up the tabs strip is `flex-1 min-w-0 overflow-x-auto`, so it scrolls sideways rather than wrapping below — the earlier `flex-wrap` version wrapped onto a second line on an iPad) rather than on a separate row below — the tabs' JSX lives once, in that combined row; the `dashboards.length === 0` empty-state branch doesn't render it at all (guarded by `dashboards.length > 0`), and the `editing`-mode dashboard-management strip (rename/reorder/columns) still renders on its own row below, since it's edit-mode-only chrome not part of the everyday navigation row.
- `src/pages/CashDashboard.jsx` — Cash Recon Dashboard (`/cash-dashboard`, `cash_dashboard` module). Just a config (`CASH_DASHBOARD_CONFIG`) for `DashboardPage`, the generic dashboard engine exported from `HSDashboard.jsx` (tabs, edit layout, widget CRUD, row-spanning grid, full screen). `HSDashboard.jsx`'s own default export is the same engine with `HS_DASHBOARD_CONFIG`.
- `src/components/dashboards/widgetTypes.jsx` — the one widget catalog for every dashboard (migration 152): `WIDGET_TYPES` (H&S + Menus types here, `CASH_WIDGET_TYPES` from `cashRecon/widgets.jsx`, `ROTA_WIDGET_TYPES` from `staff/rotaWidgets.jsx`), each with `group` (`WIDGET_GROUPS`), `module` and `nav`; `renderWidget()`, `canUseWidget(meta, me)`, `hasHsDayWidget()`, `NoAccess`. `src/components/dashboards/nav.jsx` — `useDashboardNav()` (one selected day; `ctx = { date, weekStart, selectedDay, setSelectedDay }`), `navModeFor()` (`day` / `week` / `both`), `DashboardNav`. `src/pages/Dashboards.jsx` — blank dashboards (`/dashboards`, `CUSTOM_DASHBOARD_CONFIG`). `src/pages/mobile/MobileDashboard.jsx` — `MobileDashboardPage` (any kind, read-only layout); `MobileHSDashboard.jsx` wraps it for the H&S kind (the blank dashboards aren't on the phone since 30 Oct 2026: `/mobile/dashboards` falls to the mobile routes' catch-all, the hub).
- `src/lib/dashboardGrid.js` — shared row-spanning grid for the H&S Dashboard, Cash Dashboard and Overview tiles: fixed `ROW_UNIT` rows, `grid-auto-flow: row dense`, `rowSpanFor(height_px)`/`heightForRows(rows)`.
- `src/pages/mobile/MobileHSDashboard.jsx` — phone-portrait, single-column H&S Dashboard for logging checks: same dashboards (as `DashboardTabs`, a framed strip with scroll arrows), widget types, `/api/hs-dashboards/*` reads and shared body components. No layout editing on the phone (done on the desktop page). Ignores `col_span`/`height_px` and renders full-width/natural-height so the page is the only scroll region. Imports `WIDGET_TYPE_BY_KEY` from `HSDashboard.jsx`.
- Use level and dashboards per role (migration 229; Docs.jsx → RBAC → Use, Dashboards → Dashboards per role): Use is gated with `requirePermission(module, 'use')` on `PUT /checklists/instance`, the food safety log POST / PATCH routes and the action log entry POST / PATCH / complete; `can_act` in `services/opsToday.js` uses `workLevel()`; Pepper's H&S change tools check use and carry `needs: 'use'`, read by `toolAllowed()` in `ai/tools/index.js`; `PERMISSION_RANK` replaces the copies in `auth.js` (`permissionMessage()`: "Your role can use X but not change how it is set up."), `ai/context.js` and `routes/installer.js`. Admin: `canUse` in the check panels (`components/checklists/shared.jsx`, `foodSafety/shared.jsx`, `hsActionLog/shared.jsx`; delete, setup and categories stay `canManage`), the Checklists page's View only bar, `canUseWidget()` (`!== 'none'`), the rota widgets' pay / tips checks, the Access page's level buttons from each module's `levels` with the Use line (`access-use-hint`, `access-levels`). Dashboards: `hs_dashboards.hidden_role_ids`; `services/roles.js` (`effectiveRoleId(req)`, `ownRoleIds(tx, tenantId, ids)`, also used by the nav item and Overview tile routes); `GET /dashboards` (`dashboardViewer()`, `?all=1` for Manage), the widgets GET 404 for a hidden dashboard below Manage; admin `components/dashboards/RoleVisibilityModal.jsx` (`RoleVisibilityModal`, `visibilityText()`, shared with the Overview tiles) and in `HSDashboard.jsx` the `dash-roles` Seen by button, `dash-tab` markers, the edit-mode list query. Tests: `api/test/access-use-dashboards.test.mjs`.

## Mistakes to avoid

> Append-only: never delete an entry, only correct one that turns out to be wrong. New entries go at the end.

- **postgres.js deserialises `date` columns to JS `Date` objects, not strings — this breaks map-key lookups built from date fields, silently** — `dashboardTiles.js`'s hs-status aggregation builds a lookup key `` `${template_id}|${period_start}` `` from a `checklist_instances` query; without `period_start::text` in the SELECT, the key becomes `` `${template_id}|Mon Sep 21 2026 00:00:00 GMT+0000 (Coordinated Universal Time)` `` instead of `` `${template_id}|2026-09-21` ``, so the lookup against the JS-string period computed by `periodStartFor()` never matches and a genuinely-completed weekly/monthly checklist always shows as incomplete. No error, no crash — just wrong data. This is the same family of gotcha as the existing `slot_time` entry above (composite-type `timestamptz` → JS `Date`), but for plain `date` columns feeding a string-keyed `Map`. Always cast date/timestamp columns to `::text` in the SQL when the JS value is going to be used as a map key or compared to a plain date string — don't rely on the driver's default deserialisation matching what you expect. Caught by writing a direct test against a disposable Postgres before shipping (see the food-safety migration-testing pattern below) — worth doing for any new cross-table date aggregation.
- **A tile/card grid built with a fixed `style={{ gridTemplateColumns: 'repeat(N, minmax(Xpx, 1fr))' }}` doesn't degrade at phone width — it either forces `N * X`px minimum (horizontal scroll) or squeezes below the `minmax` floor** — `Dashboard.jsx`'s Overview tile grid had this shape (4 columns, 240px minimum each = 960px+ before anything actually reflows). Fixed by switching to Tailwind breakpoint classes (`grid-cols-1 sm:grid-cols-2 lg:grid-cols-4`) with each tile's configured "span" (1-4 quarters) mapped through a `SPAN_CLASSES` lookup so a 4-wide tile is `col-span-1` on a 1-column phone grid, `col-span-2` (full width) on a 2-column tablet grid, and `col-span-4` only once the grid actually has 4 columns at `lg`. Any admin page with a resizable/spannable tile or card grid should use this same breakpoint-keyed span-class pattern rather than a fixed pixel-based `grid-template-columns`.
- **Dashboard grids pack densely, so on-screen order can differ from `sort_order`** — `lib/dashboardGrid.js` uses `grid-auto-flow: row dense` so short widgets fill the space beside a tall one (row spanning). The move up/down controls still change `sort_order`, but a later, shorter widget may render before an earlier, taller one if it fits a gap. This is intended. Don't "fix" it by removing `dense` unless you're also dropping row spanning.
- **Dashboard widget `settings` jsonb must be written with `tx.json()`, including inside the `tx(values, ...fields)` PATCH helper** — the widget PATCH maps `settings` through `tx.json()` before building the update object (other fields go in raw). Passing the plain object works by accident in some postgres.js paths and stores a JSON *string* in others, after which `widget.settings?.compact` is always `undefined` and the toggle looks like it never saves. Verified against a throwaway Postgres that `jsonb_typeof(settings)` comes back `object`.
- **A prop gated on the same condition twice in opposite directions renders nothing, silently** — `Dashboard.jsx` passed `headerExtra={editing && <VisibleToButton/>}` while `TileCard` rendered `{!editing && headerExtra}`, so the per-tile role-visibility button could never appear and nobody noticed because nothing errored. When a child conditionally renders a prop, let the caller own the condition (render `{headerExtra}` as given) rather than gating it on both sides.
- **`DashboardPage` configs carry a `useNav` hook, called unconditionally by the engine** — each config (`HS_DASHBOARD_CONFIG`, `CASH_DASHBOARD_CONFIG`) is a module-level constant, so the hook call order is stable. Never build a config inline inside a component or swap configs on the same mounted `DashboardPage`, since switching `useNav` between renders breaks the rules of hooks. Mount a different page instead.
- **Every dashboard widget type is listed in three places: the `hs_dashboard_widgets.widget_type` CHECK, `WIDGET_MODULE` in `routes/hsDashboards.js`, and `WIDGET_TYPES` in `components/dashboards/widgetTypes.jsx` (with its `module` and `nav`)** — this corrects the earlier "Adding a widget type means three places" note (`WIDGET_TYPES_BY_KIND`, `CASH_WIDGET_TYPES` + `renderCashWidget`), which predates migration 152. A type left out of `WIDGET_MODULE` is rejected by every mount; one whose admin `module` differs from the API's is offered in Add widget and then refused with a 403. Since any dashboard can hold any widget, a widget body must cope with every navigator mode: read only `ctx.date` (H&S) or `ctx.weekStart` + `ctx.selectedDay` (cash, rota) and never assume which page it is on.
- **A widget type's `nav` can be 'day', 'week', 'both' or null, and `navModeFor()` must handle each** — it only knew 'day' and 'week', so the import widget's 'both' was silently ignored and the date bar showed weeks only (no way to pick a day except the widget's own list). A new nav value needs a case in `navModeFor()` (components/dashboards/nav.jsx); cash types default to 'week' through `t.nav ?? 'week'` in `widgetTypes.jsx`, so set `nav` on the `CASH_WIDGET_TYPES` entry, never by editing the mapping.
- **`DashboardPage` configs no longer carry `useNav`, `widgetTypes` or `renderWidget`** — this corrects the earlier "configs carry a `useNav` hook" entry. The engine calls `useDashboardNav()` itself and takes widgets from the shared catalog; a config only picks `apiBase`, `keyPrefix`, `primaryGroup`, `defaultNav` and texts. Don't add a per-page widget list back: it would make that page's dashboards reject or hide widgets the other pages can add, which is exactly what migration 152 removed.
- **Showing a dashboard widget is gated twice: the API refuses to add a widget without view on its module, and the admin replaces the body with `NoAccess` for a viewer without it** — the second check matters because someone else can add a cash widget to a dashboard an operator without Cash reconciliation can open. Never rely on the widget's own data routes failing quietly (a 403 inside a widget looks like a broken page). A new widget whose body needs a narrower permission than its `module` (as the rota pay/tips gates do) must check it inside the body too.
- **A dashboard's layout controls must check the page's own dashboard module (`config.moduleKey`), never a widget's module or the user's role** — View on a dashboard means use it, Manage means change its layout, and the API mount checks the same key (`moduleKey` in `app.js`). A new `DashboardPage` config without `moduleKey` hides every layout control from everyone but platform admins. A new layout action (a button that calls a dashboard or widget write route) must sit behind `canEditLayout` / `editing`, or View users see it and get a 403. Permission to change data inside a widget is the widget module's business, not the dashboard's.
- **A login started on a page other than the Overview must carry `appState.returnTo`** — `RequireAuth` passes it and `onRedirectCallback` in `main.jsx` goes there (a full page load, since the router has already read the address). A new `loginWithRedirect()` call that leaves it out lands the person on the Overview, which broke the connector's Connect page for anyone not already signed in on office.
- **`hidden_role_ids` (menu links, Overview tiles, dashboards) must go through `ownRoleIds()` (`services/roles.js`)** — the routes stored any uuid until migration 229, so one tenant could put another's role ids on its rows (the sweep now replays them). A new "hide from roles" list must check its ids the same way, and decide the caller's role with `effectiveRoleId()` (custom role first, then the built-in row for `users.role`), the same rule `/api/me` uses for the menu.
- **A text box in a row that wraps takes `flex-[1_1_12rem] min-w-0`, never `min-w-[12rem]`** — the flag note's box had a 12rem minimum, wider than a one-column dashboard widget's row, so it stuck out and the widget scrolled sideways (found only by the browser check measuring the box against its widget). With a flex basis the box asks for its 12rem, drops onto a line of its own when the row is short of it, and still shrinks to the container. Anything added to `FlagButtons` or `ItemRow` (`components/localInfo/shared.jsx`) must be checked in the narrowest widget, not only on the page.
- **Code a dashboard widget or a phone page pulls from the report pages must be loaded lazily** — `ReportWidget` imports the result card, charts and tables; imported straight into `widgetTypes.jsx` it would put them in every dashboard's (and the main) bundle, which sits close to the service worker's 6 MiB precache limit. `widgetTypes.jsx` uses `lazy()` with a `Suspense` around the widget, and `main.jsx` the same for `/mobile/reports`. A new widget that draws something heavy must do the same.
