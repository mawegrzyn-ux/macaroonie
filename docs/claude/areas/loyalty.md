## Mistakes to avoid

> Append-only: never delete an entry, only correct one that turns out to be wrong. New entries go at the end.

- **Loyalty points and stamps change only through `settleCheck()` / `settleOrder()` (`services/loyaltySvc.js`)** — they work out what a sale should give its member now and add the difference from the ledger for that source. A route, a device event or a job that adds points for a sale itself is undone (or doubled) by the next settle. Staff adjustments, welcome points and expiry are their own ledger kinds with their own sources; anything new that gives points needs its own `source_kind` (and the CHECK on `loyalty_ledger`).
- **A loyalty reward on a till or kiosk check must be reserved by the server first and named on the discount** (`POST /pos-api/loyalty/redemptions`, then `discount.applied` with `loyalty_redemption_id`) — the sequencer checks it with `loyaltyProblem()` and refuses any loyalty discount it can't find, and a store without `loadLoyaltyRedemption()` (the venue hub) refuses them all. Never let a device make a reward's discount up, and never mark a redemption used outside `useLoyaltyRedemption()` / `useRedemption()`: the minute sweep puts back any reservation that isn't on a check.
- **A till check earns loyalty only once it is `closed`, and an online order once paid or completed** — a test or script that pays but doesn't close the check sees no points. A member can't be taken off a check while a reward of theirs is on it (the till disables the button, the rules refuse it).
- **Staff loyalty search by email matches the whole address only** (`searchMembers()` compares the email's hash) — a part of an email finds nothing; type it in full, or search by name, phone or member number.
- **A kiosk sees a member's first name only and finds them by their card only** (`forDevice()` and the `code`-only rule in `routes/loyaltyPos.js`). Anything new a device reads about a member must go through `forDevice()`, or a public screen shows emails and phone numbers.
- **`loyalty_identities` is global (no tenant) and holds email hashes only** — found and changed in system mode; never store an email, a name or a tenant's data there, and delete an identity when no member uses it (`eraseMember()` does).
- **The test fixtures switch loyalty on for tenant A** (`fillTenant()`), with a reward, a stamp card and a member. A test (or the browser seed) that needs a group without loyalty passes `{ loyalty: false }`, as `loyalty.test.mjs` does. The public loyalty API (`/loyalty-api/`) is found by the site's slug and is in the tenant sweep's `PUBLIC` list, like `/order-api/`.
- **The Loyalty website block reads live data (`bundle.site_loyalty`), not the published snapshot** — like promotions, so it hides itself as soon as loyalty or its web app is off. Don't put its words into the block's data or the snapshot.
- **The guest's loyalty card has one implementation: `mountLoyalty()` in `api/src/assets/loyaltyApp.js`** — the stand-alone web app and the Loyalty card block both run it, so a change to the card goes there, never into `loyalty.eta` or the block's partial (which only set options and `--mloy-*` colours). Its CSS is scoped to `.mloy` with `mloy-*` class names, because it sits inside tenant sites whose templates style bare elements: a new rule must keep that prefix. The file is read once at API start (`routes/loyaltyApi.js`), so restart the API after changing it. Code that signs a guest in or out on a page must go through `setSession()` (or dispatch `mcrn-loyalty-session` with `from`), or other cards on the page and the ordering checkout keep showing the old state.
- **A shared file a browser loads without a bundler must be served together with every file it imports** — the menu screen player (`/lib/`), the online ordering page (`/order-api/`) and the loyalty card (`/loyalty-api/`) load shared ES modules straight from the server, and one 404 anywhere in the import tree stops the whole page with nothing on screen. #431 made `shared/orderPricing.js` import `pos/orderFlows.js` and `pos/charges.js`; the player's hand-kept `PLAYER_LIBS` didn't serve them, and every menu screen and order ready board stayed black from that deploy (running screens reload themselves on a new player version, so they went black too). The player's list is now worked out from the imports (`importClosure()`); the ordering page's and the loyalty card's files are still listed in their routes. A new import in a shared file must keep `api/test/browser-modules.test.mjs` passing, and a page that runs unattended must be able to start again by itself (the player's watchdog in `screen/index.html`).
