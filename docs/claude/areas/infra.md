# Deploy, servers and tests

Covers: deployment and CI, nginx and certificates, WebSockets and Redis, uploads and storage, the API tests and browser checks.

Key files and mistakes to avoid for this area: read it before changing code here. What shipped and when is in `docs/claude/history/infra.md`; the index of all areas is in `CLAUDE.md`.

## Key files

Under **API**, `src/...` means `api/src/...`; under **Admin portal**, `src/...` means `admin/src/...`. Other paths are from the repo root.

### API

- `scripts/nginx-custom-domain.sh <domain> [other names]` — switches a tenant's custom domain on: writes `sites-available/macaroonie-domain-<domain>` (everything proxied to the API), certificate via `certbot certonly --webroot` (HTTP-only block left on if it fails; https kept for the main name when only an added name fails), other names redirect, `REMOVE=1` (+ `DELETE_CERT=1`) / `DRY_RUN=1`, one run at a time (flock). The admin reads that file for `server_status` (`domainServerStatus()` in `routes/website.js`, also `cleanCustomDomain()` and `platformIps()`).
- `scripts/custom-domains-sync.sh` + `scripts/install-domain-sync.sh` — the domain sync: installed by every deploy as `/usr/local/sbin/macaroonie-domains-sync` (+ the domain script as `/usr/local/sbin/macaroonie-domain`), systemd `macaroonie-domains.timer` (every minute) and `.path` (runs when the API writes `/var/lib/macaroonie-domains/kick`). Switches on verified domains (DNS precheck, www / bare twin, backoff), removes blocks nobody has saved, writes `<domain>.json` + `last-run`. API side: `domainSyncInfo()` / `kickDomainSync()` / `domainServerFields()` in `routes/website.js` (`server_auto`, `server_state`); admin `DomainServerNotice` in `Website.jsx`.
- `scripts/ensure-nginx-ws.sh` — run by every deploy (6 Nov 2026): in each server block that proxies to the API and has no `/ws` location (not `macaroonie-domain-*` files), adds `location /ws` in front of its first location, with that block's own API address (from `location /`, else `/api/`, else any proxy_pass), the Upgrade / Connection headers and 3600 s timeouts, so tills, kitchen screens, kiosks, menu screens and the live kitchen view get live connections instead of asking every few seconds; `nginx -t` or restore, then reload. Env for tests: `NGINX_SITES`, `NGINX_CONF`, `NO_RELOAD`.
- `scripts/ensure-nginx-ai-timeout.sh` — run by every deploy: puts `location ^~ /api/ai/` (proxy timeouts 300 s, buffering off, the block's own proxy_pass and limit_req) in front of each `location /api/` block, so a Pepper turn over a minute isn't cut off with a 504; `nginx -t` or restore. It and `ensure-nginx-media-upload.sh` look for their own block since the previous `/api/` block, not in a fixed window.
- `.github/workflows/ci.yml` — on every pull request and push to main: migrates an empty Postgres 16 (no pg_cron) from 001, again (expects up to date), starts the API and waits for `/api/health`; plus `node --test` of `shared/test` and `shared/pos/test`; plus job `api-tests` (its own `macaroonie_test` database, `npm test` in `api/`). Separate from the deploy workflow.
- `api/test/` — the API tests (`npm test` in `api/`, Node's test runner, one file at a time, against `buildApp()` with `app.inject()`; they empty the database, so `DATABASE_URL` must name one with `test` in it). `support/register.mjs` + `loader.mjs` swap `src/middleware/auth.js` for `support/auth-stub.mjs` (`Bearer test:<sub>` + `X-Tenant-Id`, the real permission code); `support/app.mjs` (`getApp()`, `as(sub, tenantId)`, `ok()`, `closeApp()`); `support/seed.mjs` (`resetAndSeed()`: two tenants through `POST /api/platform/tenants`, people per role); `support/fixtures.mjs` (`fillTenant(sub, tenantId, { mark, slug })`: data in every area through the API, returns `{ ids, failed, writes }`); `support/fake-claude.mjs` (stand-in Claude API, streamed or JSON). `tenant-sweep.test.mjs`: the cross-tenant sweep (every route with params as tenant B with A's ids and B's mixed in; every write A made sent again as B, also with B's ids swapped into the address; no row of B's may hold an id of A's). `ai-chat.test.mjs`: Pepper's chat loop. `system-paths.test.mjs`: every path that finds its tenant itself (system mode, migration 176). `kitchen-flows.test.mjs`, `gloriafood-kitchen.test.mjs`. The tests' database must belong to a role that isn't a superuser (superusers skip forced RLS). See Docs.jsx → Deployment → Testing.
- `scripts/ensure-nginx-http2.sh` — run by every deploy (with `ensure-nginx-manage.sh` and `ensure-nginx-spa-cache.sh`): adds `http2` to `listen ... ssl` lines that lack it on an address where another block already has it, so nginx stops warning "protocol options redefined"; `nginx -t` or restore, then reload.
- `scripts/nginx-office-ops.sh` / `scripts/nginx-apex-landing.sh` — one-off server steps: office. + ops. server blocks with HTTPS (reuses a certificate covering both names, e.g. the wildcard, else `certbot certonly --webroot`; certbot never edits the file), then switching the apex `location /` to the API. See Docs.jsx → Deployment → Moving to office / ops.
- `src/services/storageSvc.js` — Pluggable uploads. `getStorage().put(tenantId, kind, ext, mimetype, buffer)`. Drivers: `LocalStorage` (writes to `UPLOAD_DIR`, served at `/uploads/*` by `@fastify/static`), `S3Storage` (lazy-imports `@aws-sdk/client-s3`, compatible with AWS S3, DO Spaces via `S3_ENDPOINT`, Cloudflare R2). - `src/config/ws.js` — WebSocket server. Rooms keyed by venue_id. Auth via JWT query param.
- `src/jobs/queues.js` — BullMQ queues. `notificationQueue` for emails, `holdSweepQueue` for hold cleanup.

Test: `api/test/platform-status.test.mjs`.

## Mistakes to avoid

> Append-only: never delete an entry, only correct one that turns out to be wrong. New entries go at the end.

- **`notificationQueue.add()` must never be awaited in request path** — Redis may be unavailable. Always use fire-and-forget: `.catch(e => req.log.warn(...))`. The booking is created and the response sent; the email is best-effort.
- **deploy.sh requires root but builds as ubuntu** — the script requires `sudo` to talk to PM2, but all `npm install` / `npm run build` steps must run as the `ubuntu` user to keep `dist/` and `node_modules/` owned by ubuntu. If `dist/` becomes root-owned, run `sudo chown -R ubuntu:ubuntu /home/ubuntu/app/admin/dist` then redeploy.
- **Website CMS: pluggable storage via `STORAGE_DRIVER`** — `local` writes to `UPLOAD_DIR` and serves through `@fastify/static` at `/uploads/*`. `s3` lazy-imports `@aws-sdk/client-s3` (listed as `optionalDependencies` so local installs don't pay the download cost). Switching drivers mid-flight will ORPHAN existing upload URLs — run a migration script to copy files between backends before switching.
- **File ownership on server** — if git throws "dubious ownership" on the Lightsail server, fix once with `git config --global --add safe.directory /home/ubuntu/app` rather than chowning files. The deploy workflow uses `git reset --hard` which needs this.
- **`systemctl reload nginx` doesn't always pick up new `location` modifiers** — adding `^~`, `~*`, or other matching modifiers to existing locations sometimes leaves the running workers using the old matching table even after a clean reload (config tested OK, no error). Symptom: the new behaviour is in `nginx -T` output but requests still hit the old block. `systemctl restart nginx` (full process restart, ~50ms downtime) clears it. For routing-modifier changes, prefer restart over reload.
- **Apex Nginx `location /uploads/` must use `^~` prefix-priority** — the apex `macaroonie.com` server block has a regex `location ~* \.(js|css|png|jpg|...)$` that serves static admin-portal assets from `/home/ubuntu/app/admin/dist`. In Nginx, regex locations take precedence over plain prefix locations, so a plain `location /uploads/` is shadowed by the extension regex for `.png`/`.jpg`/etc. and the request gets served (with 404) from the wrong root. Fix by writing `location ^~ /uploads/ { proxy_pass ...; }` — the `^~` modifier tells Nginx to stop after a prefix match without checking regex locations. Same trap applies to any new path serving binary uploads on the apex.
- **Custom error status to dodge Nginx error pages** — Nginx by default replaces upstream JSON 502/504 bodies with its own HTML "Bad Gateway" / "Gateway Timeout" pages, so the admin UI sees no `body.error` and shows the literal HTTP status text. For "I caught the upstream failure cleanly" cases (e.g. Auth0 invitation rejected), throw `httpError(422, ...)` instead of 502 — Nginx leaves 4xx bodies alone, so the actual error message reaches the operator.
- **Lightsail wildcard cert setup runbook** — Lightsail DNS has no Certbot plugin, so wildcard issuance uses `certbot --manual --preferred-challenges dns-01` with AWS CLI hook scripts. The full sequence is documented in the chat history (this session, May 2026). Key pieces: (1) IAM user with policy `lightsail:GetDomain`, `lightsail:CreateDomainEntry`, `lightsail:DeleteDomainEntry` on the domain, (2) AWS CLI v2 + credentials on the server, (3) `/etc/letsencrypt/lightsail-auth.sh` and `/etc/letsencrypt/lightsail-cleanup.sh` hook scripts, (4) `certbot certonly --manual --manual-auth-hook ... --manual-cleanup-hook ...`, (5) renewal cron at `/etc/cron.d/certbot` running every Monday + Nginx reload hook. **Don't switch to Route53 or Cloudflare** — the user's preference is Lightsail-everything; the hook-script path keeps that. **Don't switch to Caddy on-demand TLS** for the wildcard either — saved for a future round if custom-domain provisioning becomes high-traffic. Re-running `certbot renew` is idempotent; the hook scripts handle the dance with Lightsail DNS each time.
- **Nginx `client_max_body_size` defaults to 1 MB and silently breaks PNG uploads** — the API allows 30 MB via `@fastify/multipart`, but Nginx in front of it caps the request body at 1 MB by default. JPEGs are usually < 1 MB so they slip through; PNGs are typically 2–10 MB and get rejected with 413 before they reach Fastify. Symptom from the operator's perspective: "I can't upload PNG files" (sometimes works for tiny PNGs, never for normal photos). Fix: every server block that proxies to the API must include `client_max_body_size 30M;` (or higher if the API ceiling is raised). `setup.sh` now sets it on the apex block; the wildcard `*.macaroonie.com` server block must have it too. Same trap applies to PDF menu uploads (25 MB API limit) and receipt uploads in cash-recon.
- **nginx picks a server block by listen address first, then by name, so a host with no `listen 443` falls to the `*.macaroonie.com` tenant block** — office.macaroonie.com first came up with only `listen 80`, so https went to the wildcard block, which proxies everything to the API: the admin showed the API's JSON 404 (`Route GET:/ not found`). Then `certbot --nginx --redirect` added `if ($host = office…) { return 301 https://… }` inside that block, and once the block also listened on 443 it redirected https to itself. `nginx-office-ops.sh` now writes the whole file itself (separate port 80 redirect block and 443 block, certificate found on disk or from `certbot certonly --webroot`). For any new platform host, don't let `certbot --nginx` edit a block you also add 443 to by hand; check with `sudo nginx -T | grep -n "server_name\|listen"`.
- **`certbot --nginx` installs a new name's certificate into whichever server block matches it, including the `*.macaroonie.com` tenant wildcard block** — running it for office.macaroonie.com before office had its own 443 block put `ssl_certificate .../live/office.macaroonie.com/` into `macaroonie-wildcard.conf`, so every tenant site then served a certificate without its name (browsers and NordVPN flagged them). Check `grep -n ssl_certificate /etc/nginx/sites-available/*` after any certbot run; the wildcard block must point at `live/macaroonie-wildcard/`. Don't use `certbot --nginx` on this server; `scripts/nginx-office-ops.sh` uses `certonly --webroot` and writes the nginx file itself.
- **A custom domain reaches the site only through its own nginx block (`scripts/nginx-custom-domain.sh`)** — nginx picks a server block by name, and nothing else names a tenant's domain, so a request for it falls to the default server for the port; on this server that is certbot's port-80 block for the apex, which ends in `return 404`. The guest sees a bare nginx 404 however the app is set up (domain saved, verified, site live). When a custom domain 404s, check `ls /etc/nginx/sites-enabled/macaroonie-domain-*` (or the Domain section's notice) before looking at DNS or the app. The API never issues certificates or runs anything as root; the domain sync on the server does (corrected: this entry first said nothing was automatic). Only say a domain switches on by itself while `server_auto` is true (the sync's `last-run` is fresh).
- **A script holding a `flock` must close the lock for children that may outlive it** — `exec 9>lock; flock 9` hands fd 9 to every child, and anything that daemonises (nginx started directly, a stray background process) keeps the lock forever, so the next run waits 10 minutes and gives up. `systemctl` on the server hands the start to systemd so it's safe there, but the scripts still pass `9>&-` / `8>&-` to child commands; keep that on any new call. Test shims that start nginx must detach it like systemd (close fds, stdio to /dev/null), or `$(...)` capturing their output never returns.
- **`getent ahostsv6` returns nothing for a name's AAAA records on a server without IPv6** (getaddrinfo's AI_ADDRCONFIG), which is exactly when a stray AAAA record breaks certificate checks. The sync reads AAAA with `getent hosts` (IPv6 first, no ADDRCONFIG) and keeps only addresses with a colon.
- **The API runs as several processes (PM2 cluster, `instances: max`), so in-memory state is per process** — a WebSocket client is connected to one process; `broadcast()` reaches the others only through the Redis relay in `config/ws.js`. Don't send to sockets any other way (e.g. iterating `rooms` from a new module), and don't keep anything else in a module-level variable that another process must see (caches, rate counters, locks): use Redis or Postgres. Test anything realtime with two processes, not one.
- **A deploy step that checks the API right after `pm2 restart` must wait for it** — the cluster's processes take a few seconds to listen, so a single check after a fixed `sleep` fails at random while a rerun of the same commit passes. Poll with a time limit (the health check loops for 30 s) and keep every multi-line construct in `deploy.yml`'s script valid when drone-ssh's `script_stop` inserts an exit-code check after each line: a loop on one line is the safest shape.
- **nginx server blocks on the same address must agree on `http2`, or nginx warns "protocol options redefined"** — certbot writes `listen 443 ssl;` while our scripts write `listen 443 ssl http2;`. On nginx 1.24 http2 is a property of the socket, so the warning is harmless, but it hides real warnings in the deploy log; `scripts/ensure-nginx-http2.sh` aligns them each deploy. Keep writing `ssl http2` in new nginx scripts on this server. `http2 on;` (the newer directive) doesn't exist before nginx 1.25.1, which Ubuntu 24.04 doesn't ship.
- **A Workbox `navigateFallback` must point at a page that is in the precache** — `admin/vite.config.js` leaves `index.html` out of `globPatterns` (a cached shell kept booting old deploys), but kept `navigateFallback: '/index.html'`, so the generated `sw.js` called `createHandlerBoundToURL('/index.html')` and threw `non-precached-url` on every worker start (in every admin console from 22 Aug to 14 Oct 2026; the worker still installed, but the routes registered after it never were). It is `navigateFallback: null` now. If `index.html` ever goes back into the precache, the fallback can come back with it, never one without the other.
- **Uploads over 30 MB need the media upload nginx location** — the API allows 150 MB videos only on `POST /api/media/items/upload` and `/items/:id/replace`, and only because `scripts/ensure-nginx-media-upload.sh` (every deploy) adds a regex location with `client_max_body_size 160M` before each `location /api/`. A new route that takes big files needs adding to that regex, or nginx answers 413 before the API sees it. In the API, `@fastify/multipart`'s global 30 MB limit applies unless the route passes its own `req.parts({ limits })`, and each part still has to be checked against its own type's limit.
- **A Cache API entry can't be a 206** — the screen service worker stores each video whole (status 200) and slices ranges itself. Don't `cache.put()` a ranged response or answer a video request with the whole file when it asked for a range (some players then refuse to seek).
- **nginx ensure-scripts that insert before `location /api/` must find their own block in the text since the previous `/api/` block** — `ensure-nginx-media-upload.sh` and `ensure-nginx-ai-timeout.sh` both insert there, so a check in a fixed window before the line stops seeing a block once the other script's lands in between, and the script adds itself again on every deploy (nginx then refuses the duplicate location). A new script inserting at the same place must use the same region check.
- **Migrations must build on an empty Postgres without pg_cron (CI checks every pull request)** — TRUNCATE tables that others reference in one statement with `CASCADE` (separate statements are refused even when the tables are empty), and use an extension a hosted or CI Postgres may lack only inside a `DO` block that tolerates its absence. The live server never re-runs an applied file, so fixing an old migration to build from empty changes nothing there; never change what an applied migration does to existing data.
- **The API tests empty the database they run against** — `resetAndSeed()` truncates `tenants` (cascading to everything) and the platform tables, and refuses a `DATABASE_URL` whose database name lacks `test`. Never point `npm test` at a real database, and keep that check.
- **A new table or a route that takes ids is only swept once the fixtures make a row for it** — add a step to `fillTenant()` in `api/test/support/fixtures.mjs` that makes the row through the API (so its write is also replayed as the other tenant). A named route parameter whose ids come from one table goes in `KINDS` in `tenant-sweep.test.mjs` (with the real table name: the test fails on a `KINDS` table that doesn't exist). A deliberate cross-tenant change or reference goes in `ALLOWED_CHANGES` / `ALLOWED_REFERENCES` with its reason, never by loosening a check.
- **`/uploads` files are served with `Cache-Control: public, max-age=2592000` and `Vary: Origin`**, so a browser test of what a device keeps offline passes from the browser's own HTTP cache (and a media element's in-memory buffer within a page) unless it clears them: clear the HTTP cache (CDP `Network.clearBrowserCache`) and open a fresh page, and keep a control that fails without the saved copy (`kiosk-videos` entry deleted). The service worker's video route sets `matchOptions: { ignoreVary: true }` because of the `Vary` header. And `publishMenu()` treats a time up to 30 s ahead as now (immediate, tills told): a test of a scheduled publish going live by itself must schedule further ahead.
- **The admin's main bundle must stay under the service worker's precache limit (`maximumFileSizeToCacheInBytes`, 6 MiB in `admin/vite.config.js`), or `vite build` fails and so does the deploy** — the limit is checked only by a production build (CI doesn't build the admin; the dev server never checks), and adding Help and Docs text for till layouts pushed the bundle 2 KB over it. Pages that are big and seldom opened load as their own chunks (`React.lazy` + `Suspense` in `main.jsx`, as Help and Docs since 31 Oct 2026); run `npx vite build` in `admin/` before shipping a large page or a lot of text, and split another page out rather than raise the limit.
- **Run the API tests with `--test-force-exit --test-concurrency=1`** (as `npm test` in `api/` does) — without force-exit the runner waits on the app's open handles after the last test and looks hung (a `| tail` shows nothing), and test files run in parallel collide on `resetAndSeed()` (duplicate key on `platform_admins`).
- **A test that opens WebSockets against `attachWss()` must terminate every socket in `finally`** — `wss.close()` waits for its clients, so a failed assertion that leaves a socket open makes the test hang until the runner's timeout instead of failing (the live view socket test did, 600 s, under a mutation). Keep a list of the sockets opened and `terminate()` them (and `wss.clients`) before closing.
- **`npm test` in `api/` doesn't run migrations** — `resetAndSeed()` empties the tables of whatever schema the test database has. After pulling a migration, run `node scripts/migrate.js` against the test database first, or tests fail with a 500 "column ... does not exist" that looks like a code bug (CI migrates before its API tests).
- **A server block that proxies a device host to the API must pass WebSockets at `/ws` (Upgrade + Connection headers, a long read timeout)** — without them nginx turns the socket into a plain GET, the API answers 404, and tills, kitchen screens, kiosks, menu screens and the live kitchen view quietly fall back to asking every few seconds (the live view says *Checking every few seconds*; nothing errors). `scripts/ensure-nginx-ws.sh` adds the location on every deploy; a new server block made by hand for a device host gets it on the next deploy, or run the script. And a socket that may sit quiet must be kept open from its own side: a page that only listens should send `{"type":"ping"}` (device sockets are answered with a pong) and drop a link that stops answering, as the live view and the kiosk do, or a 60 s proxy timeout closes it and a hung link is never noticed.
- **Browser checks: four traps met while testing the phone till** — `innerText` follows CSS `text-transform` (an uppercase label reads ORDER), so compare `textContent` or ignore case; a "this stays the same" check passes by accident when it reads before the page settles, so wait for the thing that would change it (or a fixed settle time) before asserting; a script that changes data needs the database reseeded before every run, mutation runs included; and never edit a source file while a mutation runner is rewriting it (it puts its own copy back over the edit): check every original is back afterwards. Also: a harness script that runs `pkill -f <pattern>` kills any shell whose own command line contains the pattern, so don't name that file in the same command (exit 144, nothing printed).
- **An admin page's address must not start with a path the admin's hosts hand to the API** — on office. and ops. nginx proxies some paths to the API before the app sees them (`/api/`, `/ws`, `/webhooks/` and the guest paths looped over in `scripts/nginx-office-ops.sh`: `/manage /reservations /widget-api /order-api /uploads/ /template-assets/`), matched as plain prefixes. `/reservations-widget`, the Reservations widget page's address from the day it shipped, starts with `/reservations`, so loading or reloading it showed the API's JSON 404: it only ever worked when reached by a link inside the app (the dev server's proxy list in `admin/vite.config.js` has the same prefix, so dev showed it too). The page is `/website/reservations-widget` since migration 241. `api/test/nav-default.test.mjs` reads the prefixes from the nginx script and the Vite config and fails on a catalogue route under one. Test a new page by loading its address and reloading it, not only by clicking to it.
- **Browser checks from one address hit the API's rate limit (200 requests a minute): send a new `x-forwarded-for` per page load, on `/api/` calls only** — the API trusts the header (nginx sets it in production), and a check that loads a few dozen pages a minute from localhost starts getting 429s that look like broken pages. Add the header through a route on `/api/` requests only (Playwright `context.route`): put on every request, Google Fonts refuses it and the page's fonts fail.
- **Browser checks of data pages: five traps met on the Reports pages** — the text of sibling block elements joins with no space between them ("Sales by dayTill sales"), so match parts, not a sentence; picking a choice already used in the last 30 s is answered from the query cache with no request, so a check that waits for the request must pick one not used before; the fixtures' "Test Guest" bookings have random times and party sizes at every seed, so expectations must follow the API's answer (or the one fixed booking), never numbers written down from one run; a check that deletes or changes data belongs in its own part with a reseed before every run, mutation runs included; and after midnight the date under test may no longer be the one the data sits on (the trading day entry above).
- **Browser checks and mutation runs: three more traps met on the builder** — an assertion must be able to fail for the reason it names: "Save is off while the report isn't ready" passed on a report with no name, which keeps Save off whatever else is true (read the note beside it, or set the page up so only the thing under test can switch it off); while a mutation runner is at work the source file it is on holds the mutation, so don't read that file to learn what the code does (and never edit it); and before counting a mutation as missed, check it changes anything at all: a `.filter()` in front of a `.map()` whose component already draws nothing for those entries can go without any difference.
- **A mutation counts as caught only when the check that fails is the one about it, and a rule needs a check in the case where breaking it shows** — the builder's first mutation run called "Back always goes to the list" caught, by two calculation checks that have nothing to do with Back: they were flaky (the test typed straight after tapping a value into a calculation, before the tap's handler had put the caret back in the next frame; `caretAt()` in the builder's checks waits for it now). "A tapped value goes in at the end" slipped through because the check only ever tapped with the cursor at the end, where the broken rule and the right one agree (the check now selects a word in the middle); "the message sits under the Mobile view button" slipped through at 390 px, where the message happens to clear the button sideways (a 320 px check catches it); "Save while the report isn't ready" was run against a part with no check of Save. Read which check failed before counting a catch, run each mutation against the part whose checks cover it, and when a mutation is missed ask first whether the check ever puts the page in the case the rule is for. A run that stops because the page the next step waits for never comes (Back went somewhere else) is a catch; a stop anywhere else is a broken check.
- **Mutation runs: three more rules met on the drill-downs** — a mutation of `api/src` or `shared/` made in place is loaded by the browser harness's API at its next restart, so never run those while browser checks or page mutations are going (and never edit the file a runner is on); a mutation's old text must be found exactly once in its file, or the runner changes the wrong place without a word; and a mutation that changes nothing has to be reasoned through before it is written off (`drillOffers()`' early return for a list: `drillSpec()` refuses every level and the rows for a list anyway, so the result is the same without it).
- **Browser checks: three traps met on charts and the print page** — a position read from the page before something scrolls (figures brought into view, a window opening) is stale by the time it is tapped: read the position and tap in one step, after the scroll has settled; a title `<p>` followed by a `<ul>` reads through `textContent` with no space between them (match the parts, as with sibling blocks); and a tap at the middle of a table row lands on a figure's cell, which opens the rows behind that figure where the report's figures count different rows: tap the row's first cell to open the row itself.
- **Mutation runs: four more rules met on charts and the print page** — a container restart can stop a fault run in the middle of a change and leave the fault in the source: after any restart look for `*.rmut-bak` / `*.bmut-bak` / `*.cmut-bak` beside the source files and put the file back from it before running or committing anything (a stray fault in `print.js` sat there until a search for the backup found it); an assertion that something is *not* drawn or written must look for exactly what the code would write when it is wrong (the check that a sliver's share isn't written looked for `>1%<`, but under 10% the share reads `1.0%`, so it passed whatever the code did: an absence check that can't fail is worse than none); and a fault that removes a response header a global plugin also sets (`@fastify/helmet` sends `Referrer-Policy: no-referrer` on every response) changes nothing a test can see, so count it as changing nothing rather than writing a check for it; and a fault run against only some parts of a browser suite must name every part whose checks could catch it (two page faults here came back missed only because the check that catches them sits in another part: read where the covering check is before writing a new one).
- **Browser checks: three traps met on opening records from report rows** — a `position: fixed` element has a null `offsetParent`, so "is it showing" read from `offsetParent` says a fixed bar is hidden (use `getClientRects().length` or its box); a locator by a button's words (`main button` with Checks) can match a tab with the same words first, which then does something else that looks right by accident (Till reports' Checks tab beside a day's own Checks button: give the page's own buttons test ids and click those); and a bar drawn by `AppShell` above every page needs the floating menu button's room below `lg` on non-touch screens too (`max-lg:notouch:ml-0` on a button pulled left with a negative margin, which otherwise sat under it).
- **Never assert or throw inside a stand-in Claude reply** (`claude.script.push(body => ...)` in the API tests) — the stand-in answers a reply that throws with a 500, and the Anthropic SDK retries 500s with growing pauses, so a failed check inside a reply shows as a test that hangs for minutes, not one that fails. Read what was sent after the call (`lastBody()`, `claude.requests`) and assert there.
- **Don't run `smartBuild()` or `askForJson()` against the real API from tests, CI or a script left running** — every call is paid and counts against the group's monthly allowance and the person's daily share. The API tests use the stand-in Claude; `api/scripts/report-smart-check.js` is for a person to run by hand before a release, and it says how many units it used.
- **A stand-in Claude script that runs out answers 500, which the SDK retries for about 8 s and the route then reports as 503 (Claude is busy)** — in an API test a 503 after a pause means the server asked the model more times than the test scripted (a second ask with another subject in full, a retry with the reasons), not that Claude was busy. Read `claude.requests` to see what the extra call was.
- **A browser check that saves a device's settings changes what the next pass opens with** — the phone checks ran at 1280 then 390 px against the same till, and the second pass started with what the first had saved, so its "the usual" checks failed. Put a device's settings back (PATCH the whole settings) before each pass that reads its defaults.
- **A reconciliation test proves a rule only for the rows its data holds: put each case the rule decides into the test's data** — the end-of-phase-3 mutation run (14 Nov 2026) found eight report rules that no test could break, every one because the tests' data had no row of the case the rule is for: an H&S action of only spaces (the Overview counts any corrective action written, so the catalogue's rule must not trim), a closed issue (not Open), a cancelled supplier order and its lines (count nothing), venues in time zones a day apart (each venue's H&S days end at its own today, never the latest), a wage paid on a day outside its own week (it counts in its week, never on that day). When a rule handles an edge (an empty value, a status that leaves rows out, a time zone, a date outside its period), add that row to the reconciliation test and check the figure moves the right way. A guard against data no route can make (a delivery without an order judged as sent late, an order judged twice) is tested by calling the function directly, as `reports-sent-late.test.mjs` calls `judgeFirstSend()`.
- **A browser check of a scheduled send uses Send now, or calls `sweepSchedules()` itself** — the browser harness's API runs no schedule worker, and the API tests call the sweep directly (SendGrid stood in by a stubbed `fetch`) rather than wait for the minute.
- **Build the admin (`npx vite build`) in a shell without the API test env** — with it sourced the main bundle came out at 8.23 MB and failed the service worker's 6 MiB precache limit, which reads as "the bundle grew"; in a clean shell it was 5.26 MB. Check the shell before splitting a page out.
- **Browser checks need a harness, which isn't in the repo: build it in the scratchpad** — run the API with the test auth stub (`node --import ./test/support/register.mjs src/server.js`, the test env, `PORT=3000`), and the admin with a Vite config that `mergeConfig`s `admin/vite.config.js` and aliases `@auth0/auth0-react` to a stand-in (signed in as `localStorage.harness_sub`, token `test:<sub>`, and exporting `Auth0Context` for the Office app's provider); seed with `resetAndSeed()` + `fillTenant()`. The config file outside `admin/` needs a `node_modules` link to `admin/node_modules` to load Vite, and Playwright is loaded with `createRequire`. A stand-in model for Pepper: a small server answering `/v1/messages` with `streamEvents()` from `test/support/fake-claude.mjs`, the API started with `ANTHROPIC_BASE_URL` pointing at it. API tests empty the same database: reseed after them, and stop the harness API before running them: its background workers (task notices, emails, the scheduled fill) write to the same database while the cross-tenant sweep checksums tenant A's rows, which it then reports as changed by a GET.
- **A new app folder with its own `package-lock.json` needs a `!<folder>/package-lock.json` line in the root `.gitignore`** — the root ignores every lock file, so `office-app/package-lock.json` was left out of its first commit without a word (git only shows it with `git check-ignore`). An Expo app also wants its own workflow (like `android-app.yml` / `office-app.yml`) and a `deploy.yml` `paths-ignore` entry, so a change to the app alone doesn't redeploy the server.
- **An Expo app's exact `react-native` must match the `expo` patch its lock file holds** — `expo doctor` checks each dependency against the installed expo's `bundledNativeModules.json`, and SDK 58's patches differ (expo 58.0.20 wants react-native 0.88.0, 58.0.26 wants 0.88.1). A fresh lock picks the newest expo patch, so `office-app` (made later) needed 0.88.1 while `android-app`'s lock still holds 58.0.20 with 0.88.0. Check with the installed `node_modules/expo/bundledNativeModules.json` (no network needed) after any change to an app's lock, and bump react-native, react and react-native-webview to what it says.
- **A new background job (a BullMQ worker) is added to `JOBS` in `services/platformStatus.js` with its interval, and to the `watchWorker()` list in `server.js`** (22 Nov 2026) — otherwise Platform status can't say when it last ran or mark it late, and a worker that stopped goes unnoticed. Status lives in Redis (heartbeats, last runs), never a module variable: the API is several PM2 processes and each would see only its own. An ioredis client with `enableOfflineQueue: false` refuses commands until it is ready: wait for `ready` first (`ready()` there), or the first heartbeat after a restart is lost.
