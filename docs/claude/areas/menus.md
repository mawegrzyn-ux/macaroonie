# Menus

Covers: menus and publishing (releases), option groups, allergens and dietary tags, the print designer, tax rates, combos (meal deals), menu times, translations, the Deliveroo file.

Key files and mistakes to avoid for this area: read it before changing code here. What shipped and when is in `docs/claude/history/menus.md`; the index of all areas is in `CLAUDE.md`.

Under **API**, `src/...` means `api/src/...`; under **Admin portal**, `src/...` means `admin/src/...`. Other paths are from the repo root.

## Mistakes to avoid

> Append-only: never delete an entry, only correct one that turns out to be wrong. New entries go at the end.

- **Secondary combo row canvas at z=4** — secondary combo rows (where the spanning card from the primary row above paints over them) must have `z-index: 4` AND `pointer-events: none` on their canvas div. z=4 ensures their clipped gradient background paints above the primary's z=3 stacking context. `pointer-events: none` lets click and drag events pass through to the primary row's spanning card. Without z=4, the gradient is invisible (the primary's z=3 stacking context covers T3B entirely).
- **Menu variant groups are tenant-wide libraries** — `menu_variant_groups` + `menu_variant_options` hold reusable option sets (Protein, Size). Items attach groups via `menu_item_variant_groups`; optional `menu_item_variant_prices` override a single option's price on that dish. Ad-hoc `menu_item_variants` remain for one-off options. Do not copy group options onto items — keep the live link. Item photos live on `menu_items.image_url`.
- **`Menus.jsx`'s save-payload builder whitelists fields explicitly — it does not spread `...item`/`...section`** — the read-side draft hydration DOES spread (`{...s}`, `{...it}`), so a newly-added field flows into local editor state and displays/edits fine, giving the false impression that wiring is complete. But the PATCH-time payload builder (`(draft.sections || []).map(...)` in the save mutation) lists fields one by one; a field left out of that list is silently dropped on every save even though the UI showed it correctly right up until the page reload. Whenever you add a field to `menu_items`/`menu_sections` (or any similarly-shaped whole-tree-upsert page), grep for the explicit save-payload mapping specifically — don't assume the read-side spread means the field is already wired end-to-end. Bit us building `calories`/section `image_url` (caught before shipping, not in production).
- **The printed menu's preview is only accurate at full page width** — `menu_print.eta` uses the same page size and padding on screen and in print so its fit check can measure each sheet, but below 800px the columns collapse to one (screen only) and the check is skipped. Never add screen-only padding or sizing to `.page`, or the "fits / too long" result stops matching what prints.
- **Menu section and dish ids must survive a save — the print designer points at them** — `upsertMenuTree()` deletes and re-inserts the tree, and until migration 121 every save issued new ids, so anything storing a `menu_sections.id` / `menu_items.id` silently lost its link. It now inserts under the ids the client sends, and `Menus.jsx`'s save payload sends `id` for every section and item. A new caller of `upsertMenuTree()` must send ids for existing rows (or accept that links to them break), and must give fresh ids when copying (as `/duplicate` does, remapping `print_layout`). Note the delete still fires `ON DELETE SET NULL` on `fs_cooking_checks.menu_item_id` on every save — keeping ids did not fix that link.
- **The menu designer and the designed print share one renderer — change block output only in `shared/menuLayout.js`** — the designer canvas must never grow its own copy of a block's HTML or CSS, or the design stops matching what prints (the canvas/SSR drift trap from the website builder). Both sides also have to agree on grid maths (`layoutGeometry()`), so the API's `LayoutBody` bounds check and the designer's clamping both call it. The designer loads Tailwind's preflight while the print page does not: any shared CSS rule on an element Tailwind resets (`img`, headings, borders) must set every property it relies on explicitly, and use at least `.ml-page .x` specificity to beat `.ml-page img`-style rules.
- **In the menu designer, grid position to mm is not `x * colMm` once a sheet is folded** — with `print_layout.fold` set, grid lines past the middle are shifted by the fold gap, so block positions must come from `blockStyle()` (which uses `colStart`/`colEnd`/`rowStart`/`rowEnd`) and pointer maths from `colAtMm()`/`rowAtMm()` in `shared/menuLayout.js`. Multiplying by `geo.colMm` / `geo.rowMm` directly puts anything in the right or bottom half off by the gap.
- **Web ordering tables point at dishes without foreign keys** — `order_items.menu_item_id` and `ordering_item_availability.item_id` are plain uuids because `upsertMenuTree()` deletes and re-inserts the menu tree on every save; a FK would null them (SET NULL) or block the save. Ad-hoc variant option ids in baskets are `v:<label>` for the same reason.
- **Menu layout fonts are CSS variables, never literal family names in `MENU_LAYOUT_CSS`** — every rule uses `var(--ml-body)` / `var(--ml-heading)` / `var(--ml-script)`, set on the page by `pageStyle()` and on a block by `blockStyle()` when it has `opts.font`. A new rule with a hardcoded `'Inter'` ignores the operator's font choice, and a font name that isn't in `FONT_WEIGHTS` is never loaded (the URL builder drops it), so it silently falls back. `.ml-block` sets `font-family: var(--ml-body)` itself because a child inherits the page's already-resolved family, not the variable: without it a block's font override would only reach elements that set their own font-family.
- **Printing drops CSS background colours unless the element sets `print-color-adjust: exact`** — Chrome's print (and "Save as PDF") leaves backgrounds out when "Background graphics" is off, which is the default, while the on-screen preview shows them. Dietary tag chips, highlighted sections and house favourites printed white until both menu print layouts (`menu_print.eta`, `shared/menuLayout.js`) set the rule on them. Any new coloured element that must print needs it too (both the plain and `-webkit-` forms). Test with `page.pdf({ printBackground: false })`, not a screenshot.
- **Whether a dish can be ordered at a time is decided by its menus' schedules, via `itemOffAt()` / `menuOnAt()`, and the collection time counts, not the time of ordering** — a dish in several menus is orderable when any of them is on. Any new ordering path (table QR, delivery, POS) must check the basket at its promised time the same way, or it will sell lunch dishes at dinner. Date ranges only clash from today on in `scheduleProblem()`: pass `today` (venue-local), or an old menu that ended last month blocks saving. (Corrected by migration 230: a menu's online schedule comes from menu times (`webSchedules()`), overlapping menus are no longer refused anywhere (`menuTimesWarnings()` notes them, both are on), and the check that stops a save is `menuTimesProblems()`; `itemOffAt()` with the promised time is still the rule for what can be ordered.)
- **Anything that points at a menu row by id needs that row to keep its id across `upsertMenuTree()`** — sections and dishes did since migration 121, footer notes (`menu_callouts`) only from the footer-notes pick: before that every save gave them new ids, which would have silently emptied any designer block that picked notes. A new pointer (designer option, website block) at another menu child table must first make that table insert the client's id, send the id from `Menus.jsx`, and remap it in `/duplicate`.
- **A dish's attached variant group comes in two shapes: `{ options: [{ option_id, overridden, price_pence }] }` from the server (`loadMenuFull()`) and `{ overrides: [{ option_id, price_pence }] }` once edited in `Menus.jsx`** — read its price overrides only through `overridesOf()`. Code that read `g.overrides || []` treated a freshly loaded group as having none, so changing one option's price wiped the dish's other custom prices.
- **A menu's print design is `menus.print_design_id`, not the only design** — since migration 135 there can be several `menu_print_designs` rows per menu. Anything that prints or previews "the menu's design" must go through the print route (`?design=` or the menu's chosen one), and code copying a menu must copy every design and remap it (`remapLayout()` in `menus.js`).
- **An allergen's level has six menu renderers and they must agree: May contain looks like Contains, Can be removed adds the asterisk** — `menu_print.eta`, `menu_print_dietary.eta`, `shared/menuLayout.js`, `blocks/menu_inline.eta`, `MenuInlineCanvas` (`dataBlocks.jsx`) and `shared/ordering.eta`. Each reads `item.allergen_levels[code]` itself. A new place that draws dish badges must do the same, and must get `allergen_levels` from its loader (it is a separate field from `dietary`, so a loader that only selects codes silently drops every level, and a writer that only sends `dietary` resets every allergen to Contains). Only staff tools (`LevelChip`) draw May contain differently.
- **A tag with `show_on_menu` off must be filtered where guest data is loaded, not in `loadMenuFull()`** — the menu editor and the matrix need every tag. The guest loaders (`loadPrintMenu()`, `GET /menus/public/:id`, `loadInlineMenus()`, `loadOrderingMenu()`) drop hidden tags, and every renderer skips a dish code with no matching tag, so a new guest-facing menu surface must load through one of these or call `menuTags()` itself (as `MenuInlineCanvas` does, since it reads the admin route). The "Can be removed" note must use `hasRemovable(item, shownTags)`, not raw `allergen_levels`, or it shows for a hidden allergen.
- **A dish's dietary tags have two writers: the menu editor's whole-tree PATCH and the Allergen matrix's `PUT /menus/:id/allergens`** — the PATCH rewrites `menu_item_dietary` from whatever the editor loaded, so a menu open in `Menus.jsx` from before a matrix save puts the old tags back when it is saved. The matrix PUT invalidates `['menu', id]`, which only helps a tab in the same browser. Any new place that edits dish tags must write only the dishes it changed (never a whole-menu replace) and invalidate both `['menu', id]` and `['allergen-matrix', id]`.
- **What the key under a menu lists, and the asterisk note's words, come only from `allergenKey()` with the tenant's allergen notice** — an `allergens` footer note no longer prints its own `title`/`body` (the column is still NOT NULL, so the admin keeps sending the stored title). A new surface that shows menu badges and a key must load the notice (`loadAllergenNotice()`, or `allergen_notice` from `loadMenuFull()`) and pass it to `allergenKey()`; filtering tags by "used on this menu" by hand ignores the operator's ticks and `used_only`, and hardcoding "Can be removed on request" ignores their wording. `in_key` is written only by `PUT /menus/allergen-notice`, which sets it for every tag of the tenant from `key_tag_ids`, so a caller that sends a partial list switches the rest off.
- **A Deliveroo file must go back byte for byte as it came, apart from the cells we fill** — read it with `parseCsv()` (keeps every value as text, reports the line endings) and write it with `toCsv(columns, rows, { eol, trailing })`. Reading a CSV with the `xlsx` library or any parser that types values turns ids like `1e5` or `0123` into numbers and dates into dates, and Deliveroo then can't find the items (item_id must never change). Only `FILL_FIELDS` columns may change; a new column the tool fills must be added there, which also makes it keepable and typeable.
- **An allergen we know about must never be dropped from the Deliveroo file silently** — a tag with no Deliveroo code is an error in `dishValues()` and blocks the CSV download. Don't turn that into a warning or filter unmapped tags out to get a clean file: the dish would show on Deliveroo without that allergen.
- **A new menu, section, dish or footer-note field must also go into `menuSaveBody()` (in `shared/menuSave.js` since 24 Nov 2026; first in `routes/menus.js`)** — it is the loaded-menu-to-PATCH-body copy used by `/duplicate` and by every AI menu tool, and the PATCH rewrites the whole tree, so a field left out is wiped from the whole menu the next time the assistant changes anything on it (and copies lose it). This is on top of the existing touch points (Zod bodies, `loadMenuFull()`, `upsertMenuTree()`, the Menus page payload). The round trip `menuSaveBody(loadMenuFull())` → PATCH must leave the menu unchanged; check a new field survives it.
- **AI menu tools never write ad-hoc `variants` and never change a variant group** — dish options go only through `variant_groups` with per-dish `overrides` (the Menus page also sends `variants: []`). A choice a group doesn't have is refused rather than added, because adding it would change every dish using that group. Allergens and dietary tags are matched to existing tags only: never create a tag from a name the model read off a photo, or a misread word becomes an allergen on the website, print, ordering and the till.
- **Anything that shows a menu to guests or devices must load it with `loadMenuVersion()` / `loadMenuVersions()` (`services/menuReleases.js`), never `loadMenuFull()` or its own SQL on `menus` / `menu_sections` / `menu_items`** — since migration 165 those tables are the draft, so a new reader that queries them shows prices and dishes nobody has published (and a reader that drops `is_published` from the version and reads it off the `menus` row instead gets the draft's setting). Editors and admin pickers stay on the tables. A menu with no release isn't live: a reader must treat "no live version" as "not on the menu", not fall back to the draft (staging is the one deliberate draft reader).
- **A field added to a menu row must also be judged by `shared/menuDiff.js`** — `releaseContent()` decides what a release keeps and `contentKey()` what counts as a change. A column that is re-made on every save (like one-off option ids, or `sort_order` renumbered 0, 1, 2) must be left out of the comparison, or every save shows "changes not published" and Publish is offered for nothing; a tenant-wide setting that should stay live must go in `MENU_DROP` and be attached at read time in `withExtras()`.
- **Release rows are immutable and cached by id in each API process** — never UPDATE a release's `snapshot` (or `goes_live_at` of a live one) to fix a menu: publish again, or cancel a scheduled one. A test that moves `goes_live_at` must keep it after every earlier publish, or the older release stays live.
- **A print link from the admin to the draft goes through `useOpenPreview()` (a preview link), not `/api/menus/:id/print`** — the plain print URL is public and shows the live version; opening it from the editor after a save shows the old menu, which reads as "my change didn't save".
- **Screen data must come from `screenConfig()` / `designerData()`, which read the live menu versions** — a board that read the menu tables would show unpublished prices on the restaurant's screens. Sections hidden everywhere are dropped in `slimMenu()`, tags through `menuTags()`; a new field a board shows must be added to `slimItem()` / `slimMenu()` or the player never gets it.
- **Playlist times end before their end time (`boardOnAt()`), unlike online-ordering menu times (`menuOnAt()`, end included)** — so back-to-back times (11:00-15:00, 15:00-22:00) never show both boards. Don't swap one function for the other; 23:59 counts as midnight in `boardOnAt()` only.
- **A dish's tax has one rule: `taxFor()` in `shared/tax.js`, fed the dish's levels `[dish, section, menu]` and the sale's context `{ venue_id, order_type_id, revenue_stream_id }`** — this corrects the earlier "A dish's ordering VAT has three levels" entry: `vatRateFor()` and the `vat_rate_takeaway` / `vat_rate_eat_in` columns are gone (migration 170). A new place that prices or reports a sale (table QR, delivery, a GloriaFood import into the till) must build its context and call `taxFor()` (or the till's `posTax()`), never read a rate off the dish, or exceptions for order types, locations and streams are silently ignored. Revenue streams decide tax only through exceptions that name them.
- **A migration that changes the shape of menu content must rewrite `menu_releases.snapshot` too and blank `content_hash`** — readers load live versions from the snapshots, so a column moved only on the menu tables leaves the live menu in the old shape, and an unchanged hash makes every untouched menu read as "changes not published". Migration 170 rewrote the snapshots in SQL and set `content_hash = ''`; `rehashReleases()` (run by `backfillFirstReleases()` at API start) re-hashes them with `shared/menuDiff.js`.
- **A combo's steps, picks and prices have one set of rules: `shared/combos.js`** — a new surface that shows or sells a combo (kiosk, table QR, a report) must go through `resolveSteps()` / `priceCombo()` (via `priceItem()` or `priceLine()`) and show its price with `comboMenuPrice()`. Pricing parts by hand skips conditions (a sauce step left after the fries were swapped), sold out choices and the rule that a part's base options don't change the deal price. Anything that finds a combo's dishes needs the `{ itemsById, sectionItems }` ctx: online it must include dishes switched off for ordering (`combo_parts`), or a combo offering them can't be completed.
- **A combo step's condition may only point at an earlier step** — `resolveSteps()` walks the steps in order and drops picks on hidden steps as it goes, and `cleanCombo()` drops a `when` naming a later or unknown step on save. An import or editor that writes combos must keep that order, or the step silently never shows.
- **The till keeps one modifier per repeated pick; group only to show them** — `selectionFromModifiers()` (Make it a combo) rebuilds the selection from a line's modifiers, so storing "2 x Cheese" as one modifier would lose a pick. Show modifiers through `groupModifiers()` + `modifierText()` and combo parts through `countParts()`. Online order lines are different: their options are display only (the order is priced from the selection), so `priceChoiceSet()` stores a repeat once as "2 x Cheese" at the summed price; never parse those labels back into picks.
- **Automatic combos are discounts, not changed lines** — on the till a `promotions.set` entry with `kind: 'combo'` (`promotion_id` = the combo's item id), online an `order_promotions` row with `promotion_id` NULL and `combo_item_id` set. A report or query that groups discounts by `promotion_id`, or joins `order_promotions` to `promotions` with an inner join, drops combo savings. And combos run before promotions: a new discount engine must take `line_total - comboOff`, as `priceBasket()` does, or a line gets both discounts in full.
- **A new boolean on an option group must be left out of `releaseContent()` when false (`GROUP_FLAGS` in `shared/menuDiff.js`)** — attached groups ride in every release snapshot, so a new column that defaults to false appears in the draft and not in older releases, and every menu reads as "changes not published" until republished.
- **A combo's allergens are the union over every dish it can hold (`comboItemIds()`), never "none listed"** — a combo row has no tags of its own, so reading its own `dietary` showed "No allergens listed" for a meal full of them. Use `itemLevels()` (strongest level per tag over all its dishes, with the "Depends on what you choose" line), and on the order page the allergens of what was actually picked.
- **Only previews may load the draft menu: `kioskConfig()` uses `menuVersion: 'draft'` only together with `preview: true`** — a device route (`/pos-api/config`) must never pass a menu version, and a new preview kind must carry its choice in its signed link or stored row (never a query parameter beside the token, which anyone holding a published preview link could flip). Anything a preview shows from the menu must come through `tillMenus(..., version)` so the editor's switch reaches it; option groups are tenant-wide and live in both versions, which is why a flavour picture shows in the preview before publishing and a dish photo doesn't.
- **Menus made from files go through `createMenuFromSections()` only** — the import route and Pepper's create_menu share the plan (tag matching, option groups, the whole-tree save), so a menu read from files can't hold another tenant's tags or groups and never creates tags. Don't save the reading's answer straight into the menu tables, and keep `POST /read` free of writes (the person reviews first).
- **An option group copy copies columns generically, but ids inside them aren't remapped** — `POST /api/menus/variant-groups/:id/copy` inserts every `menu_variant_groups` / `menu_variant_options` column but the id and timestamps, so a new plain column comes along without a code change; a new column holding the id of the group itself or of its options (like `child_group_id` asking the group itself) must be remapped in that route, and a new `menu_translations` key kind for groups or options added to its key list.
- **What guests see as an option group's name is its display name, and only two places supply it** — a published menu holds it as the attached group's `name` (`shownGroup()` in `releaseContent()`), and the live group library is selected as `COALESCE(display_name, name) AS name` (`tillConfig()`, `kioskConfig()`, the translation sources). A new guest-facing reader must load menus through `loadMenuVersion(s)` (drafts for guests get `withShownGroupNames()`) or select the library the same way; reading `menu_variant_groups.name` or `loadMenuFull()` for guests shows staff names like Flavour x2 (copy). Staff pages (the Menus editor, Variant groups) keep the name with `display_name` beside it: `GET /api/menus/:id` reads `loadMenuFull()` straight for that reason.
- **What suits a kiosk guest's allergens and diets is decided only by `guestFit()` / `countFits()` in `shared/kiosk.js`** — the allergens screen's count, the menu's marks, the dish page and meal deal choices all go through it (`fitOf()` / `countFor()` in `store.js`), so a new place that shows or filters dishes for the guest's picks must call it rather than read `item.dietary` itself, or it will disagree about may contain (doesn't suit), can be removed (suits, with a note) and meal deals (judged by their required steps' choices, not the union of every dish). The picks live only in the kiosk's state: never send them to the server or keep them past `restart()`.
- **A Zod `.default()` on a field the code falls back for with `??` makes the fallback dead code** — the menu tree schemas had `sort_order: z.number().int().default(0)`, so `upsertMenuTree()`'s `item.sort_order ?? ii` never numbered anything by position and every dish sent without one tied at 0. Use `.optional()` where the handler has its own fallback. And never let a test (or a screen) read "the first" of rows whose order the query leaves open: `json_agg(DISTINCT jsonb_build_object(...))` orders by the jsonb, which compares the `id` key first, so ties come back in random-id order and a test that reads `items[0]` passes or fails by chance (the CI failures of 23-24 Oct 2026). Pick test data by id or name, and give every ORDER BY a unique last key.
- **A combo part's options come only from `dealItem()` / `partChoices()` (till, kiosk) or `partOptions()` (online), never from `part.pos_choices`, `posChoices(part)` or `choicesOf(part)` directly** — a dish or section choice in a combo step can change what its dish asks inside the deal (`option.groups`: left out, only some options, another group, how many), and the pricing applies those changes (`priceCombo()` hands the choice's groups to `partPrice()`). A new place that shows, picks or prices a combo part (a receipt preview, a Pepper tool, a new display) must find the step choice the pick came from (`sameChoice()` / matching `option_id` + `item_id`) and go through those helpers, or it offers options the pricing then refuses (BBQ in a deal that offers three flavours) or misses a swapped group entirely. Code that matches separate dishes to a deal must check `dealFits()`, and anything that turns a dish's picks into a deal's must trim them with `picksWithin()`.
- **A combo part's options must be asked with `askedChoices()` and priced or shown with the deal's own picks filled in (`withDealPicks()` / `fillDealPicks()`)** — `dealChoices()` keeps a group the deal leaves one option in, marked `fixed`, so code that renders `part.pos_choices` / `partOptions()` as they are asks the guest a question with one answer, and code that reads only the guest's picks (a part page's "complete" check, a picture, a summary) misses the deal's pick. Pricing fills it itself (the part callbacks of `priceItem()` / `priceLine()`), so never strip `fixed` groups before pricing, and never compute a part's options or picks outside these helpers. A new rule for when a group is fixed goes in `fixedPicks()` only.
- **A whole-tree save must send back data the page doesn't edit, never an empty list for it** — the Menus page "retired" a dish's own options by sending `variants: []` on every save, but other writers (the sample menu seeds, imports, the API, Pepper's `menuSaveBody()`) still made them, and the PATCH rewrites the whole tree, so every save deleted them and, through `cleanDealGroups()`, the meal deal rules that referred to them. Before declaring a field retired, grep every writer; while any remains, the page must pass it through (and show it, or nobody knows it is there).
- **A dish's option price inside a meal deal comes from `dealChoices()` only** — a group with deal `prices` is turned into an extra group there, so a new surface that reads `part.pos_choices`, `choicesOf(part)` or the library group's own `price_mode` / option prices to show or charge a deal part gets the dish's prices instead of the deal's (and a base group's options read as dish prices, not "+£" charges). Go through `dealItem()` / `partChoices()` / `partOptions()` (as the deal options entry above says) and show prices with `optionPriceText()`, which reads the choice's `mode`.
- **Ids kept in a uuid array (no foreign key) must be removed when the row they point at is deleted, and a settings page must only send back ids it shows** — Ordering setup kept a deleted menu's id in `ordering_settings.menu_ids`, didn't show it, sent it back on every save, and the route's own-menu check refused it ("A chosen menu wasn't found"), so the page could never save again (live report, 30 Oct 2026). Deleting a menu now runs `forgetMenu()` (`routes/menus.js`) over every array that holds menu ids (ordering settings and menu times, revenue streams, Deliveroo settings; since migration 230 menu times are `menu_times` rows that go with the menu by foreign key), and the ordering and Deliveroo reads return only the menus their pages list. A new column holding a list of another table's ids needs the same: clean it where those rows are deleted, filter it on read, and add it to `forgetMenu()` if it holds menu ids.
- **When a menu is on comes only from `menu_times` through `channelTimes()` (`shared/menuTimes.js`, migration 230), and which menus are online only from `ordering_settings.menu_ids`** — online ordering reads `webSchedules()`, the till and kiosk configs `tillMenuData(..., { channel })`. A new channel or a new place that shows menus at a time (a table QR page, Pepper, a report) must read its cell through `channelTimes()` (a schedule, null = any time, false = off), never `row.times` alone (that ignores Any time, Own times and Off) and never a schedule of its own. A menu with no row is on at any time on tills and kiosks: read `channelMenuTimes()` with `?? null`. Never store a web cell as off: `menu_ids` says that, and the PUT keeps the cell's times for when the menu goes back online.
- **A tap that switches a till's menus goes through `switchMenus()` (`shared/menuTimes.js`) and `useShownMenus()`'s `pick()` / `follow()`** — a result equal to what the menu times show must become `follow()`, or the till keeps a pick that lapses only when the menus on now change, and its Menu times button stays unlit while the screen shows exactly the times' menus. A new way of switching (a Pepper action, a kiosk staff switch, another zone) must reuse them rather than write `prefs.menu_pick` itself.
- **A test of what a release holds must read `menu_releases.snapshot` from the table, not `loadMenuVersion()` in the same process** — `services/menuReleases.js` caches each release's content by id when it is inserted (`remember()`), so a test that reads the live version back gets the content the code meant to store, never what was stored (a mutation that saved the whole draft passed until the allergen publish test read the snapshot). Other API processes read the table: a wrong snapshot shows there.
- **Publishing part of a draft must start from the live release, never the draft** — `publishAllergens()` builds its release with `withDraftTags(live, draft)`, which takes only dish tags from the draft; a new partial publish (prices only, one section) must do the same and must lock the menu rows first (`FOR UPDATE`, in id order when several), as `publishMenu()` now does, or a full publish landing in between is undone by a release made from the old live content. Scheduled releases made before must get the same part too (copy and cancel, never UPDATE a snapshot), or they bring the old values back when they go live.
- **`setSearchParams(next, { replace: true })` drops `location.state` unless it is passed again** — the menu print designer writes `?design=<id>` into its address once it knows which design is open, and that navigation replaced the history entry without its state, so "opened from the menu editor" (`state.from === 'menu'`) was gone a moment after arriving and Back said Designs instead of Menu. Pass `state: location.state` to every `setSearchParams()` / `navigate()` that only changes the query, and read state that decides something for the whole visit once at mount (`navState` in `MenuDesigner.jsx` is a ref). A browser check of such state must wait until the page has settled its address before asserting.
- **A place that shows the allergen lookup is gated by the `allergens` module, not `menus`** (migration 258) — the page, the dashboard widget (`WIDGET_MODULE`), the Overview tile (`TILE_MODULE`), the phone tile (`module` in `mobile/registry.js`) and Pepper's `find_dishes` (its own `modules`) all take Allergen lookup, so front-of-house without Menus can answer an allergy question. A new one must do the same, read the live version only, and never offer the matrix or a write without Menus.
- **What an item is comes from `itemType(item, section, menu)` in `shared/catalogue.js`, never from one level's `item_type`** (22 Nov 2026, migration 267) — a dish's `item_type` is null when it follows its section, a section's when it follows the menu, and a release published before migration 267 has none at all (food). Read the resolved type, and ask `needsAllergens()` / `showsInKitchen()` instead of comparing with 'food', so a fourth type later changes one table. A new place that shows allergens, diet tags or calories, or sends dishes to the kitchen, checks it. `releaseContent()` drops a menu's type when it is food so older releases stay in step with their draft: keep that when touching the release shape.
- **Guests and devices get resolved types from `loadMenuVersions()`, the admin and the publish diff get them as stored** (22 Nov 2026) — `loadMenuVersions()` runs `resolveItemTypes()`: every item's `item_type` is its resolved type, and a non-food item comes with no `dietary`, `allergen_levels` or `calories`. `loadMenuVersion()` (one menu) doesn't, because `publishStatus()` compares it with the draft and a stripped copy would never be in step; a reader that loads one menu for guests calls `resolveItemTypes()` itself (the print and public menu loaders, the live allergen matrix do). A shape built from those items for a device (`posSvc`, `orderSvc`) passes `item_type` on.
- **An option's own codes live in `menu_item_option_codes`, never in `menu_item_variant_prices`** (22 Nov 2026, migration 268) — a row of the prices table means "this dish's own price" to the editor (`overridesOf()`), the report subject Dish option prices and the release; codes-only rows there would read as prices. A dish's `option_codes` is left off when it has none (an empty list would put every older release out of step with its draft), and every save runs `codeProblems()` (the API refuses with 422; the Menus page holds Save). Product codes compare in lower case.

- **Another area that changes menu prices goes through the menus routes and the whole-tree save, never the tables** (27 Nov 2026, inventory phase 7a) — Push prices (recipes' `routes/costScenarios.js`) loads `GET /api/menus/:id`, changes prices with `pushPrices()` (`shared/scenarios.js`) and PATCHes `menuSaveBody()` of the result in-process as the person, so every field and Menus manage hold. A dish's price lives on that menu's dish (no venue, stream or order type price); a dish priced by its options gets them as its own prices (`overridden`), never the library option's. A new field on a dish must still be in `menuSaveBody()` or Push prices drops it.
- **The allergen matrix's `PUT /:id/allergens` has a caller outside the menus area: the Recipes page's allergen check** (27 Nov 2026, inventory phase 8a) — `POST /api/allergen-checks/dishes/:id/accept` GETs the draft matrix and sends one dish's whole `levels` (every tag id, dietary tags too) through `callApi()`. A change to the route's body (a new field per item, tag ids becoming codes, `publish` meaning something else) changes what accepting a difference does; run `api/test/allergen-checks.test.mjs` with the menu tests. Guests' allergens (Pepper's `find_dishes`, the lookup, print, ordering) stay the live release's until someone publishes.
