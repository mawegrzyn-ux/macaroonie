## Mistakes to avoid

> Append-only: never delete an entry, only correct one that turns out to be wrong. New entries go at the end.

- **A printed page box as tall as the paper gives a blank sheet after every page on a real printer** — `@page { margin: 0 }` only removes the browser's margins; many printer drivers keep a few mm of their own, so the page area is shorter than the paper and a paper-height `.page` / `.ml-page` spills its empty bottom strip onto a new sheet (PDF export never shows it, which is why it slipped through). Size print pages with `100vh` / `100vw`, which Chromium resolves to the printable page area, not with the paper's mm height. The designed print also translates `.ml-content` by half the difference so the design stays where it was placed on the paper. Reproduce by adding `@page { margin: 5mm }` and counting PDF pages.
- **A web page can't print to a network printer or reach the venue LAN freely** — no raw TCP from a browser, an `https` page may only call `https`/`wss`, and Chrome asks permission before a public site talks to a LAN address. That's why the POS prints through the venue hub (`hub/`) and why the hub's address and certificate scheme matters (`docs/POS.md` §2.1). Don't plan POS features that assume the till itself talks to printers or other tills directly.
- **A printed ticket is drawn only by `kitchenTicket()` / `receipt()` in `shared/pos/tickets.js` from a layout (`shared/pos/ticketLayout.js`)** — the till's browser print, the hub's ESC/POS, the sequencer's print jobs and the designer's preview all go through them, so a new place that prints (a reprint, a report slip) must pass the venue's layout (`cfg.layouts` / config `print_layouts`) or it ignores the design. A new block type needs `BLOCK_TYPES` (options and defaults), `cleanOpts()`, its drawing in `tickets.js`, `blockSummary()` and `BlockOptions` in `PrintDesigner.jsx`; one with words a venue can change also needs `TEXT_KEYS`. Keep `defaultLayout()` drawing exactly the old tickets (the shared test compares them).
- **Every print job's printer must exist when the sequencer saves it** (`pos_print_jobs.printer_id` references `pos_printers`): a job for a deleted printer fails the event's whole transaction. Deleting a printer clears it from kitchen printer boxes and devices' receipt printer, and `loadKitchenConfig()` / `printConfig()` drop ids of printers that are gone or switched off. Anything else that stores a printer id must be cleared the same way.
- **A print job is collected by whoever prints its printer, and only the collector reports on it** (`POST /pos-api/print-jobs/claim`: the hub takes `connection = 'hub'` printers' jobs, a till or kitchen screen its own `device` printers'). A new device kind that prints must be added to the claim's kinds and its config must carry its printers (`tillConfig()` and `kdsConfig()` do); never let any device mark another's collected job printed.
- **The hub's code reaches mini PCs only through `hubRelease()`: a file the hub needs must be imported (statically or with `import('./...')`) from `hub/bin/*.js`** — `importClosure()` follows relative imports to decide what goes in the release; a file read any other way (`fs.readFile` of a sibling, a path built from strings) isn't shipped and the installed hub breaks after the next update while the repository copy works. Any change to `hub/` or the shared files it imports is a new version that every hub installs by itself at its next quiet moment, so run `node hub/bin/hub.js --self-test` and `node --test hub/test/*.test.mjs` before merging; a change that passes the self test but stops at start is rolled back on each hub and held back (Update now retries it).
- **A hub must never exit on a refusal it can recover from** — the launcher counts quick stops and goes back a version after three, so an unlinked hub (401) or an unreachable cloud must keep running (showing a new code, retrying), not `process.exit(1)`.
- **A USB printer on the hub is found by its id at every print, never by its device file** — `/dev/usb/lp0` and `lp1` swap when printers are plugged in another order; `local_id` (usb:vendor:product:serial or port, or win:name) is what Till setup stores. Status questions and tickets to one printer go through the same queue (`queued()` in `usb.js`), or a DLE EOT can land inside a ticket's command.
- **`hub/install/setup.cmd` is run by cmd.exe, which forgives little** — it is served with `\r\n` line endings (`installScript('cmd')`) and must stay plain ASCII; nothing it calls may pass a path or argument by pasting `%~f0` / `%~1` into PowerShell code (a downloaded file named "macaroonie-hub-setup (1).cmd", or an apostrophe in a user name, breaks it): hand them over in environment variables, as it does. Don't add `rem` lines or unquoted `(` `)` inside an `if (...)` block. Whether the install worked reaches it only through `$global:MacaroonieHubFailed`, set by `install.ps1`'s last line; a change there must keep setting it. `install.ps1` must stay plain ASCII too: the setup file runs it from a downloaded file, and Windows PowerShell 5.1 reads a file without a byte-order mark as ANSI.
- **Code in `pos/` that a WebView can't run must go through the app bridge (`pos/src/lib/nativeApp.js`)** — inside the Android app (`android-app/`) `window.print()` does nothing, new windows don't open and pages on other domains are refused, so a feature that prints, opens a tab or sends the device elsewhere needs a branch on `IN_APP` that posts a message (`tellApp()`) and a case in `android-app/App.js`'s `onMessage`. A new message type changes the shell, which only reaches devices with a new EAS build: keep the web side working when the app doesn't answer (older builds ignore unknown types). Navigating the WebView to another device address is fine: the app follows and remembers it.
- **Code that must run inside the Android app's web page is a string (`CORNER_SCRIPT` in `android-app/corner.js`), never `fn.toString()`** — the app runs on Hermes, which keeps no function source (`toString()` gives `[bytecode]`), so a script built from a function works in Node and the tests and does nothing on the device. Write the page side as a string, keep any native copy of the rule beside it, and test both with the same inputs (`android-app/test/corner.test.mjs`). Positions in the page are CSS pixels: divide dp by `visualViewport.scale` (the kiosk zooms through the viewport tag); Playwright's taps are in CSS pixels too, so a test of a zoomed page must convert.
- **The Android app's dependencies come from `expo/bundledNativeModules.json`, never `npm install <pkg>@latest`** — a native module of another version builds but crashes on the device; `npx expo install` is the usual way but needs the Expo API (blocked from the build environment), so read the version from that file and pin it (exact for non-expo packages, `~` for expo-*). `android-app/package-lock.json` is committed on purpose (EAS installs from it): don't remove the root .gitignore's exception.
- **At a hub-first location a device's event can be decided twice, first by the hub and then by the cloud (migration 218): both must reach the same answer from the same rules** — a check rule, a permission or a number rule that exists only in the cloud's code (a route handler, the Postgres store) makes the hub accept what the cloud then refuses (a conflict a manager must sort out). Rules go in `shared/pos/checks.js` / `sequencer.js` / `deviceRules.js`, which both run; anything the sequencer's store reads must be in the hub's context (`hubContext()` in `services/hubFirstSvc.js`) and kept in the mirror. Events that need a cloud-only service (card machines, loyalty) must be named in `needsCloud()` (`shared/pos/mirror.js`) so the hub passes them through instead of deciding them.
- **A device call the venue hub answers must be in `HUB_PATHS` (`pos/src/lib/transport.js`) and in `hub/src/lan.js`, with the same request and reply shape as the cloud's route** — the device code doesn't know which one answered. A call missing from the hub's server 404s on the hub and falls through to... nothing: `viaHub()` only falls back to the cloud on no answer, 409 or 401, so a 404 reaches the screen as an error. Anything else (config, prices, card machines, loyalty, receipts) stays cloud-only and must not be added to `HUB_PATHS`.
- **The hub's own setting changes reach it only when it reloads its set-up (every 30 s, or when a device it doesn't know calls)** — a change in the admin (hub first, a PIN, a printer, a menu price) reaches devices by `pos.config` at once but the hub's decisions up to 30 s later. Don't build anything that assumes the hub knows a change the moment it is saved; test with a wait for the hub's report (`info.mirror`, `info_at` after the change), not a fixed sleep.
- **The admin build doesn't catch a component or icon that is used but not imported** — JSX `<Check />` with no `Check` in scope builds fine and throws `Check is not defined` only when that part renders (it crashed the Printers window's USB list after the hub parts moved to `HubSection.jsx` and the icon import went with them). After moving components between files, open every page and window that renders them (the browser checks do), not just `vite build`.
- **One computer is one venue hub: a new link starts with nothing of the last venue** — `forgetVenue()` (`hub/src/link.js`) deletes everything in `VENUE_FILES` beside hub.json whenever the link ends (unlink, removed in Store tech, a new link), and venue.log lines carry the hub id so another hub's events are never replayed. A new file the hub keeps for its venue must be added to `VENUE_FILES`, or a second restaurant linked on the same computer inherits the first one's data. Never delete a linked hub's files with sales still to send: `unlink()` uploads first and refuses (exit 2) while the cloud can't take them.
- **On Windows, ending a scheduled task ends only the process it started** — the hub's launcher, not the hub it runs, which kept both ports and the old link beside the new copy (live report, 31 Oct 2026). Stop a hub with `Stop-Hub` (every node.exe whose command line has the hub's folder) in install.ps1, never by matching the launcher alone; the hub also exits by itself when `MACAROONIE_HUB_LAUNCHER_PID` is gone.
- **The Windows service program (`hub/install/HubService.cs`) must stay C# 5 and plain ASCII** — it is compiled on the mini PC by the .NET Framework 4 csc.exe, which knows no `$""`, `?.`, `nameof` or `=>` members, and it travels inside install.ps1 (a single-quoted here-string the API fills in, which ends at a line starting with `'@`; Windows PowerShell reads a file without a byte-order mark as ANSI). Check a change with `mcs -langversion:5 -sdk:4.5 -r:System.ServiceProcess.dll`, and run the Windows check (`hub-windows.yml`) before merging: nothing else compiles or runs it. A process the service starts must go through its job object (`Start()`), or stopping the service leaves it running.
- **In install.ps1, a native program run while `$ErrorActionPreference` is Stop can end the install** — Windows PowerShell 5.1 turns anything it writes on stderr into an error once redirected (`2>&1`). Run csc.exe, sc.exe and powercfg.exe in a function that sets `$ErrorActionPreference = 'Continue'` (as `Install-HubService` and `Set-HubPower` do) and judge them by `$LASTEXITCODE`; cmdlets in such a function need `-ErrorAction Stop` to still throw. Passing a value with embedded quotes to a native program is unreliable in 5.1: change a service's path with `Win32_Service` `Change`, never `sc.exe config binPath=`.
- **The hub's printer bytes depend on the printer's language: render through `render(ops, { cols, language: p.language })`, never `render(ops)` alone** (migration 254) — a Star printer in Star Line Mode has no GS commands and prints each as text (a ! and a B on every line), reads ESC/POS's `ESC a n` as a paper feed and `ESC d n` as a cut, and misreads Epson's DLE EOT status question. A new way the hub prints or asks a printer how it is must pass the printer's `language` through, and a new print operation needs a command in both `CMD` and `STAR`.
