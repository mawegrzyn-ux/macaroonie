## Admin portal design principles

The admin portal is **optimised for tablet-sized touch screens** used by front-of-house staff at a host stand or service counter. Design decisions must reflect this:

- **Touch targets minimum 48 × 48 px** — buttons, covers selectors, slot tiles, grip handles
- **`touch-manipulation` CSS on every interactive element** — eliminates 300 ms tap delay on iOS/Android
- **No hover-only affordances** — every interactive element must be discoverable and usable by tap
- **`type="tel"` / `inputMode="tel"`** on phone number inputs — triggers numeric keypad on iOS/Android tablets without custom code
- **Custom numeric keypad** for covers/number inputs on touch devices — `inputMode="none"` suppresses native keyboard; a 3×4 grid overlay is rendered instead. Detection: `navigator.maxTouchPoints > 0` evaluated once at module load as `IS_TOUCH`
- **Date as a styled button with invisible `<input type="date">` overlay** — tapping the label opens the OS date picker on mobile, and a native datepicker on desktop; avoids custom calendar components
- **Minimum 1015 px wide layout assumed** — sidebar + timeline must remain usable at that width without horizontal scroll inside panels
- **All modals scrollable** — use `max-h-[85vh] overflow-y-auto` on modal content areas so content does not clip on smaller tablet screens in landscape

When adding new UI: always verify interactive elements are finger-sized, add `touch-manipulation`, and test at 1015 px width.

## Mistakes to avoid

> Append-only: never delete an entry, only correct one that turns out to be wrong. New entries go at the end.

- **`sidebarExpandedDefault` only controls initial state** — it initialises the `open` state in AppShell's `useState`. Subsequent manual toggles work normally per-session. Mobile always starts collapsed regardless of the setting. Touch devices (see the `IS_TOUCH` entry below) ignore this setting entirely and always start collapsed, since they get the phone-style sidebar treatment regardless of screen width.

- **A change that ships something Help or Docs listed as still to come must change those lines in the same change: grep both pages for "Still to come", "Not built yet", "comes later" and the feature's own words** — Help's Reports box listed rota pay and tips, Cash Recon, menus, reviews and reports about two things at once as still to come through the four pull requests that built them (phase 3a to 3d), Docs' Not built yet box and its limits ("one subject per report") did the same, and Help's kitchen screens section said the venue hub comes later two weeks after Hub first shipped. Nothing fails when such a line goes stale: the end-of-phase browser re-run found them only because an old check looked for an older line. A docs check that reads a "still to come" line should name what is still to come, so it fails when that ships.
- **Task notices go only to people who can act on the task, judged on their own levels** — the feed is worked out once as the group's owner (every area), so `wants()` (the person's settings and `permissionAtLeast(levels[module], workLevel(module))`) is the only thing between a task and someone who mustn't see it. A new notice kind or source must go through it, and must claim its `task_notices` row before sending, or overlapping sweeps and several API processes send it twice.
- **The Office app's bridge answers only our pages** (`bridgeAllowed()` in `office-app/links.js`): the access token goes to any page that asks, so a new bridge call that hands over something private must keep that check, and the web view must keep other hosts out (`staysInApp()`), opening them in the browser.
- **Inside the Office app the pages sign in through `OfficeAuthProvider`, which fills Auth0's own context** — a page that calls Auth0 some other way than `useAuth0()` (a direct `@auth0/auth0-spa-js` client, a redirect of its own) breaks there. Anything new about sign-in must work through the context.
- **Android draws Expo apps edge to edge (always, from SDK 54): a native shell must keep its content out from under the status bar, the navigation buttons and the keyboard itself.** The Office app's web view sits inside `useSafeAreaInsets()` padding plus the keyboard's height from `keyboardDidShow` (React Native gives it less the navigation bar, so add `insets.bottom`); nothing resizes the window for the keyboard any more. The status bar's icon colour follows the page under it (`StatusBar style="dark"` over white pages). Overlays (the scanner) pad themselves too.
- **A new Help or Docs section is a new file, `admin/src/pages/help/<id>.jsx` or `admin/src/pages/docs/<id>.jsx`, exporting `id`, `label`, `order` (a plain number literal) and `Section`** (22 Nov 2026) — `Help.jsx` and `Docs.jsx` gather every `.jsx` in their folder but `parts.jsx` and sort by `order`, then id, so pick an order between the two sections it belongs between (orders are spaced by 10) rather than renumbering others. Pepper's help index reads the Help files as text and takes the order from `export const order = N` with a regex: a computed order sorts the section last for Pepper while the page shows it elsewhere. Helpers go in the folder's `parts.jsx`; any other file there is taken for a section.
- **A new admin page's menu entry is one record in its area's `shared/nav/<area>.js`, and a new area's file must be added to the imports in `shared/nav/index.js` by hand** (22 Nov 2026) — `shared/` runs in Node and Vite, so `index.js` can't gather the folder; `shared/test/navPages.test.mjs` fails while a file in the folder is left out. Give the record a `section` from `sections.js`, an `order` among its section's (or parent's) links and a `catalogOrder`, both spaced by 10 so a new page slots in without renumbering (ties go by path). A migration that adds the link to menus already saved is still needed (rule 21).
- **A page that reads a deep link (`useDeepLink()`, `admin/src/lib/deepLink.js`) must call it after its own "first venue" default effect, and must hold a day back until its venue is on screen when changing venue resets the day** (22 Nov 2026) — effects run in the order the hooks are called, and a default written as `if (!venueId && venues.length) setVenueId(venues[0].id)` reads the render's old `venueId`, so declared after the link's `apply` it overwrote the link's venue in the same commit. Online orders resets its day to today at the venue whenever the venue's time zone changes, which would throw away the link's day: it keeps the day in a ref (`linkDay`) and sets it in an effect declared after that reset, once the link's venue is the one shown. `apply` only sees shapes (`shared/nav/links.js`): it must check the venue is in the page's own venue list. A new deep-linked page needs `accepts` (and `tabs`) on its record in `shared/nav/<area>.js`, or `pageLink()` drops everything for it.
- **The usage record keeps a page's path only, and a person's record stays their own** (22 Nov 2026, migration 270) — `usagePath()` (`services/usageRecord.js`) drops the query string and turns every id-like part of the address into `:id`; send it `location.pathname`, never `location.search` or a full URL, and never add a column for what a page showed. Group-wide figures must carry no person: a new field, figure or link on `usage.pages` / `usage.searches` that reads `user_sub` (or the words typed) is a ranking of people (decision 8 of the Pepper-first strategy); a person's own rows go only through `usage.mine`, whose rule reads `{me}`. A new place that asks Pepper from a search box calls `useSearchUse()` (`lib/usage.js`) so its searches count, and every list of results calls `onPick(route)` so the record knows what was opened.
- **Pins are each person's own and only pages of their own menu: read and save them only through `/api/pins`** (22 Nov 2026, migration 272) — the route keeps `user_sub` from the login and checks every path against `navTreeFor()` (the menu /api/me sends), so a new place that shows or adds pins (a star on a search row, the phone hub) must call it rather than write `home_pins`, and must send back the whole list in the order shown: `PUT` replaces it (rule 13). A pin's venue and tab go through `cleanPin()` / `pageAccepts()`: a page that starts taking a venue needs `accepts` on its record, not a change to the pins code. Nothing may read another person's pins (decision 8): no report subject covers the table.
- **`/` is Home, for everyone: never give its record a module, and link to the Overview as `/overview`** (22 Nov 2026, migration 273) — Home is where every sign-in lands, so a module on its record (or on a group's menu link through a migration) would hide it from a custom role that doesn't name that module, the same trap migration 227 fixed for Today. `api/test/nav-default.test.mjs` lists `/` as the only page with no module. Code that meant the Overview by `'/'` (a migration's anchor, a test, a link) now means Home: 243's anchor list (`'/dashboards', '/'`) puts Reports after Home on a menu with no Dashboards link. A notice, a redirect or a stand-in that should open the day's tasks opens `/` (on the phone pages `/mobile/today`).
- **The ask bar's results come only from the browser: never put a model call, or a request that waits on one, between a keystroke and the list** (22 Nov 2026, Pepper-first step 2c) — every page jump with a local match must cost no model call (the step's measure), and the bar must work with Pepper off. A new kind of result (records, contacts) is searched locally or by a plain API route; only Enter with no row lit, the Ask button, the Ask Pepper row or an ask under the bar hand words to Pepper. A new place that hands words to Pepper goes through `askPepper()` from `useAsk()` (a new chat in the drawer), never its own chat, and calls `useSearchUse()` like the bar.
- **A key handler on a box inside the shell must not stop Escape it doesn't use** (22 Nov 2026) — React's `stopPropagation()` stops the native event too, so the drawer's window listener never saw Escape while the cursor was in Home's empty bar, and Pepper's drawer couldn't be closed from the keyboard. The bar stops it only when it clears its words or closes its own window.
- **A window opened from inside a page's card must be portalled to `document.body` (`createPortal`)** (22 Nov 2026) — the pins editor is drawn from `PinStrip`, which sits inside cards on Home and in an Overview tile; portalled, its backdrop and focus order don't depend on what the card's ancestors do (overflow, stacking). Check a new window with `document.elementFromPoint()` over the menu, not by eye: a dimmed screenshot is easy to misread.
- **A test that replays an old migration's SQL breaks when a later migration drops a column it writes: rewrite the replay, never the old migration** (22 Nov 2026, migration 274) — `nav-default.test.mjs` runs 241's DO block and 243's menu insert on today's schema, and both still insert `show_in_launcher`; `noLauncher()` takes the column (and its `false`) out of the text before running it. A migration that drops a column must grep `api/test` for SQL read from `migrations/` (`readFileSync(...migrations...)`) and for the column's name, and a migration test that needs the dropped column (274's own) adds it back for the run.
