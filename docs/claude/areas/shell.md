# App shell, navigation, mobile, Today

Covers: AppShell and the sidebar, the navigation designer and menu search, the launcher, Settings, the phone app (/mobile, ops.), Today, platform hosts, shared UI parts, the in-app Help and Docs pages.

Key files and mistakes to avoid for this area: read it before changing code here. What shipped and when is in `docs/claude/history/shell.md`; the index of all areas is in `CLAUDE.md`.

## Key files

Under **API**, `src/...` means `api/src/...`; under **Admin portal**, `src/...` means `admin/src/...`. Other paths are from the repo root.

### Admin portal

- `src/components/PageErrorBoundary.jsx` — wraps the page outlet in `AppShell` and `MobileShell` (keyed by path): a page that throws while rendering shows "This page stopped working" with the error and a Reload button instead of blanking the admin.

- `src/components/MobileSuggestModal.jsx` — mounted at the bottom of `AppShell` (desktop shell only, never rendered under `MobileShell`). Detects a touch device in portrait at ≤700px (`IS_TOUCH && matchMedia('(max-width: 700px) and (orientation: portrait)')`, checked on mount and on an `orientationchange`-driven media-query listener so a mid-session rotation into portrait also triggers it) and offers a big modal pointing at `/mobile`. Dismissing either button (Open mobile view / Stay on this page) sets `maca_mobile_prompt_dismissed` in localStorage — offered once per browser, never nags again.
- `src/components/MobileViewToggle.jsx` — persistent floating pill button, bottom-left, shown any time the viewport matches `IS_TOUCH && matchMedia('(max-width: 700px)')` (no portrait requirement, no dismissal — unlike `MobileSuggestModal` above, this is an always-on toggle rather than a one-time nudge). Takes a `target` prop (`'mobile'` or `'standard'`) and navigates to `/mobile` or `/` respectively. Mounted twice: `<MobileViewToggle target="mobile" />` in `AppShell.jsx` (next to `MobileSuggestModal`), `<MobileViewToggle target="standard" />` in `MobileShell.jsx` (after `<Outlet />`) — the latter is the only way to get from `/mobile/*` back to the full desktop admin without editing the URL by hand.

## Admin portal design principles

The admin portal is **optimised for tablet-sized touch screens** used by front-of-house staff at a host stand or service counter. Design decisions must reflect this:

- **Touch targets minimum 48 × 48 px** — buttons, covers selectors, slot tiles, grip handles
- **`touch-manipulation` CSS on every interactive element** — eliminates 300 ms tap delay on iOS/Android
- **No hover-only affordances** — every interactive element must be discoverable and usable by tap
- **`type="tel"` / `inputMode="tel"`** on phone number inputs — triggers numeric keypad on iOS/Android tablets without custom code
- **Custom numeric keypad** for covers/number inputs on touch devices — `inputMode="none"` suppresses native keyboard; a 3×4 grid overlay is rendered instead. Detection: `navigator.maxTouchPoints > 0` evaluated once at module load as `IS_TOUCH`
- **Date as a styled button with invisible `<input type="date">` overlay** — tapping the label opens the OS date picker on mobile, and a native datepicker on desktop; avoids custom calendar components
- **Minimum 1015 px wide layout assumed** — sidebar + timeline must remain usable at that width without horizontal scroll inside panels
- **All modals scrollable** — use `max-h-[85vh] overflow-y-auto` on modal content areas so content does not clip on smaller tablet screens in landscape

When adding new UI: always verify interactive elements are finger-sized, add `touch-manipulation`, and test at 1015 px width.

## Mistakes to avoid

> Append-only: never delete an entry, only correct one that turns out to be wrong. New entries go at the end.

- **`sidebarExpandedDefault` only controls initial state** — it initialises the `open` state in AppShell's `useState`. Subsequent manual toggles work normally per-session. Mobile always starts collapsed regardless of the setting. Touch devices (see the `IS_TOUCH` entry below) ignore this setting entirely and always start collapsed, since they get the phone-style sidebar treatment regardless of screen width.
- **`AppShell`'s sidebar treats ALL touch devices like phone-width, never the `lg:` desktop icon-rail/push-content mode, regardless of actual screen width** — `IS_TOUCH` (`navigator.maxTouchPoints > 0`, same pattern as `NewBookingModal.jsx`/`MobileViewToggle.jsx`) gates every `lg:` class that previously assumed "wide screen = mouse-driven desktop": `open` starts `false` unconditionally, the collapsed aside is `w-0` (never `lg:w-14`, the icon rail), the aside never gets `lg:relative` (stays a `fixed` overlay that never reserves permanent layout width), and the floating hamburger button's `lg:hidden` is dropped so it stays visible and usable at any width. This exists because landscape tablets (an iPad landscape is ~1024px, right at the `lg` breakpoint) were getting the desktop treatment — a permanently-expanded or icon-rail sidebar eating screen width — even though front-of-house staff hold and tap a tablet like a phone, not a laptop with a mouse. Every future `lg:` class added to `AppShell.jsx` for sidebar open/collapsed behaviour must be paired the same way (`!IS_TOUCH && 'lg:...'`) or a touch tablet will silently regress back to desktop chrome.
- **`tenants.nav_style = 'launcher'` hides the ENTIRE sidebar tenant-wide, and `nav_items.show_in_launcher` defaults to `false` for every item** — switching a tenant into Launcher mode before an admin has flagged at least one nav item as a quick-access tile leaves every user (including the admin) with no sidebar. The Nav Designer's Sidebar/Launcher toggle is the way back. **Correction (same day):** the escape hatch was first added only to `/launcher`'s empty state, which meant a tenant with even ONE tile configured had no way back — reproduced live in production. Fixed by moving "Back to full menu" into the page header, always visible whenever `nav_style === 'launcher'` and the viewer has `nav_designer:manage`, regardless of tile count. Don't gate a nav escape hatch on any content-dependent condition — it needs to be unconditionally reachable or it isn't an escape hatch. (Corrected 22 Nov 2026, migration 274: launcher mode, `nav_style` and `show_in_launcher` are gone. The lesson stands for any mode that hides the menu.)
- **Dashboard's `SHORTCUT_OPTIONS` (the per-user Quick access widget on `/`) is a SEPARATE feature from the Navigation designer's Launcher** — they're both called "quick access" in normal conversation, which is confusing. `SHORTCUT_OPTIONS` is a hardcoded catalog in `Dashboard.jsx` that every user picks their own subset from, always available regardless of `nav_style`. The Launcher (`/launcher`) only exists when `nav_style = 'launcher'`, only shows links an admin flagged in the Nav Designer, and replaces the sidebar rather than living inside the Dashboard page. (The Launcher is gone too since migration 274.) When a new top-level module ships, remember to add it to `Dashboard.jsx`'s `SHORTCUT_OPTIONS` — this was missed for Food safety, Checklists, and H&S Dashboard for a long stretch. (Corrected 22 Nov 2026, migration 272: `SHORTCUT_OPTIONS` and its local storage are gone. The tile shows the person's own pins, picked from their own menu, so a new page needs nothing there.)
- **Eta `<% %>` JS string literals need the same apostrophe-escaping as any other single-quoted JS string, but this also applies inside `DataTable`/table-row arrays in Help.jsx and Docs.jsx** — a straight apostrophe inside a single-quoted array-literal string (e.g. `'this week's list'`) terminates the string early and breaks the esbuild parse with a confusing "Expected ']' but found ..." error pointing at the apostrophe, not the actual mismatched quote. Fix: escape it (`'this week\'s list'`) — plain JSX text content (inside `<P>`/`<H3>` etc., not a JS string literal) does NOT need escaping, only literal JS string values do.
- **`/mobile` is a second route tree, not a responsive mode of the desktop pages** — `AppShell.jsx` (sidebar, ≥1015px tablet chrome) and `MobileShell.jsx` (header-only, phone-portrait) are two separate layouts mounted as sibling top-level `<Route>` trees in `main.jsx`, both inside the same `RequireAuth`/`TenantGate`. Don't try to make an existing desktop page "responsive down" into the mobile experience — build a dedicated component under `src/pages/mobile/` (reusing the desktop page's data hooks/mutations/body components, not its layout) and register it in `src/mobile/registry.js`. `MobileHSDashboard.jsx` is the reference example.
- **The `/mobile` PWA identity swap is a runtime `<link>`/`<meta>` rewrite, not a second build** — there is one `index.html` and one `vite-plugin-pwa` instance (main manifest, scope `/`). `admin/public/mobile.webmanifest` is a hand-written static file (scope `/mobile/`) that ships in every build regardless of which routes a given visitor uses; `MobileShell`'s mount/unmount effect is what actually makes `/mobile` install under a different name/icon than `/`. If you add a new manifest field that needs to differ per surface (e.g. `orientation`), edit the static file directly — there's no shared generator between the two manifests.
- **iOS "Add to Home Screen" reads `<link rel="apple-touch-icon">` + `<meta name="apple-mobile-web-app-title">` from the current page, not the manifest** — pre-17.4 Safari (and many users are still on it) ignores the Web App Manifest for icon/name purposes. `MobileShell`'s manifest-swap effect must also rewrite those two tags, not just `<link rel="manifest">`, or the installed mobile icon/name on iPhone silently stays "Macaroonie" instead of "Macaroonie Ops".
- **A structured-data feature can ship years of iteration with zero Help.jsx/Docs.jsx coverage if nobody added a section for it at the time** — the entire Menus feature (migration 048 onward: sections, dishes, variant groups, dietary tags, print, the `menu_inline` website block) had no entry in either file until the `calories`/section-image change added the first one. Don't assume "no doc gap flagged" means "no doc gap exists" — if you're about to document a small change to a feature and can't find its existing section, that's a sign to add a baseline section, not skip documenting because "there's nowhere to put it."
- **A page under `AppShell` must reserve left-side space for the fixed collapsed-sidebar hamburger button, or its own title overlaps it below `lg`** — `AppShell.jsx` renders `<button className="fixed top-3.5 left-3.5 z-10 ... lg:hidden">` whenever the sidebar is collapsed (the normal state on any viewport under `lg`, and always on mobile). A page's own header needs `pl-14 lg:pl-<normal>` (see `OrderSheets.jsx`'s `pl-14 lg:pl-4`) so its title doesn't render directly underneath that icon. `Dashboard.jsx`'s Overview header (`px-6 h-14 border-b`, no left-padding override) had this bug for a long stretch — invisible on tablet/desktop where the sidebar is normally expanded, only visible once someone actually collapsed the sidebar or opened the page on a phone. When adding a new top-level page header under `AppShell`, check it against a collapsed sidebar at phone width before considering it done — this is the same class of bug as the sticky-header-opacity entry above (correct on the common path, silently wrong on a less-common one).
- **`MobileSuggestModal` (one-time nudge) and `MobileViewToggle` (persistent floating button) solve different problems — don't conflate them** — the suggestion modal fires once per browser on first phone-portrait detection and is then gone forever (`maca_mobile_prompt_dismissed`); it was never meant to be a recurring way back into `/mobile`, and before `MobileViewToggle` shipped there was no way at all to get from `/mobile/*` back to the full desktop admin short of manually editing the URL (the `MobileShell` header's back-arrow only goes to the mobile hub, not out of `/mobile` entirely). `MobileViewToggle` is deliberately simpler in its detection (`IS_TOUCH && matchMedia('(max-width: 700px)')`, no portrait requirement, no localStorage dismissal) since it needs to be reliably present on every visit, not just once.
- **A narrowed mobile form must still round-trip every field the desktop form has, even ones it never shows** — `MobileWages.jsx` only lets an operator edit `total` and `cash_amount` per staff entry, but its save payload still includes `entry_type`/`hours`/`rate`/`notes` read straight from the loaded entry, unchanged. Omitting a field entirely from the PUT body (rather than passing its current value through) would have silently zeroed it out server-side the next time a mobile save fired — e.g. an hourly entry's `hours`/`rate` would revert to blank the moment someone glanced at Wages on their phone, even though they never touched those fields. Any "focused" mobile rebuild of a richer desktop form needs to pass every field the API expects, not just the ones the mobile UI exposes for editing.
- **A `position: sticky` page header with `z-10`+ can fully hide (and swallow taps on) `AppShell`'s fixed collapsed-sidebar hamburger button, not just visually overlap it** — the earlier "page title sits under the hamburger" bug (Dashboard.jsx, fixed by adding `pl-14`) was cosmetic: both elements were visible, just crowded together, because Dashboard's header had no competing z-index. `CashRecon.jsx`'s page headers are `position: sticky` with their own `z-10`/`z-20`, which (a) creates a new stacking context and (b) ties or beats the hamburger's `z-10`, so the header paints fully OVER the button — it disappears completely and the tap lands on the page's own header instead. This is a strictly worse failure mode than the cosmetic overlap: the user has no way to open the sidebar at all, not even an ugly one. Fixed by raising the hamburger to `z-40` (safely above every in-page header currently in the app) rather than relying on every page to keep its own header below `z-10` forever — a single high z-index on the one thing that must always be reachable is more robust than auditing every page's stacking choices. When adding a new `position: sticky` page header, keep it below `z-40` or the hamburger fix stops covering that page.
- **A pre-existing native `<select>`-styled venue/venue picker on a content page is easy to mistake for a sidebar redesign, especially when the sidebar itself is unreachable** — `CashRecon.jsx`'s `VenueSelector` (an actual `<select>` element, styled to look like a button, switching between VENUES within the current tenant for reconciliation purposes) is completely unrelated to `AppShell`'s tenant-name-in-header switcher (added the same day, switching TENANTS).
