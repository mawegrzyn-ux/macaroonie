- ✅ **Hub first: the location trades through the venue hub, with the internet down too** *(migration 218)* — the user's ask (29 Oct 2026): "hub first means we run off the hub ? ... would like to rearchitecure for hub first if hub present"; step two after per-device numbers. Design and limits in `docs/POS.md` section 11. The cloud stays the one record; at a location with a linked hub and `pos_settings.hub_first` on (default), tills, kiosks, kitchen screens and order ready boards send their events to the hub on the venue network (`http://<hub>:9181`, `Authorization: Lan <id>.<key>`, keys derived per device from the master key and its secret hash, the hub knowing only their sha256). The hub decides them over its copy of the venue (`shared/pos/mirror.js`: the cloud's state plus pending events, the same sequencer), answers at LAN speed, prints its own tickets, queues tickets for printers plugged into tills, and sends events up in order (`POST /pos-api/hub/events`, decided again by the cloud at the hub's time, `pos_events.hub_id`, jobs saved printed); it follows the cloud (`GET /pos-api/hub/sync`) and rebases (an event that no longer applies is a conflict). Card machine and loyalty events pass through to the cloud. Kept on disk (`venue.json` snapshot, `venue.log` fsynced per event, replayed after a restart). One primary hub per venue (linked, reported its port, seen in 15 minutes, oldest). Devices: the transport tries the hub first for events / sync / kitchen sync / day report / checks / presence (2.5 s), falls back to the cloud, asks the hub again every 30 s (5 s after an unknown key, which also makes the hub reload its set-up); cursors per source; 2 s polling on the hub; the kiosk counts the hub as a connection; order ready boards read numbers from the hub; status dot / kitchen bar / kiosk staff panel / till settings say venue hub. Only where the page may call plain http: Android app 1.3 (`mixedContentMode="always"`, cleartext via `plugins/withVenueNetwork.js`) or an http page. Store tech → Printers → Venue hub: the Hub first switch (own Save) and each hub's state from its report (sent every minute and when it starts or stops taking events). Tested: mirror unit tests, 6 hub tests (keys, CORS / PNA, a newly linked device known after one call, events and printing, internet down and a restart, hub first off, no set-up after a restart), 6 API tests (`api/test/hub-first.test.mjs`), the full API suite, and 32 end-to-end browser checks with a real hub process linked to the API and two counter tills and a kitchen screen on the production build: online through the hub, the API stopped and the devices' cloud calls cut, the tills seeing each other's orders, the kitchen getting and bumping tickets, the X report from the hub, everything uploaded when the API came back with nothing refused, hub first off sending orders straight to the cloud, Store tech's switch and the hub's row at 1280 / 390, a viewer read only; 2 mutations caught (13 checks).

- ✅ **The venue hub on Windows runs as a Windows service** — the user's ask (31 Oct 2026, after asking how robust the hub is and whether an Android hub or a Windows service would be better; they chose the service, installed with the PowerShell command, no paid code-signing certificate): on Windows the hub runs as the service **Macaroonie hub** (`MacaroonieHub`) instead of a scheduled task. `hub/install/HubService.cs` is a small service program the installer compiles on the PC with the C# compiler Windows ships (.NET Framework 4 csc.exe, so C# 5), registered automatic as LocalSystem with Windows' restart-on-failure; it runs the launcher in a job object, so stopping the service or the program dying ends every hub process. Where Windows won't run it (no compiler, Smart App Control) the installer falls back to the scheduled task; installing over an older hub moves it to the service and removes the task. The installer also stops sleep and hibernation on mains power and turns USB selective suspend off (`MACAROONIE_HUB_POWER=leave` skips). `hub.json` is written atomically. No migration. Tested: the service compiled with mono's mcs at C# 5 and its loop run in console mode (arguments, restarts, stop), the installer parsed with PowerShell 7 and the served copy carrying the source whole (`api/test/hub-appliance.test.mjs`), hub tests; and the real installer on GitHub's Windows machines with Windows PowerShell 5.1 and PowerShell 7 against a stand-in cloud (`.github/workflows/hub-windows.yml`: install, a code on the hub's page, the hub and the launcher killed and started again, the service program killed (nothing left, Windows starts it again), stop, reinstall, the task and back, a linked hub moved to another venue, uninstall).
