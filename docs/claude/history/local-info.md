# Local info: what shipped

Completed work in this area, oldest first, as written at the time. Reference only: for how things work now read `docs/claude/areas/local-info.md` and the code. A later entry can supersede an earlier one.

New entries: a few lines each (what shipped, the migration number, the date, where the code is). No test tallies.

- ✅ **Local info: weather, traffic, events and incidents around each venue** *(migration 240)* — the user's ask (8 Nov 2026): "capture local information - weather, traffic, events, incidents. information using smart search - pepper tools perform google search, or specific site search ... User configurable frequency of searches (once a day, every n hours, once a week.). User is also able to enter events. Everything per venue, but can be tenant wide. Calendar view at tenant or venue level, or a list view. Weekly/monthly Dashboard - ahead and retrospective. Use pepper to run analysis on demand." **Captures** per venue (`local_info_sources`): weather needs no key (Open-Meteo, the venue's town geocoded once onto the source, seven days ahead, severity from the WMO code, rain and wind); events / traffic / incidents / other run a Pepper web search (`searchForJson()` in `services/aiJson.js`: the `web_search` server tool, optionally pinned to one site, structured findings), each on its own clock (hourly to weekly, `nextRunAt()` venue-local; Run now on the row) from its own five-minute worker (`sweepLocalInfo()` in `startLocalInfoWorker()`: due sources claimed FOR UPDATE SKIP LOCKED with a 10-minute `running_until` lease, so two processes never run one source at once; `next_run_at` always advanced, `last_error` kept and shown on the row). Findings keep only dates two weeks back to ninety days ahead and dedupe by `external_key` (a repeat never un-hides or renames an item). **Items** (`local_info_items`): typed events (title, kind, severity, a day or a range, time, place, link; group-wide or one venue) edit and delete; captured items hide instead (an edit 422s — the next capture would overwrite it anyway). **Page** `/local-info` (Home menu, module `local_info`): month calendar with severity-coloured chips (dots on a phone), the day's items sorted weather first, list view, venue filter with Every venue, Show hidden, the Captures window (add / edit / switch off / delete with what it captured, Run now, last ran and next). **Dashboard widget** `local_info` on every dashboard kind (the next 7 days; options `look_back` and hide per kind). **Pepper tools** `local_info`, `add_local_event`, `run_local_capture`. Search captures count the tenant's monthly Pepper allowance (`addUsage()`, no person); weather costs nothing. Limits: Open-Meteo's free API is non-commercial — buy their API plan (`OPEN_METEO_URL` / `OPEN_METEO_GEOCODE_URL` point at the customer endpoints) or swap the provider in `captureWeather()` before real franchisees rely on the weather; the web search capture is built against a stand-in Claude, not yet run against the live API (first live capture: check the findings and the row's error); no push or alerts (the calendar and widget are pull-only). Tested: 7 API tests (`api/test/local-info.test.mjs`: capture CRUD and refusals, the weather capture against a stand-in Open-Meteo (claimed once, geocoded once, hidden stays hidden), a town the map doesn't know keeping its error with the schedule carried on, the search capture against a stand-in Claude (dating, window, dedupe), typed events and the captured-only-hide rule, the staff connector's three tools, deleting a capture taking its items), 6 shared tests, 11 of 11 deliberate mutations caught (the warning threshold, ends_on fallback, due-now advance, Monday grid, dedupe un-hiding, geocode cache, claim guard, allowed_domains pin, the date window, the date-column trap, the captured-edit guard) + 2 of 2 UI mutations, 47 browser checks at 1280 / 1015 / 390 (owner and viewer: calendar chips and the venue switch, the day modal, hide / unhide with Show hidden, add / edit / delete an event, a backwards range refused, captures CRUD + Run now + a failed capture's error on its row, both widget options on a custom dashboard, read-only view, phone dots with no sideways scroll).
- ✅ **Today: the week's weather and local news** — the user's ask (14 Nov 2026): "extend today's to include event headlines and show weather info for the week". No migration. Under the greeting on Today (the office page and the phone's), a **This week** card for the venue picked, from Local info: the forecast for each of the next seven days that has one (the day's name, a picture of the weather, the highest and lowest, rain from 1 mm, red for a warning and amber for a notice, the forecast's words on hover and to screen readers; a day with no forecast is a gap in its own column, never a later day moved up), then up to five local news items (events, traffic, incidents and typed events, the venue's own and the whole group's, hidden ones left out), soonest first then loudest, each with when (Today, Tomorrow, a day's name, Until Tuesday for something already running, Monday to Wednesday), its time, its place and a **Source** link when it has a web address, and "3 more in Local info" for the rest. Not changed: the website's social, ordering and delivery links (also only Zod's `url()`, typed by staff and shown on the group's own site). Tested: shared tests (`shared/test/links.test.mjs`, the `weekAhead()` test), `api/test/ops-today.test.mjs` (the week ahead: forecast days, headlines in order, counts, other days left out, another venue's own news, a viewer seeing it, an operator without Local info not; `javascript:` and `data:` links refused on POST and PATCH), `api/test/review-recording.test.mjs` (bad page links refused by the route and the connector, nothing stored), the Local info tests, 55 browser checks of the card (office at 1280 and 1015, phone at 390: the forecast row with a gap, colours, temperatures, rain, the headlines' order and words, Source only for web addresses, the more link, 48 px targets, the other venue's own news; a viewer, an operator without Local info; Local info's list and event window refusing a `javascript:` link and saving an https one; the empty week for a manager and a viewer), 19 Reviews page checks at 1280 and 390 (an https source page a 48 px link in a new tab, `javascript:` and `data:` ones not links), 25 Help / Docs checks; the Reviews and API review checks each failed with the old code put back. - ✅ **Local info: staff flag what captures found as relevant or not, and Pepper tunes each capture's search from the flags** *(migration 248)* — the user's ask (14 Nov 2026): "for events, weather calendar update, allow users to flag if the info is relevant or not relevant . based on the feedback use Pepper AI to analyse feedback and adapt capture queries". Each item a capture found (events, traffic, incidents, the weather) has **Relevant** and **Not relevant** buttons on the Local info page's list and day window and on the dashboard widget: one flag per person, tap again to take it off, with how many people flagged it each way; typed-in events have none. For a search capture (not the weather), Pepper reads the flags on what it found (the 60 most recently flagged findings of its own kind, with their counts) and writes a few phrases of what the search should look for and leave out; its web search uses them beside the operator's own Also look for words, never in place of them. It learns again by itself before the capture's next run whenever a flag changed (a failure is kept on the capture and the run carries on), or at once with **Learn now**; the Captures window shows the flags' counts, what Pepper learned, that flags changed since, why the last learning failed, and **Forget what Pepper learned** (asks first). A capture's **Learn from flags** switch (on unless switched off) stops both and keeps what was learned for later. Weather flags are only shown (a forecast has no search to tune). Pepper's `local_info` tool shows the flags and what each capture learned; reports count each item's flags and say what each capture learned. Tested: `api/test/local-info-flags.test.mjs` (8 tests: each person's own flag with everyone's counts, the same flag again changing nothing, taken off; Learn now sending the flagged findings to a stand-in Claude as data and storing, clipping and counting what came back; the next search carrying what was learned, a run learning first only when flags changed; a failed learning kept on the capture with the run carrying on; learning switched off; Forget, a change of kind, weather, who may and another group's capture; Pepper's `local_info` tool; reports counting the flags as the Local info page does), the fixtures flag a finding (the tenant sweep replays it), the catalogue test (234 tables), the local info tests, 89 browser checks (the list and day window at 1280 px; the Captures window: counts, the note while flags changed, Learn now learned / no pattern / refused, Forget asking first, Run now learning first and searching with it, the switch off and on; a viewer; a touch phone at 390 px; 1015 px without sideways scroll; the dashboard widget).
- ✅ **Local info: delete future entries in bulk, from the Captures window and through Pepper** — the user's ask (14 Nov 2026): "give pepper a tool to bulk delete local info (going forward) meeting specified criteria, in calendar>captures add option in each capture to delete future entries generated from this capture in bulk in specific date range (optional until)". No migration. One route, `POST /api/local-info/items/delete` (Local info Manage), deletes calendar entries from a day on (today at the earliest, never the past) to an optional last day, by venue or the whole group, capture, typed in or captured, kinds, severities and words in the title, details or place, with a dry run that counts first. A finding someone hid stays hidden (that is what stops its capture adding it again), and a finding people flagged as relevant or not is hidden instead of deleted, so Pepper keeps learning from the flags; everything else goes. Captures window: each capture has **Delete future entries** (first day, optional last day or No end, a live count of what goes, what is hidden instead and what stays, then Delete N entries and Yes, delete). Pepper: `delete_local_info` (a venue, the whole group or a capture by name, plus the same criteria; the confirm card says what is deleted, hidden instead and kept with the first entries, and pins the first day, venue and capture). A capture's next run can find deleted findings again (the card and the window say so). Tested: `api/test/local-info-delete.test.mjs` (5 tests: dry run counts per criterion with nothing written; refusals for a past day, an end before the start, a venue and the whole group together, another group's venue or capture, bad values, a viewer; another group's delete touching only its own; a real run with flags going with their findings and a flagged finding hidden; the next capture run bringing back what was deleted and not what was hidden; Pepper over the staff connector by venue, by capture and with nothing matching, the audit; the chat's confirm card from the dry run and its pins), the fixtures' dry run for the tenant sweep, 70 browser checks (the Captures window at 1280, 1015 and a touch phone at 390: the panel's counts and words following the days picked, a last day before the first moved with it, No end, a past day refused with today's date, Keep them, a refused delete saying why, Yes, delete with the flagged finding hidden instead and its flag kept, only the hidden one left after, Cancel and Edit closing it, the weather capture's own note and delete, a viewer without it; 48 px targets, no sideways scroll).
- ✅ **Local info: the same event found more than once shown as one entry** *(migration 249)* — the user's ask (14 Nov 2026): "calendar pepper captures, i need a mechanism after each capture run (except for weather) that consolidates duplicates, there is a lot of events that are the same but captured from different sources, slightly differnet name description but in essence refer to the same incident of event". After every run of a traffic, events or incidents capture (Run now included; never the weather), `mergeAfterRun()` asks Pepper (one short call per batch on the everyday model) which of the venue's findings of that kind, from any of its captures, are the same event or incident, and puts each group into one entry: the report kept on show is the loudest, then the one that runs longest, then the first found (`pickKeeper()`), one someone hid keeps the whole entry hidden, and the others sit under it (`merged_into`). Only findings within a day of each other are compared, and findings with nothing near them are marked looked at without asking. Flags move to the entry (each person's newest), and every capture with a report in it learns from them. The entry shows once on the calendar, the list, the day window, the dashboard widget and the Today page, with **N other reports of this** (each report as found, with its days, place and a source link); **Not the same** then **Yes, on its own** (Local info Manage) makes a report its own entry for good (`keep_separate`). A report inside an entry can't be changed, flagged or deleted on its own (422); Delete future entries hands another capture's report over when it deletes an entry, and leaves the capture's own reports under other entries. The Captures window counts each capture's findings under another entry and says why a merge failed (kept in `merge_error`, cleared by the next pass that works; the run itself always counts). Pepper's `local_info` shows other reports and a merge problem, the delete card what is handed over; reports count entries once with Other reports and Kept apart. Tested: `api/test/local-info-merge.test.mjs` (9 tests against a stand-in Claude: two captures' reports of one event put into one entry with their flags; an answer grouping days a week apart making two entries; a hidden entry staying the entry; two people's flags; Not the same; Pepper's tool; reports; a copy refused on its own and the bulk delete handing an entry over; a failed ask kept on the capture with the run carrying on and the next run asking again), the local info suites (`local-info` 7, `local-info-flags` 8, `local-info-delete` 5), `reports-catalogue` 8, `reports-weather` 7, the tenant sweep (fixtures with a merged entry), shared tests 340, the admin build, 75 browser checks (the calendar's one chip and the day window, the list's other reports and their details, Not the same and its question, the Captures window's counts and merge problem cleared by Run now, Delete future entries handing a report over, at 1280 and 1015, a touch phone at 390, a viewer without Not the same, the dashboard widget's count; 48 px targets, no sideways scroll, no page errors). Not yet run against the live model.
- ✅ **Local info: a note saying why something is relevant or not** *(migration 252)* — the user's ask (15 Nov 2026): "when flagging event as relevant or irrelevant allow user to leave short note why". After a tap on Relevant or Not relevant (the Local info list, the day window, the dashboard widget) a box opens under the buttons for an optional reason, up to 200 characters; **Say why** / **Change your note** opens it again and emptying it takes the note off. Your own note shows as Your note, other people's with their names. A note belongs to its flag (turning the flag clears it, taking the flag off removes it) and adding, changing or removing one counts as a flag change, so the capture learns again before its next run. Pepper reads the notes when it learns (on each finding's line, as data, a reason weighing more than a bare flag) and its `local_info` tool shows them; merged entries keep each person's note with their flag; reports don't read notes. Found by the browser check and fixed: the note box stuck out of a one-column dashboard widget. Tested lean: shared `localInfo` (9), API `local-info-flags` (9), `local-info-merge` (9), `local-info` (7), `local-info-delete` (5), the tenant sweep (the fixtures send a note), one short browser pass (47 checks: 1280 px, a touch phone at 390 px, a viewer, the widget). Learning from notes has only run against a stand-in Claude.
