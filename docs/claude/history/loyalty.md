# Loyalty: what shipped

Completed work in this area, oldest first, as written at the time. Reference only: for how things work now read `docs/claude/areas/loyalty.md` and the code. A later entry can supersede an earlier one.

New entries: a few lines each (what shipped, the migration number, the date, where the code is). No test tallies.

- ✅ **Loyalty: points, stamp cards, rewards, a web app, wallet cards, a members list** *(migration 211)* — the user's ask (26 Oct 2026): "Architectur must support both tenant wide and application wide loyalty, ie tenant can have own loyalty web app, but they can aslo join macqroonie loyalty. We gonna build tenant level loyalty - standard features like points, stamps, shared redemption, shared acquisitions, rewards, points redemption, google apple wallet integration. Scan at kiosk, till, online, features on off switches. Basic crm, with gdpr"; their choices: earning and spending shared across the tenant's locations, sign-in by an emailed code, Macaroonie's wallet accounts with an own-account override, the web app both on the tenant's site and on `loyalty.<domain>/<slug>`. Programmes have a scope: `tenant` (built) or `network` (Macaroonie's own, seeded off; members linked across tenants by `loyalty_identities`, email hashes only). Programme settings (`normaliseProgramme()`): a switch per feature, points (per pound, smallest spend, welcome, expiry by inactivity), earn / spend per channel (till, kiosk, online) and per venue, joining words, card colours. Rewards (money off, percent off, a free dish; for points, from stamp cards or from staff; smallest order, cap, channels, how long a held reward lasts) and stamp cards (per dish or per visit, a cap per order, a reward when full). Earning is never added by a device: `settleCheck()` / `settleOrder()` work out what a sale should give now (after discounts, without tips or service charge, less refunds; a check when closed, an order when paid or completed) and add the difference from the ledger, so refunds, a member put on later and repeats settle themselves; the minute sweep catches anything missed and expires points and held rewards. Spending: the server reserves a reward (points off or the held reward), the till / kiosk puts `check.member_set` and a `discount.applied` naming the redemption on the check, and the sequencer checks it (`loyaltyProblem()`: venue, member, check, the discount no bigger than allowed, used once); online, the quote prices picked rewards in `priceBasket()` and `createOrder()` reserves them in the order's transaction; anything taken off, voided, cancelled or unused is put back. Web app (`/loyalty` and `loyalty.<domain>/<slug>`): six-digit email code (15 minutes, 4 an hour per address, 5 tries), join with consent, the QR card, points, stamps, rewards, history, Apple / Google Wallet, details, newsletter, data download, new card code, delete. Till: the programme in a check's actions (scan or search, join, Use / Take off, can't remove a member with a reward on). Kiosk: Loyalty card on the order page (card only, first name only, what the order earns, a reward that no longer fits left off, join by QR code). Online: sign in or join at checkout, rewards, what it earns. Wallet: `.pkpass` signed with openssl and zipped by hand, Google save link (JWT), APNs pushes and Google patches when a balance changes. Members (CRM): search, filters, CSV, profile, adjust points, give / take back rewards, put back a stuck reward, new card code, close / open, export, erase (owner or admin; also from Customers anonymise). Loyalty website block. Tested: shared tests (programme, rewards, cards, points words, discounts, the sequencer check, kiosk orders with rewards and a skipped one), `api/test/loyalty.test.mjs` (9 tests: programme and permissions, other tenants' dishes and rewards dropped, web app sign-in and join, till earning on close, stamps filling a card, spending reserved / used once / put back, kiosk card-only lookups, online quote / order / completion / cancellation, staff CRM incl. a closed membership, GDPR export and erasure), `api/test/loyalty-wallet.test.mjs` (stand-in Apple and Google servers), the loyalty test in `system-paths.test.mjs` (both web app addresses, the public API, the block live and hidden when the web app is off), the tenant sweep with loyalty in the fixtures, the full API suite, 12 shared / API and 3 browser mutations caught, browser checks (admin 69, till 40, kiosk 52, online 48, web app 32, block 17).
- ✅ **A Loyalty card block, a Loyalty page you can design, and member or guest at checkout** *(migration 214)* — the user's asks (29 Oct 2026): "can you build a block for the website to show loyalty details - show qr code, balance, history,etc. also loyalty page, like order online, needs to be editable via website>pages" and "For ordering, add option to register / join loyalty, so user can choose registered loyalty user or guest login". The guest's loyalty card is one module, `api/src/assets/loyaltyApp.js` (`mountLoyalty()`), served as `/loyalty-api/app.js`: the stand-alone web app (`loyalty.<domain>/<slug>`) and the new **Loyalty card** block both run it, so there is one card. Block options: heading (blank = the programme's name), intro, which parts show (how you earn, stamp cards, rewards, history, settings, wallet), width, button and box colours, card colours (blank = the programme's; words on a set card colour go black or white). Signed in it shows the QR card, points, stamp cards, rewards, a History tab and a Settings tab (details, new card code, data download, sign out, delete). Pages on one page share the sign-in (`mcrn-loyalty-session` event, storage events across tabs). The tenant site's `/loyalty` is now a built-in website page (`system_key = 'loyalty'`, migration 214 seeds it with a Loyalty card block), listed in Website → Pages & modals as Loyalty at /loyalty: title and blocks editable, can't be deleted, unpublished, moved or made a modal (422 with a reason), `/p/loyalty` redirects, left out of the sitemap; 404 while loyalty or its web app is off; it keeps the web app's manifest so it still installs. `shared/sitePages.js` names the built-in pages and their addresses for the admin and the API (`pagePath()`: Pages list, LinkPicker, sitemap, llms.txt). Checkout: a guest who isn't signed in is asked How would you like to order? (Sign in or join, with what the order earns, or Continue as a guest); the rest of checkout waits; guest is kept for the visit (sessionStorage), with a Sign in instead line; member signs in or joins in the panel and the name, email and phone fill from the card; signing out clears what the card filled and asks again; a guest already signed in (from the web app or a Loyalty card block) goes straight to the form. `/me/rewards` also returns the member's name, email and phone. Tested: `api/test/loyalty-page.test.mjs` (3 tests: listed and guarded, title and blocks published, the block's options, the redirect, sitemap, the block on the home page with a light card, 404 while off, another tenant and a viewer; four mutations caught), the loyalty tests in `system-paths.test.mjs` and `loyalty.test.mjs`, 50 checkout browser checks (1280 / 390: asked first, guest, kept after a reload, sign in with the emailed code, details filled, sign out, join; a signed-in guest), 43 card checks (the page and the block: sign in, card, stamps, rewards, history, settings, sign-in shared between blocks and tabs), 20 page builder checks (listed, no delete, the note, the canvas samples, settings following and saved, 1015); two UI mutations caught.
