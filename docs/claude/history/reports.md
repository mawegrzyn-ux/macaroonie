# Report builder: what shipped

Completed work in this area, oldest first, as written at the time. Reference only: for how things work now read `docs/claude/areas/reports.md` and the code. A later entry can supersede an earlier one.

New entries: a few lines each (what shipped, the migration number, the date, where the code is). No test tallies.

- ✅ **Report builder: groundwork, the engine and a first viewer for till sales, online orders and bookings** *(migration 243)* — the user's go-ahead (12 Nov 2026): "re report builder - i am happy with your proposed answer to 1 to 8 points, go ahead with the build", accepting the eight answers recommended in `docs/REPORTS.md` section 22 (one Reports module with View / Use / Manage; till sales, online orders and bookings first; PDFs by a headless browser after a memory check; data links with a key for owners and admins, personal data off unless switched on per link; scheduled emails to outside addresses set by owners and admins; Pepper straight after the builder; the existing fixed reports stay; Appendix B's starter reports). This is the first of the plan's PRs: phase 0 and the first part of phase 1. **Built**: a report is a JSON definition (`shared/reports/spec.js`), looked up in a data catalogue kept in code (`api/src/reports/catalogue/`: 26 subjects over till sales, online orders, bookings and what they share; every table in the database has a decision), turned into SQL by the server (`compile.js`: names only from the catalogue, every value a person gave a numbered parameter, the tenant id on every row read) and run as the person looking at it, read only, on its own small pool (`run.js`, `withReport()`): lists, summaries with subtotals and a total (one statement with GROUPING SETS), tables across (matrices), top or bottom N with everything else, a period beside the one before or last year, calculations, drill steps. Guards: problems as sentences (422), role checks (403), two reports at a time for a group (429 after 5 s), the planner's cost estimate before anything runs, 20 s on screen and 120 s for a file, 5,000 rows of a list on screen, results kept a minute. The till stores three more breakdowns per check (discounts, charges, VAT by rate) and a cancelled order's, a void's and a refund's details as columns, written from the `checkTotals()` its own day figures use, with older checks filled in when the API starts. Module `reports` (owner / admin Manage, operator View, viewer none; Use builds, saves and downloads), the `/api/reports` routes, saved reports shared with nobody, some roles or everyone, stars, a record of every run and file (kept 400 days, never the typed values), 28 starter reports in code (till 15, online 6, bookings 7), CSV files (a list streamed, up to 250,000 rows) and Excel files (200,000 cells, an About sheet). Admin: Reports in the Home menu after Dashboards (`/reports`: search, area buttons, Starred / Your reports / From your team / Starter reports by area, stars) and the viewer (`/reports/:id`: the period and venues for the visit, one table drawing for a list, a summary and a matrix with the headings, first column and totals staying in view, notes, Refresh, CSV / Excel with Use, Delete). **Not as the plan had it**: the private file store waits for the phase that first keeps files (4); the catalogue has no `staff.people`, `online.payments` or GloriaFood subject of its own (`till.takers` and `online.sales` cover them); exports are `POST`; a list's file has no totals row; an Excel file's ceiling is cells, not rows; "Guests by day and sitting" became Guests by day and time, and voids / cancelled orders and charges / tips are two reports each (28 starters for Appendix B's 26 phase-1 lines); platform-wide starters live in code, not in a table; the builder, charts, drill-down on the page and the print page are the next PR (1b), so nothing can be built or saved on screen yet. Fixed on the way, found by the browser checks: a refusal (no access, no such report) showed only after a second of "Loading" (the app retries a query once: `retryUnlessRefused`), a manager saw "Only you" on someone else's private report (now Not shared), the viewer's delete button was 44 px (`ConfirmDelete big`), a date in the pinned first column wrapped onto two lines, and a subtotal row was two-tone. Tested: 464 shared tests (39 new: the definition 15, periods 7, calculations 8, formats 7, the till's breakdowns 2); API `reports-engine` (21), `reports-catalogue` (7: every table has a decision, every id column of a catalogue table is accounted for, no secret column is read), `reports-api` (14) and three reconciliation tests holding reports against the pages' own routes for the same days: `reports-till` (8, the Z report), `reports-online` (7, Transactions and the Report tab), `reports-bookings` (5, the Bookings list); the fixtures save, run, preview, export, change, share, copy and star a report, so the tenant sweep replays each as the other tenant; the full API suite (559 tests, all passing; one skips itself when run close to midnight); 120 of 120 deliberate mutations of the API and shared rules caught; 130 browser checks at 1280, 1015 and 390 px for an owner, an admin, an operator with View and no Till reports, a viewer and a touch phone, with 30 of 30 deliberate mutations of the pages caught; the Help and Docs sections rendered. The pull request's first CI run failed one test: it ran at 00:22, when the test till's sales still sat on the trading day before while a saved report's "today" was the calendar day. The tests' till days now go on the calendar day at the venue and a test states the rule (Common mistakes: "Today" in a till report).
- ✅ **Report builder: build your own (the builder)** — second PR of the user's go-ahead (12 Nov 2026: "re report builder - i am happy with your proposed answer to 1 to 8 points, go ahead with the build"), phase 1b-1 of `docs/REPORTS.md`. Save, Save as, a question before leaving with changes not saved. **One set of rules**, `shared/reports/build.js`, for the admin now and Pepper later: what a field, figure or link can be in a report (`pathUses()`), the Data panel's tree and search, every edit (each gives back a whole checked definition, or the same object when nothing changes) and the words. The catalogue view now says which subjects a role can build on (`base`) and which figures add up through a list of rows (`across`, from the one list the engine refuses by, `ACROSS_AGGS`). **Viewer**: Edit (your own, or anyone's with Manage) or Customise (a copy to make your own), More (Make a copy, Name and details, Share with Manage: only you, some roles, everyone, or offered as a starter; Delete asking first), and a button for each choice a report asks for (the files follow them). **Found and fixed on the way**: a date or time filtered by "is empty" / "isn't empty" stopped the report with a database error, since the engine took the time zone as a statement parameter and then didn't use it (found by the first run of the test that runs everything the builder offers); something typed that isn't a number counted as "nothing picked" and showed every row; messages at the foot of the builder sat under the floating Mobile view button on touch phones; icon-only buttons and grips were 40 px wide; the shared `Modal`'s Close button was 44 px; a link from a thing to another of its own kind was never offered in the Data panel (no subject has one yet; found by a unit test written after the mutation run). **Not as the plan had it**: charts, drill-down on the page and the print page are the next PR (1b-2); no undo; filters made of several parts are read and taken off, never made on screen; tags aren't edited; sharing needs Manage on Reports. Tested: 477 shared tests (13 in `shared/test/reportBuild.test.mjs`: what each kind of path can be, the Data panel's tree and search, every edit, the words, a filter's value); `api/test/reports-build.test.mjs` (7 tests: everything the Data panel offers, for every subject, put into definitions the way the screen does and run on a database with real sales; what the builder leaves out is refused by the engine; a new report about anything shows something straight away; a session in the builder where every step runs; filters fixed and asked; the search; the across rule on made-up figures); the full API suite (566 tests); 388 browser checks (255 of the builder at 1280, 1015, 900 and 800 px and on a touch phone at 390 and 320 px, for an owner, an admin, an operator with Use and one with View; 133 of the Reports list and the viewer, with the Help and Docs sections rendered); deliberate mutations: 59 of the pages (57 caught, 2 change nothing), 89 of the shared rules (85 caught, 4 change nothing), 8 of the API side (all caught, two of them only once the across rule had a test of its own).
- ✅ **Report builder: tap a row to open it up (drill-downs)** — third PR of the user's go-ahead (12 Nov 2026: "re report builder - i am happy with your proposed answer to 1 to 8 points, go ahead with the build"), phase 1b-2 of `docs/REPORTS.md`. No migration. **In the viewer** a row of a summary can be tapped (the whole row, 48 px high on a touch screen, with a button of its own for a keyboard): a window names the row, shows its figures and offers what it can be opened into, **By <field>** for each level the report offers (the same figures broken down by something else) and **Show the rows** (the checks, dishes sold, payments, orders or bookings behind it); with one thing to open into there is no window. In a table across, a figure opens that cell and the row's name the whole row; the Total row opens too; the row for everything else can't. A trail above the table (All, then each row opened and what it was opened into) goes back to any step; the period, venues, other choices, Refresh and the CSV / Excel files follow the place, and what was opened can be opened further, each field once on the way down. The steps last for the visit. **The rows behind a figure** are the rows that figure counts (Net sales lists dishes on closed checks that weren't voided, and the list adds up to the figure), with a note when only some rows are listed; where a report's figures count different rows (payments beside refunds) a tap means the figure tapped, else the row. **In the builder** Set up ends with a Drill-down part for summaries: **Tap a row: break it down by** (up to 8 fields, dragged into order, a date or time by its bucket) and **Tap a row: show the rows** (the usual columns for that kind of row, or chosen ones, up to 30), filled from the Data panel by tap or drag; the preview's rows can be tapped the same way, and any change to the report goes back to the report itself. **Server side** the page sends steps and the server makes each definition from the report's own (`drillSpec()`), so someone with View can open rows up without being able to run a definition of their own, and sees only what their role may see; a run's record keeps the steps without the values held. The starter reports already named their levels, and every summary can list its rows (the subject's usual list columns). **Found and fixed on the way**: a row of a result the engine had split by currency by itself couldn't be opened (the server refused the currency as "not a grouping of this report"; `currencyPath()` is let through as `also`); the viewer's period, venues and other choice windows showed the picks from the last time they were open for an instant when opened again (their starting state was set in an effect after the first paint; now by the handler that opens them). **Not as the plan had it**: the catalogue has no hierarchies (a report's levels are its own `drill.down`); a report can't name another report as its drill target; the steps aren't kept in the address; in a summary a tap means the row unless the figures count different rows; a figure with no rule of its own, or one reached through a list of other rows, lists every row; chart taps come with charts and opening the record itself from a row is its own PR. Tested: 480 shared tests (the drill tests in `shared/test/reportSpec.test.mjs` and `reportBuild.test.mjs`); API `reports-engine` (23 tests: steps made into definitions, the rows behind a figure and their note, a row of a result split by currency, a compared report opened both ways), `reports-api` (16: steps on run, preview and both files, a step that can't be made refused, someone with View opening rows up, the run's record without the values held) and `reports-build` (8: every level and rows list the builder offers, for every subject, runs); the full API suite (571 tests, all passing); 523 browser checks at 1280, 1015 and 390 px (133 of drill-downs: the viewer for an owner, an operator with View at 1015 and a touch phone, and the builder's Drill-down part and its preview; 256 of the builder; 134 of the Reports list and the viewer, with the Help and Docs sections rendered); the production build (main bundle 5.19 MB); deliberate mutations: 38 of the shared rules (37 caught, 1 changes nothing), 25 of the API side (24 caught, three of them only once checks were added for them: the note for more than three figures, a subject with no one venue, a figure kept from a role; 1 changes nothing), 52 of the pages (51 caught, one of them only once a check was added for it; 1 changes nothing).

- ✅ **Report builder: Pepper builds a report from a few words (the smart builder)** — seventh PR of the user's go-ahead (12 Nov 2026: "re report builder - i am happy with your proposed answer to 1 to 8 points, go ahead with the build"), the first part of phase 2 of `docs/REPORTS.md` (section 10). No migration. **New report** starts with **Describe it to Pepper** (Reports Use or Manage, and Pepper): a request in the person's own words, an example to tap, or a photo or PDF of a report they use now; **Build it** answers within about a minute with the report run on their figures (200 rows), its name, **What this shows** (one sentence worked out from the definition, never the model's words), **What Pepper assumed** and **What Pepper couldn't do**, and up to three questions when a name could mean more than one thing: a choice changes the report on the page at once, and answers add up. Then **Save it** (name and description filled in), **Change it** (in words: "only Fridays", "add guests", "as a line chart"; the name is kept unless the change makes it wrong), **Open in the builder** (Back comes back to the answer), **Ask in other words** or **Start again**; the answer survives Back and a reload, and saving replaces the page so it can't be saved twice. Pepper is shown only refs for the subjects, figures, fields and links the person's role can build with (never a table or column name, never a row of data), and its answer becomes a definition only through the builder's own edits, then the same checks as one built by hand, run as the person; one retry with the reasons. Each build counts towards the group's allowance and the person's daily share. With it: a list of 63 real requests with what a right answer must contain (`api/scripts/report-requests.js`) and a script that runs them against the live model as one person of a group (`api/scripts/report-smart-check.js`). Not as the plan had it: 3 to 8 subjects in full (not 6 to 10); names in the data are found among the report's own rows rather than by `pickByName()`; changes go through the same route with `previous` (no separate `/refine`); the code is `api/src/reports/smart.js` (not `ai.js`). **Found and fixed on the way**: after a change the report's name fell back to the subject's label (the current report went to Pepper without its name). Tested: shared tests (reportChoices, reportDescribe; 538 in all), `api/test/reports-smart.test.mjs` (11 tests against a stand-in Claude: refs only and the role's subjects only, the answer run as the person, venue and data names with their questions, another group's venues, the retry and the second ask, a change keeping the name, files, nothing fits, refusals for roles, Pepper switched off, a refusal by Claude, an empty request; the request list names only what the catalogue has and `checkAnswer()` passes a right answer and says what a wrong one misses), 75 browser checks on the Describe page and the answer at 1280 and 390 px, the request script run end to end against a stand-in Claude on a filled test group. Not yet run against the live model.
