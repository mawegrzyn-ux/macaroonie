# Menu screens: what shipped

Completed work in this area, oldest first, as written at the time. Reference only: for how things work now read `docs/claude/areas/screens.md` and the code. A later entry can supersede an earlier one.

New entries: a few lines each (what shipped, the migration number, the date, where the code is). No test tallies.

- ✅ **Menu screens (digital menu boards) + sold out from the till** *(migration 166)* — `/screens` (module `screens`, nav link after Menus): screens paired by a six-letter code shown on the device (`screen_pairings`, only hashes stored; the screen keeps its secret), each with a venue, ID (S1...), size, rotation, fit and a board or playlist; identify, reload, new device, remove, online / showing from heartbeats. Board designer (`/screens/boards/:id`): pixel canvas, blocks heading / text / menu list / featured dish / price / image / box / clock / allergen key, drag, corner resize, snap, layers, fonts, colours, live or draft prices, a venue's sold out in the preview. Playlists with per-board seconds and times of day / dates (`ScheduleEditor`, end not included). Player PWA on `screens.<domain>` (plain files in `screen/`, Chrome install or Fully Kiosk): pairing screen, config in localStorage, service worker (player network-first, images and fonts cache-first), board rotation by time of day, scale + rotation + fit, image preload, wake lock, identify overlay, reload on a new player version; WebSocket pushes (board / playlist / screen changes, `menus.live` on publish, sold out) plus a minute poll. Prices are the live menu versions. Till: hold a dish to mark it sold out (today / until put back / back on; permission `sold_out`, on for Supervisor and Manager; manager PIN otherwise), shown greyed on every till, online ordering, the orders board and the screens (`services/soldOut.js`). Fixed: `ScheduleEditor` showed "{datesLabel}" / "{resetLabel}". Tested: 100 API checks (pairing, config, live vs draft prices, hidden sections, tags, sold out from the board and the till incl. permissions, playlists and validation, two tenants, view / none, module off, delete, player host and file serving), 45 browser checks (designer drag / resize / nudge / blocks / save / draft prices, pairing a real player through the admin, rotation, identify, sold out push, playlist, remove; 1280 / 1015 / 390 px; view only), 11 till browser checks, 11 renderer unit tests.
- ✅ **Menu screens: video, walls, transitions, animation; dropping photos into the editors** *(migration 167)* — Video block (Media now takes MP4 / WebM up to 150 MB; nginx location for the two upload routes from every deploy; each screen keeps the videos in its service worker cache and plays byte ranges from it offline) and Scrolling text block; block animations (comes on / while on) with designer Play; playlist transitions with an admin preview; walls (`screen_walls`: grid, places, gap, the wall's board or playlist, "Make a board this size", designer guide lines). Screens keep in step through a server clock (`/screen-api/time`), clock-based rotation (`playlistPosition()`), the next board drawn 3 s early, transitions and animations timed from the shared clock and videos nudged every second (playbackRate or seek). Also: a new config re-fits what is on screen (turning a screen didn't apply until the board changed), a reopened socket fetches the config (changes made while a screen was offline waited for the minute poll), view-only people can play the playlist preview, Media upload accepts Screens manage, the designer shows videos still until Play. Dropping files (user report, 16 Oct 2026: "dragging dropping images doesn't work very well"): in the board and menu designers the browser's own picture drag cancelled the block move (reproduced: `dragstart` on IMG then `pointercancel`); fixed with `noImageDrag` + `user-select` / `-webkit-touch-callout: none`. Photos from the computer can be dropped onto boards, menu design pages, the page builder canvas and every picture field (`lib/fileDrop.js`); `installDropGuard()` stops the browser opening a dropped file over the admin. The page builder's grip handle had an inline `opacity: 0` that beat its hover rule, so it never showed; now CSS-only (hover, selected, always on touch). Tested: 57 API checks, 31 player checks (two screens on a wall in step: board, transition within 40 ms, scrolling text, video within 0.15 s; offline video from the cache; catch-up after offline), 41 admin checks (designer, playlists, walls, media, 1280 / 1015 / 390 px, view only), 23 drag-and-drop checks, the PR 2 suites (100 API, 45 UI), 17 renderer unit tests.

Order status block: `tile_main` / `tile_lines` (Each tile in the screen designer; migration 189 turned `show_names` into `tile_lines ['name']`), `boardNumbers()` entries carry tent, table, name, type and source. Kitchen screens: setting `ticket_main` (Till setup → Kitchen screens → Ticket title), `ticketTitle()`. Kiosk: `checkout.number_kind` tent (default) | table, tent wording in nine languages, Done screen tent line; designer Paying panel Number to type. Bench test orders take a tent and a name. Tested: 130 shared tests (orderInfo, screen layout tiles, boardNumbers, kiosk words in every language, bench), 11 kitchen-flow API tests (ticket title saved / sent / refused; an order ready board's feed to a paired menu screen with name, table and type), the migration on sample boards, 39 browser checks (designer Each tile with the canvas following, save and reload, a real ready order drawn by the player with TENT 23 / Order 88 / Ali, Ticket title in Till setup then on the test bench, the kiosk preview asking for a tent and the Done line, Table number instead, 1015 px, view only).

- ✅ **Choose how often devices check for changes; menu screens in the Android app** *(migration 216)* — the user's asks (29 Oct 2026): "can you make the update frequency configurable, for performance reasons" and "can we DMBs as option to the app pls". **Pull times**: per location in `pos_settings` (whole config 60-3600 s, standard 180; prices and sold out 0 = off or 10-600, 30; menu screen boards 30-3600, 60; order ready board numbers 5-300, 15), one rule in `shared/pos/pullTimes.js`, carried as `pull` by every device config (a change changes the version, so devices download it; menu screens also get `screens.changed`). Devices schedule each pull from the current config (`createPullTimers()` in `pos/src/lib/livePull.js`, used by the till, kiosk and kitchen screen stores; `setPullTimers()` in the player) and start again straight away when a new config brings other times. Store tech → **Device updates** (`/pos/updates`, nav link added by migration 216 after Card machines): Standard / Less often / Least often, a row of times per pull, an asks-an-hour estimate for the location's devices, Save, Use these at every location (`POST /api/pos/pull-times/everywhere`, with a confirm). The till's settings, the kiosk's staff panel and the player's settings panel say how often. Also fixed: the kitchen screen's config timer was never stopped on disconnect. **Android app 1.2**: Menu screen as the fourth device type (`https://screens.<root>/`), a menu screen or kiosk never leaves for another site (`staysPut()`), the Picker works with a TV remote (focusable, a white ring, preferred focus), the app shows on an Android TV's home screen (`plugins/withTvLauncher.js`: LEANBACK_LAUNCHER, `android:banner`, touchscreen / camera / leanback not required; checked with `expo prebuild` in a scratch copy), and the player shows Change device type on its pairing screen and in its settings panel when inside the app. Tested: 4 shared tests, an API test (defaults, every device kind's config incl. a paired menu screen, refusals for 6 out-of-range values, viewer and another group, every location and only the group's), the nav test, 3 app tests (roles), `expo export` and `expo prebuild`, 32 browser checks on a production build (a kiosk and a till: no asks at 10 minutes, every 10 s straight after the change (gaps 10.0 s), none when off, the whole config once a minute; the kiosk's staff panel line; a menu screen asking every 30 s and its settings panel line; Device updates at 1280 / 390 and View only) with a mutation (timers not restarted) caught by 4 checks, and 8 player checks with a stubbed app bridge.
- ✅ **Order ready boards in the live kitchen view; a meal deal's parts ticked one by one; menu screens start again** — the user's asks (4 Nov 2026): "1. in the live kitchen view, can you include ORBs 2. When checking off items on the KDS screens, allow individual item tickoffs in bundles". No migration. **Boards in the live view**: under the kitchen screens, each order ready board as guests see it, the real menu screen player in live mode in a frame of `screens.<root>` read by the live view's signed link (`/screen-api/live/config`, `/screen-api/live/orders`, the socket's `board_live` branch; nothing paired, nothing kept on the device). As set up: each menu screen of the venue showing an Order status block (its board, a playlist board or its wall's), as it shows now, with its name, what it shows and whether its device is on; One per station, or no such screen: a plain board of each board station's numbers (`liveBoardConfig()`), or of every counter and online order when the flow has no board station. Upright, in the screen's own shape, own Full screen. **Part ticks**: on a combo's ticket each part row is its own 48 px target; at a prep station a tap marks that part done (the parts made there), at the pass or a runner ticks it off (every part); the dish row counts them (1/3); the last part is the whole dish done or ticked off (with the bump the last dish makes, or the last-tick bump), the dish still moves on as one; undoing one part of a done dish undoes the dish and keeps the others; a remake, undoing the whole dish or the dish sent back drop them; two of the same part are one row. **Found and fixed (my bug from #431)**: `shared/orderPricing.js` started importing `pos/orderFlows.js` and `pos/charges.js`, which the player's hand-kept `PLAYER_LIBS` didn't serve, so the player's module never ran and every menu screen and order ready board stayed black from that deploy (screens reload themselves on a new player version, so running ones went too). `PLAYER_LIBS` is now worked out from the imports (`importClosure()`, shared with the hub release), `sw.js` keeps the same list, `index.html` reloads by itself every minute while the player hasn't started, and `api/test/browser-modules.test.mjs` follows every module tree served without a bundler (the player, online ordering, the loyalty card; 5 of 5 mutations caught). Screens that went black need one reload (or a restart) after this deploy; they recover by themselves from then on. Tested: 9 shared tests (`shared/pos/test/kitchenParts.test.mjs`), 2 API tests through the sequencer (`api/test/kitchen-parts.test.mjs`), 4 new live view API tests (`api/test/kitchen-live.test.mjs`: the boards list, the player's reads by the link incl. refusals, framing only in live mode, the socket's rooms), a system-paths test, 4 browser-module tests, the full API suite, shared, shared/pos and hub tests, and browser checks on three real paired kitchen screens (grill, fryer, pass: each station's parts, 1/3, the last part done and the ticket going, At Fryer at the pass, 1/4 then 3/4 with both pots in one tap, the last part ticking the meal off, unticking one part, 48 px rows) and the live view (a menu screen board and a plain board in frames showing PREPARING and READY as orders are sent and bumped, an upright board beside a wide one, One per station, full screen and back, the view only, 1440 and 390 px).
- ✅ **Order ready boards: one column, or only some order types and revenue streams** *(migration 237)* — the user's ask (6 Nov 2026): "order ready board module for screens - allow user to select to show either orders being prepared, or orders that ready, or both, also allow user to filter orders to specific stream or order type". The renderer filters before Most shown and leaves out numbers of other kinds fading out of a change; the designer's examples take the picked order types. Tested: a new renderer test and kitchen test (13 of 14 shared mutations caught, the last after adding the stream-sample check), `api/test/order-board-filters.test.mjs` (4 tests: a till's counter order's stream and type on a paired screen's feed and a change of stream, an online order's stream into the kitchen, the designer's lists one per name and only the group's own, the migration; 3 of 5 API mutations caught, the two missed are a tenant filter and a venue filter that forced RLS and the ordering settings already enforce), the full shared suites, 35 browser checks in the designer (Show and its panel at 1280, the chips and summary, the examples, save and reload, clearing, a gone name, 1015 px, View only).
