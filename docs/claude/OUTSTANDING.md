**3. Header & Footer as page-builder blocks**
The site header and footer are currently template-baked (`templates/{key}/partials/header.eta` + `footer.eta`) and read auto-derived data: tenant_site logo + nav from venues/menus/pages, social_links, address, etc. Operators want them editable AS BLOCKS in the page builder so they can add/remove nav links, swap CTA copy, restructure footer columns, surface custom social handles. Required:
- Two new block types: `header` and `footer`. Each has rich data shape (header: `{ logo_url, brand_text, nav_items: [{label,url}], cta: {text, url} }`; footer: `{ columns: [{title, items: [{label,url}]}], copyright, show_social, show_powered_by }`).
- React canvas components for both, with editor controls (add/remove link, drag-reorder).
- Eta block partials per template (`templates/{key}/blocks/header.eta`, `footer.eta`) so each template renders its own signature chrome.
- Rendering shift: `index.eta` and `location.eta` STOP including `partials/header.eta` / `partials/footer.eta`. Instead, the home_blocks/page_blocks array renders, and we auto-prepend a `header` block + auto-append a `footer` block when missing (so the user always gets working chrome out of the box).
- Page builder UX: header block should be locked at index 0, footer at the last position (no drag). New "+" inserter sits between them.
- Picking a page template seeds blocks with header + footer at the expected positions.

**11. `/mobile` PWA install identity on Android — confirmed broken on real device, needs a subdomain** *(code done with migration 138: ops.macaroonie.com. Takes effect once `scripts/nginx-office-ops.sh` has been run and Auth0 allows ops.; still to confirm on a real Android device.)*
Real-device testing (item 10) surfaced that Android Chrome does not treat `/mobile` as a
separately-installable PWA the way iOS Safari does. Chrome ties "already installed?" to
the *origin*, not to which manifest is currently linked — since a WebAPK is already
installed for `macaroonie.com` (the main app, `scope: "/"`), Chrome's install flow offers
to open that existing app instead of creating a distinct "Macaroonie Ops" icon, regardless
of `MobileShell`'s manifest/link-tag swap. The only reliable fix is a genuinely different
origin for `/mobile` (e.g. `ops.macaroonie.com`), since PWA install identity on Android is
origin-scoped. **Pick this up together with the office/ops subdomain work discussed earlier**
— fold the `/mobile` PWA identity fix into that same subdomain rollout rather than doing a
one-off DNS/Nginx change just for this. Until then, "Create shortcut" (Chrome's fallback
option) is the only way to get a distinct icon/name on Android, and it's a browser
shortcut, not a standalone WebAPK.

**46. Architecture: one API (a monolith), and whether to split it into services (backlog, the user, 21 Nov 2026)**
- The user's thought: "we have this monolith, i think we need to section the app into microservices", with a request for input and recommendations. Nothing is decided and nothing is built.
- What there is (measured 21 Nov 2026): one Fastify API (about 96,000 lines in `api/src`, 81 route files, 95 route plugins registered in `app.js`, 248 tables in one Postgres with forced RLS) run as a PM2 cluster on one Lightsail machine beside nginx, Postgres and Redis. The background workers (emails, hold sweep, GloriaFood poll, AI clean-up, local info, report schedules) start in `server.js`, so they run inside every API process. The front ends are separate builds already (`admin/`, `pos/`, `screen/`, `hub/`, `android-app/`) and share their rules through `shared/`.
- Recommendation given with the request (21 Nov 2026): don't split into microservices now. Keep one codebase and one database, and split by how the work runs, not by feature. In this order:
  1. A worker process of its own: the BullMQ workers, sweeps and schedules, PDFs by headless Chrome, kept report files, the pollers. Background and heavy work then can't slow requests down, and runs in one place instead of every API process.
  2. The device API (`/pos-api`, `/screen-api`, `/ws`: tills, kitchen screens, kiosks, menu screens) as its own process group, apart from the office API, so an office deploy, a heavy report or a Pepper turn can't disturb trading.
  3. Pepper's chat and the other long AI routes (`/api/ai/`, streams of up to 600 s) as their own process group.
  4. The public tenant sites, the ordering page and the booking widget as their own process group, behind a cache.
  Each is the same code started with a role that says which route plugins and workers it registers, so there are no new contracts between services and no split of the data. Inside the code: keep each area behind its own service functions (the 22 areas of `docs/claude/areas` are the map) and add an import check so one area doesn't reach into another's files.
- Why not microservices: (a) one developer: microservices pay off when several teams must deploy on their own, and here they add contracts, pipelines and ways to fail with nobody to share the load; (b) the data doesn't split cleanly: a till event is decided under the venue's sequencer lock and writes the check, its kitchen orders and its print jobs in one transaction, loyalty is settled from the same checks straight after, the day's Z fills Cash Recon, the report builder reads most tables through its catalogue, Pepper and Today call other areas' routes in-process (`callApi()`), and the venue hub must decide check events exactly as the cloud does from `shared/`; (c) tenant isolation is one mechanism now (`withTenant()` and forced RLS) and would have to be rebuilt in every service; (d) cost: more machines and more moving parts before the first real customer; (e) it wouldn't cut AI usage: a change that crosses services needs more context, not less (the notes split of 21 Nov 2026 is what addressed that).
- Where a separate service is right: a part with its own runtime or memory needs (PDF rendering with headless Chrome, image processing), its own security boundary (public data links, payment webhooks) or a clean edge in the data. Nearest candidates: the PDF renderer, Pepper's chat (it already reaches the rest through HTTP-shaped calls), local info captures, the public site renderer (it reads the published snapshot). Poor candidates: the till, kitchen screens, kiosks, loyalty, online ordering and menus (shared transactions and rules), and bookings with customers.
- Signs to look again: a second development team; a part that needs another stack; one part's load ten times the rest; a need to deploy the till's API on a different schedule from the office's; an outage where one area took the tills down.
- Before deciding: write down what hurts today (deploy risk, slow tests, AI cost, a feared outage) and measure the live machine (item 42). This goes with item 42 (infrastructure on AWS): the process roles above are the units that plan would scale.
