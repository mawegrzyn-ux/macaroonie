# Macaroonie's current state as it bears on an AI-first back office (repository analysis, 22 Nov 2026)

Scope and method. Source: the repository at `/home/user/macaroonie` only (branch `ccr-8a02ce1e-6lipav`, head `0205f32`), read on 22 Nov 2026. No web sources. Nothing was run against a database, server or test suite: every count is static, from the files, and each says how it was counted. Links are paths from the repository root with line numbers. "Built" means the code is in the repository; "planned" means it is only in a planning document. ## 1. Navigation and information architecture: how many pages exist, how the menu is organised, what search does, and how someone reaches a task today

### Takeaway
The office has about 90 routed pages behind a 12-section, 93-link menu that each group can redesign, plus a keyword search over pages and saved reports with a hand-over to Pepper. Three home pages coexist (Overview, Today, Launcher), and Today is the only one that turns data into "what to do now" with a form one tap away; most pages cannot be opened at a given venue, day or tab from their address.

### Inferences
- Steps to a task today, read from the code and not measured with users. Classic route: one click on a sidebar link (out of 93, so usually a scroll or a search first: type, then Enter or a click), then choose venue, day or tab on the page because the address carries none; a day's cash-up is roughly menu link, venue, day in the week view, fill, Submit. Today route: one tap on the task's button opens the same form in a sheet. Pepper route: one message ("do today's cash-up") and one tap on the card's Open button.
- The menu is already a per-tenant data structure with descriptions and search words for every page, which is most of what a natural-language navigator needs to choose a destination. What it cannot yet express is the destination's context (which venue, day, week or record).
- Page matching has three implementations (the local search, the nav-search model call, `open_page`'s scorer with its own synonyms), which the project's own rule 12 ("one implementation of each rule") would count as a duplication.
- Store tech (28 links, 26 `/pos/` addresses on mostly one route) is the densest part of the menu; PEPPER_FIRST already suggests splitting it.

### Gaps
- No usage data exists, so which pages people open, how often search is used and how long tasks take cannot be answered from the repository (no `nav_events` table; planned in [docs/PEPPER_FIRST.md:189-197](docs/PEPPER_FIRST.md)).
- PEPPER_FIRST (21 Nov) says the collapsed rail shows 76 links and Store tech has 27; the tree today has 78 second-level links and 28 in Store tech. The difference is one day's additions (the Tech board, 22 Nov); the newer count is from the code.
- Whether sidebar sections are collapsible by default at runtime was not checked in a browser.

## 2. Pepper, the assistant: tools, confirmation, form cards, help, voice, readers, connectors, prompt, tool selection, limits and what it cannot do

### Takeaway
Pepper has 159 staff tools across 16 areas (58 read, 97 change, 4 that plan a new location or open an order), all calling the admin's own routes as the person, with every change behind a Confirm card. Only 10 tools are sent in full per request and the rest are found by tool search; forms, help answers, a day briefing, voice, attachments and two MCP connectors are built, but several of these have only been tested against a stand-in model API.

### Inferences
- Pepper already covers the everyday verbs of most modules (61% of its tools change data) and leaves set-up and design work to pages. An AI-first front door would lean on exactly that split: act by tool where a tool exists, navigate to a page for the rest.
- The tool layer is large and hand-written: 16,323 lines in `api/src/ai` (`wc -l`), one plan / describe / run trio per change tool. Each new capability is a new tool, a prompt line, an activity label and an action label in four different files ([docs/claude/areas/pepper.md:37](docs/claude/areas/pepper.md)).
- Tool search plus a cached, never-edited system prompt is the cost design: 10 full schemas and one 15.6k-character prompt per request instead of 159 schemas. The unit allowance and per-person share are the only brakes on more chat use.

### Gaps
- No measurement of Pepper against the live model exists in the repository (accuracy, tool-search hit rate, latency, cost per turn). The requirement for an evaluation set (K3 in CHAT_FIRST) is not built.
- No record of how often staff use Pepper versus pages (K1, K2 not built).

## 3. Forms and data entry: the patterns in use, whether anything is generated from a schema, where validation lives, and how many forms the sheets and form cards cover

### Takeaway
Forms are hand-built React components with an explicit Save per section, and almost all validation is on the server (560 Zod object schemas in the routes against 7 in the admin). Nothing generates a form from a schema today; the reusable asset is the opposite one: a catalogue of 10 real form panels that Today, the phone app, dashboards and Pepper's cards all mount.

### Cited Findings
- **House rules.** Every save is explicit, each section with its own Save button, no auto-save; destructive actions need a double confirmation; no native browser pop-ups; touch-first with 48 px targets. — [CLAUDE.md "Standard Design Rules" 1-6](CLAUDE.md)
- **Whole-tree saves.** "Whole-tree saves replace everything (a menu, a week's wages, a rota week, a checklist's ticks, a device's settings, a supplier's venues). A caller must send back every field, also the ones it doesn't edit." The API has 97 `app.put(` handlers (grep). Pepper's tools rebuild the whole body for these (for example `menuSaveBody()`, `rotaPlan()`, `recordPlan()`). — [CLAUDE.md rule 13](CLAUDE.md), [docs/claude/areas/pepper.md:13](docs/claude/areas/pepper.md)
- **Hand-built inputs.** `admin/src` has 699 `<input`, 334 `<select` and 87 `<textarea` occurrences, 519 `useMutation(` calls and 692 `api.post/put/patch/delete(` calls; 87 full-screen overlays (`fixed inset-0`) in 50 files (grep counts). — [admin/src](admin/src)

### Inferences
- The server already holds a machine-readable description of nearly every write (560 route schemas, 97 change-tool schemas), but the admin's forms do not read it. A generated form would have to be derived from the server's schemas, since the client has almost none.

- Retail expansion has one concrete hook in the repository (CATALOGUE.md) and it is parked; the vocabulary is restaurant-specific throughout (dishes, covers, sittings, kitchen screens).

### Inferences
- The report catalogue's labels ("Dishes sold", "Supplier orders", "member of staff") are already the reconciled business vocabulary; table and route names are the legacy layer. A framework would most cheaply adopt the catalogue's subject keys as entity names.
- Deep links are the gating work for navigation with context, and they are page-by-page (each page's state must move into, or be seeded from, the address).
- For forms, the low-risk path the code supports is widening the fixed catalogue (10 of F1's 14, then set-up forms) and pre-filling Confirm cards, rather than rendering arbitrary forms from schemas; a generic renderer would bypass the rules that live in the panels.

### Gaps
- No inventory of which pages could take deep links cheaply; PEPPER_FIRST names six to start and says "each needs its own check".
- Whether route Zod schemas could be exported to the admin (as tool schemas are) was not tested.
