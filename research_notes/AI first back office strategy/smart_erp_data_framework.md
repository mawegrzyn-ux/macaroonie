## 1. Metadata-driven platforms: how they describe entities, fields, views, permissions and actions, what is generated, and how the metadata is exposed to AI agents

### Takeaway
Every major platform now exposes its existing metadata (tables, fields, relationships, permissions, automations) to agents through a small set of generic "search the schema, describe it, then read or act" tools, mostly over MCP, with the agent running under the signed-in user's permissions. None of them lets the model act on raw tables alone: writes go through pre-defined, typed actions (Salesforce actions backed by Flow or Apex, Odoo server actions, Dataverse custom APIs, ServiceNow workflows), and the trend through 2026 has been to add more deterministic control around the model, not less.

### Inferences
- The common shape across Dataverse, Frappe, Notion and SAP is: (a) a searchable description of the data model, (b) generic read tools that respect the caller's permissions, (c) writes only through pre-declared actions. A platform that already has a module and permission registry, a report catalogue and API routes with validation schemas has most of the raw material; what it lacks is one registry that joins them and can be searched and described at runtime.
- What these vendors generate from metadata is the plain part (CRUD forms, list views, REST API, permission checks, simple reports). Agent behaviour is not generated: it is authored (topics or subagents, instructions, skills or playbooks) and increasingly scripted deterministically (Salesforce Agent Script). A small team should expect the same split.
- Odoo's warning is the most transferable lesson: a tool's safety has to live in the tool (server-side checks), because the model will sometimes call the wrong one.
- Microsoft's removal of per-purpose tools in favour of generic `search` plus `describe` suggests that "describe the schema on demand" scales better than one tool per table, at least for reads.

## 2. Ontology and action layers: Palantir Foundry and AIP, "system of action" ideas, and what makes an action safe for an agent to call

### Takeaway
The action is the unit of safety: a named, typed operation with its own validation rules (who may run it, with which parameter values, on objects in which state), its side effects attached, and a setting for whether an agent may run it unattended or only after the user confirms. Palantir's action types are the clearest documented example, and MCP's tool annotations, Dataverse's approval-gated deletes and Odoo's warnings all point the same way.

### Cited Findings
- Palantir "submission criteria" are conditions built from the user's context, the action's parameters and object or relation data, combined into logical statements; an action can only be submitted if all its criteria pass; each action type has its own independent criteria; criteria are separate from the permission to edit the action type itself. **[summary]** — [Palantir docs, submission criteria](https://palantir.com/docs/foundry/action-types/submission-criteria/)
- If criteria fail, side effects such as webhooks are not triggered; criteria can carry custom failure messages so the user sees why; criteria, rules and resulting edits can be tried in a test run before applying. **[summary]** — [Palantir docs, action type permissions](https://palantir.com/docs/foundry/action-types/permissions/); [Palantir docs, getting started with action types](https://www.palantir.com/docs/foundry/action-types/getting-started/)
- In Palantir's agent builder the "Action" tool type lets an agent execute an ontology edit, "and this can be set to run automatically or only after the user confirms". A function that edits the ontology cannot be given to an agent directly: it must be wrapped in an action type. A "Request clarification" tool lets the agent pause and ask the user. **[summary]** — [Palantir docs, agent tools](https://palantir.com/docs/foundry/agent-studio/tools); [Palantir community answer](https://community.palantir.com/t/how-does-an-action-type-tool-work-in-palantir-aip/2727)
- AIP Agent Studio was renamed AIP Chatbot Studio in the week of 27 April 2026; Palantir also documents an Ontology MCP and a Palantir MCP for external agents. **[summary]** — [Palantir docs, Chatbot Studio overview](https://palantir.com/docs/foundry/agent-studio/overview/); [Palantir docs, Ontology MCP](https://palantir.com/docs/foundry/ontology-mcp)
- ServiceNow uses "system of action" for the same idea: workflows, approval chains and business rules exposed to agents, each call identity-verified, permission-scoped and audited. Vendor press release. **[summary]** — [ServiceNow press release](https://newsroom.servicenow.com/press-releases/details/2026/ServiceNow-opens-its-full-system-of-action-to-every-AI-Agent-in-the-enterprise/)
- MCP's tool definition carries a name, title, description, `inputSchema`, optional `outputSchema`, optional behaviour `annotations` and an `execution.taskSupport` flag. Clients "MUST consider tool annotations to be untrusted unless they come from trusted servers". Servers MUST validate all inputs, implement access controls, rate limit invocations and sanitise outputs; clients SHOULD prompt for confirmation on sensitive operations and show tool inputs to the user before calling. **[read]** — [MCP specification 2025-11-25, tools (GitHub source)](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/server/tools.mdx)
- MCP separates protocol errors from tool execution errors (`isError: true`); input validation and business-rule failures should be tool execution errors so the model can read them and correct itself. **[read]** — [MCP specification 2025-11-25, tools](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/server/tools.mdx); [MCP 2025-11-25 changelog](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/changelog.mdx)
- Odoo: the AI does not enforce business rules, and a tool runs unconditionally unless its own code prevents it. **[read]** — [Odoo 19 documentation source](https://github.com/odoo/documentation/blob/19.0/content/applications/productivity/ai/server-actions.rst)
- Anthropic advises using programmatic (scripted) tool calling only for tools that are safe to run in parallel or retry, that is, idempotent ones. **[read]** — [Anthropic engineering, advanced tool use, 24 Nov 2025](https://www.anthropic.com/engineering/advanced-tool-use)

### Inferences
- A workable "action definition" for a small team, drawn from the above, has these parts: a stable name and plain description; a typed parameter schema; the permission (module and level) required; preconditions evaluated on the server against the current user and the target record's state, each with a human-readable failure message; a side-effect class (read, reversible write, hard-to-reverse or external effect such as money, email, publishing); a confirmation policy derived from that class; an idempotency rule; a structured result; and, where possible, a declared inverse (undo) action.
- Palantir's rule that agents get actions, never raw edit functions, matches an assistant that calls the same API routes as the UI. The step still missing in most hand-built tool sets is making preconditions, side-effect class and confirmation policy declared data, so the confirm card, the audit entry and the tool description all come from one place.
- "Explain why not" (criteria failure messages returned as tool errors the model can read) is a cheap, high-value feature: it lets the assistant tell the user which rule blocked the action.

### Gaps
- Palantir's object type, link type and function definitions, the action log, and whether actions can be reverted were not read (palantir.com unreachable). Background, unverified: actions can write an action-log object and some edits can be undone by the submitting user.
- The specific MCP annotation names were not shown on the page read. Background, unverified: `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`.
- No independent study was found measuring how much declared preconditions or confirmation steps reduce agent errors.

## 3. Semantic layers for analytics: effect on natural-language-to-query accuracy, and how to give an LLM governed access to metrics

### Takeaway
The 2026 evidence says a curated semantic description of the data adds roughly 17 to 23 percentage points of accuracy over raw schema, and that the modelling work matters more than the model or the query mechanism; the cost is that the layer answers nothing outside what has been modelled. The recommended access pattern is tools that list metrics and dimensions and run a metric query by name, with free SQL as a fallback, not the default.

### Cited Findings
- dbt Labs benchmark (April 2026, vendor testing its own product): on an insurance dataset, 11 questions run 20 times each, Claude Sonnet 4.6 scored 98.2% through the semantic layer against 90.0% writing SQL over the same tables, once three extra models covered every question; GPT-5.3 Codex scored 84.1% with text-to-SQL. The authors state the layer "can only answer questions that fall within the scope of what's been modeled". **[summary]** — [dbt developer blog, semantic layer vs text-to-SQL 2026](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)
- In the same benchmark, better schema modelling alone (no semantic layer) moved text-to-SQL accuracy from 64.5% to 90.0%; before the extra models were added, the semantic layer could not answer questions needing too many entity hops. **[summary]** — [HackerNoon summary of the benchmark](https://hackernoon.com/why-better-schema-modeling-beats-better-text-to-sql-models)
- An academic paired benchmark (arXiv 2604.25149, 2026): 100 questions on the Contoso dataset, three frontier models; supplying a semantic-layer document improved accuracy by 17 to 23 percentage points for every model, and the presence of that document "accounts for essentially all of the significant variance", with model choice mattering little. **[summary]** — [arXiv 2604.25149](https://arxiv.org/abs/2604.25149)
- The Open Semantic Interchange specification was first published on 27 January 2026 under Apache 2; the project entered the Apache Incubator as Apache Ossie on 10 July 2026. **[summary]** — [Snowflake blog, OSI specs finalized](https://www.snowflake.com/en/blog/open-semantic-interchanges-specs-finalized/); [Apache Ossie site](https://ossie.apache.org/)
- The Ossie core spec (version shown as 0.3.0.dev0, still changing) defines a semantic model as datasets (with a source, primary key and fields), fields (expression, optional dimension flag, label, description, datatype), metrics (name plus aggregation expression, dataset-scoped or model-scoped), relationships (from and to datasets with matching column lists) and an `ai_context` that can sit on any of them, with recommended keys `instructions`, `synonyms` and `examples`. Expressions have a primary SQL form and optional per-dialect variants; vendor-specific data goes in `nonportable_extensions`. **[read]** — [Ossie core spec](https://github.com/open-semantic-interchange/OSI/blob/main/core-spec/spec.md)
- Reference converters exist for dbt, GoodData, Polaris and Salesforce; the repository also holds a Python SDK, validation tooling and a compliance grader. **[read]** — [Ossie repository](https://github.com/open-semantic-interchange/OSI)
- The dbt MCP server gives an agent semantic-layer tools (`list_metrics`, `get_dimensions`, `get_entities`, `get_dimension_values`, `query_metrics`, `get_metrics_compiled_sql`, `list_saved_queries`) alongside separate SQL tools (`execute_sql`, `text_to_sql`), so a client can request metrics by name with filters and grouping, and inspect the compiled SQL without running it. **[read]** — [dbt MCP server repository](https://github.com/dbt-labs/dbt-mcp)
- Microsoft takes the other route for operational data: the Dataverse MCP server gives agents a `read_query` tool limited to supported SQL SELECT statements, under the caller's security context. **[read]** — [Microsoft docs source on GitHub](https://github.com/MicrosoftDocs/powerapps-docs/blob/main/powerapps-docs/maker/data-platform/data-platform-mcp.md)
- SAP translates agent queries from an ontology (SPARQL) into SQL at runtime. **[summary]** — [SAP Architecture Center reference architecture](https://architecture.learning.sap.com/docs/ref-arch/e15602)

### Inferences
- A hand-written catalogue of about 130 subjects with fields, measures and links, from which both a report builder and an LLM build reports, is already a semantic layer in the sense these benchmarks test. The evidence supports keeping it and deepening it, not replacing it with text-to-SQL over 240 tables.
- The cheapest accuracy gain suggested by the Ossie spec and the benchmarks is descriptive: per-field and per-measure synonyms, instructions and worked examples (the `ai_context` idea), plus an explicit "this question is outside the catalogue" path so the assistant says so instead of improvising.
- Adopting Ossie as an internal format is premature for a small team (the spec is at 0.3 and still changing). Shaping the catalogue so it could be exported to it later costs little: datasets, fields, metrics, relationships and AI context map closely to subjects, fields, measures and links.
- Both published benchmarks are small (11 and 100 questions). The direction is consistent; the exact percentages should not be quoted as general truths.

### Gaps
- Cube, LookML and AtScale: no 2025 or 2026 source could be read. Background, unverified and older: AtScale (2023 to 2024) claimed 20% to 92.5% accuracy with its semantic layer on a TPC-DS-based test; data.world (2023) reported GPT-4 at about 16% on enterprise SQL questions without and 54% with a knowledge graph; Google has claimed Looker's semantic layer cuts generative-AI query errors by about two-thirds. All three are vendor studies.
- A counter-claim appeared in search summaries (MotherDuck reporting 95% on 500 BIRD questions using schema alone, against a 92.96% human baseline, and arguing that good data modelling is the semantic layer), but the originating page was not identified or read.
- The dbt blog and the arXiv paper could not be opened; method details, the three model names in the arXiv study and its hallucination figures are missing.

## 4. Protocols and contracts for agents: MCP in 2025 to 2026, agent-to-agent protocols, JSON Schema as the contract, and what to do with 150+ tools

### Takeaway
MCP is the settled contract between agents and business systems, and its July 2026 revision made it stateless, moved tasks and interactive UI ("MCP Apps") into extensions, and allowed full JSON Schema for tool inputs. For a catalogue of 150+ tools the consistent advice is: do not load every definition up front (search-and-load on demand), consolidate tools around jobs instead of endpoints, keep a few always loaded, add usage examples to the difficult ones, and consider code execution only for read-heavy multi-step work.

### Cited Findings

MCP revisions
- 2025-11-25 revision: added URL-mode elicitation, experimental tasks (durable requests with polling), tool calling inside sampling, OAuth Client ID Metadata Documents as the recommended client registration, incremental scope consent, icons, guidance on tool names, default values in elicitation schemas, JSON Schema 2020-12 as the default dialect, and the rule that input validation errors are tool execution errors so models can self-correct. **[read]** — [MCP 2025-11-25 changelog (GitHub source)](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/changelog.mdx)
- 2026-07-28 revision (release candidate locked 21 May 2026, final dated 28 July 2026): the protocol is stateless (no initialize handshake, no session id; version and capabilities travel with each request), so any server instance can handle any request; servers that need state return an explicit handle (the example given is a `basket_id`) that the model passes back. **[read]** — [MCP blog, 2026-07-28 release candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)
- Same revision: a server asks the user for input by returning a result of type `input_required` with the requests and an opaque state; the client re-issues the call with the answers (this replaces held-open server-to-client requests). Tasks moved out of the core into an official extension (`tasks/get`, `tasks/update`, `tasks/cancel`; the server decides when a call runs as a task). Roots, sampling and logging are deprecated. Tool `inputSchema` and `outputSchema` support full JSON Schema 2020-12 including `oneOf`, conditionals and `$ref`. Authorization was hardened (issuer validation per RFC 9207 and five further changes). **[read]** — [MCP blog, 2026-07-28 release candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)
- Secondary sources differ on whether 2026-07-28 was still a candidate or final at the time they wrote; later ones describe it as final. **[summary]** — [Google Developers blog on the stateless update](https://developers.googleblog.com/scaling-ai-agent-infrastructure-with-the-mcp-stateless-updates/); [WorkOS summary](https://workos.com/blog/mcp-stateless-spec-2026-07-28)

Structured input from the user (elicitation) and UI
- Elicitation form mode: the server sends a message and a `requestedSchema` that must be a flat object of primitive properties only (strings with length, pattern and format such as email or date; numbers with minimum and maximum; booleans; single or multi-select enums; defaults allowed). Nested objects and arrays of objects are not allowed. The user can accept, decline or cancel, and must be able to review and edit before sending. Secrets and payment credentials must never be requested in form mode; they go through URL mode, where the user is sent to an external page the client and model cannot see. **[read]** — [MCP specification 2025-11-25, elicitation (GitHub source)](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/client/elicitation.mdx)
- MCP Apps (official extension, 26 January 2026): a tool points at a `ui://` resource of bundled HTML and JavaScript; the host renders it in a sandboxed iframe and talks to it by JSON-RPC over postMessage; the app can receive tool results, call server tools, update the model's context and send follow-up messages. Hosts can review templates before rendering, log every message, and require user approval for tool calls the UI starts. Launch hosts were Claude, Goose, VS Code Insiders and ChatGPT; it standardises patterns from MCP-UI and the OpenAI Apps SDK. **[read]** — [MCP blog, MCP Apps, 26 Jan 2026](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/); [MCP Apps repository](https://github.com/modelcontextprotocol/ext-apps)
- Google's A2UI (protocol v1.0, Apache 2.0) is the declarative alternative: the agent emits UI as validated data composed from a catalogue of components the app developer approved, rendered natively (Lit, React, Angular, Flutter, SwiftUI); arbitrary executable code is disallowed. It can render inside MCP tool results. **[read]** — [A2UI repository](https://github.com/google/A2UI)
- A vendor guide sorts generative UI into three patterns: static (the front end owns the components; the agent picks one and fills it with data), declarative (A2UI and similar) and open-ended (MCP Apps, where the agent side returns a whole UI surface), trading consistency and safety for flexibility as you move along. **[summary]** — [CopilotKit, developer's guide to generative UI in 2026](https://www.copilotkit.ai/blog/the-developer-s-guide-to-generative-ui-in-2026)

Agent-to-agent
- A2A is an open protocol for agents built on different frameworks to work together as agents, not as tools: discovery through Agent Cards, JSON-RPC 2.0 over HTTP, streaming and push notifications. It is a Linux Foundation project shown as part of the Agentic AI Foundation, and says it "complements MCP". **[read]** — [A2A repository](https://github.com/a2aproject/A2A)
- A2A reached version 1.0 in early 2026 and the Linux Foundation counted more than 150 supporting organisations at its first anniversary (April 2026); the figure counts supporters, not production deployments, and one analysis calls MCP the more mature protocol with the larger ecosystem. **[summary]** — [Linux Foundation press release](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year); [independent analysis](https://philippdubach.com/posts/mcp-vs-a2a-in-2026-how-the-ai-protocol-war-ends/)

Scaling a tool catalogue
- Measured cost of definitions: a five-server setup with 58 tools used about 55,000 tokens before the conversation started; Anthropic saw 134,000 tokens of tool definitions internally before optimising. **[read]** — [Anthropic engineering, advanced tool use, 24 Nov 2025](https://www.anthropic.com/engineering/advanced-tool-use)
- Tool search (definitions marked to load on demand, found through a search tool): about 85% fewer tokens, and accuracy on Anthropic's MCP evaluations rose from 49% to 74% (Opus 4) and from 79.5% to 88.1% (Opus 4.5). Use it when definitions exceed about 10,000 tokens or there are more than about ten tools; keep the three to five most-used tools always loaded; write clear names and descriptions because search matches on them; tell the model in the system prompt what categories of tool exist. Vendor's internal tests. **[read]** — [Anthropic engineering, advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- Tool-use examples (one to five realistic sample calls on a tool definition) raised accuracy on complex parameter handling from 72% to 90% in internal testing. **[read]** — [Anthropic engineering, advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- Programmatic tool calling (the model writes one script that calls several tools; intermediate results stay out of the conversation): 37% fewer tokens on complex research tasks, small accuracy gains; suited to large data, three or more dependent calls, filtering and parallel work; not suited to single calls or where the model must reason over every intermediate result. **[read]** — [Anthropic engineering, advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- Suggested order for a high-volume agent: prompt caching on tool definitions from the start; tool search at ten or more tools; context editing for long conversations; programmatic calling when repetitive chains appear. **[read]** — [Claude platform docs, manage tool context](https://platform.claude.com/docs/en/agents-and-tools/tool-use/manage-tool-context)
- Code execution against tool APIs: presenting tools as code files the agent explores cut one example workflow from 150,000 tokens to 2,000 (98.7%); the stated costs are a secure sandbox with resource limits and monitoring, "operational overhead and security considerations that direct tool calls avoid". **[read]** — [Anthropic engineering, code execution with MCP, 4 Nov 2025](https://www.anthropic.com/engineering/code-execution-with-mcp)
- Tool design: do not build tools that only wrap API endpoints; consolidate multi-step work into one tool (the example is `schedule_event`, which finds availability and books); start with a few high-impact tools; namespace by service and resource; return names, not opaque ids; offer concise and detailed response formats; paginate and truncate with sensible defaults; make error messages specific and actionable; describe each tool as you would to a new hire; and drive changes from an evaluation with held-out tasks. **[read]** — [Anthropic engineering, writing tools for agents, 11 Sep 2025](https://www.anthropic.com/engineering/writing-tools-for-agents)
- The MCP project's client guidance describes the same two patterns (progressive discovery through a search meta-tool; code mode) and notes OpenAI and Anthropic support them natively; MuleSoft ships a gateway policy that hides a server's tool list behind discovery tools. **[summary]** — [MCP client best practices](https://modelcontextprotocol.io/docs/develop/clients/client-best-practices); [MuleSoft gateway policy](https://docs.mulesoft.com/gateway/latest/policies-included-mcp-progressive-disclosure)
- Counterpoints from practitioners: progressive disclosure only pays once definitions take a share of the context worth recovering, and a generic dispatch tool becomes the most privileged tool on the server, so it needs authorization and audit at execution time. **[summary]** — [AWS Builder Center post](https://builder.aws.com/content/35xb5uKp4NFWoJPGf8p3SGldhG1/an-agent-with-too-many-tools); [dev.to practitioner post](https://dev.to/halemogpa/your-mcp-server-doesnt-need-to-put-all-its-tools-in-the-models-context-3g)
- Agent Skills apply the same idea to instructions: only a name and description are loaded up front, the body when relevant, linked files and scripts when needed. Microsoft's Dataverse "business skills" are the business-platform equivalent. **[read]** — [Anthropic engineering, Agent Skills, 16 Oct 2025](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills); [Microsoft Power Platform blog, 5 May 2026](https://www.microsoft.com/en-us/power-platform/blog/2026/05/05/dataverse-agent-data-platform/)

### Inferences
- For about 150 hand-written tools the low-risk sequence is: (1) cache the definitions; (2) group tools by module with consistent prefixes and defer most of them behind a search step, keeping a handful always loaded; (3) merge overlapping tools around jobs; (4) add examples to the tools whose parameters go wrong most; (5) only then consider scripted calling, and only for read-only tools.
- A tool registry that already records module and permission can drive the search step for free: filter the candidate tools by what this user may do before the model ever sees them. That shrinks the catalogue and removes a class of refusals.
- MCP elicitation is a ready-made contract for "dynamically generated forms" in a chat: a flat schema of primitive fields that the user reviews and submits. Its deliberate limits (no nesting, no arrays of objects) are a useful guide to what should be generated and what should stay a hand-built form card.
- For a first-party assistant inside the product, the "static" pattern (the agent chooses a pre-built card or form and fills it) is the safest fit and is what confirm cards and form cards already are. MCP Apps matter mainly for showing the product's cards inside third-party assistants such as Claude or ChatGPT.
- A2A matters only if the platform's assistant must work with agents run by other companies (suppliers, delivery platforms, accountants). It is not needed for the internal framework.
- The stateless MCP revision fits a multi-process Node deployment well: no session affinity, state passed as explicit handles.

### Gaps
- Cloudflare's "code mode" figures and other vendors' results could not be read.
- No independent (non-vendor) benchmark of tool search or code execution accuracy was found; the numbers above are Anthropic's own.
- OpenAPI-to-MCP generators and their pitfalls: not sourced beyond Anthropic's "do not just wrap endpoints" advice.
- The 2025-06-18 MCP revision (structured tool output and elicitation first introduced, OAuth resource-server changes) was not read directly; its contents are inferred from the later pages.

## 5. One definition, many surfaces: schema-first frameworks, admin generators and schema-driven forms; what works and where they stop

### Takeaway
Generating the database table, API, validation, permission checks, list view and simple form from one definition works and is in production at scale (Frappe, Odoo, Payload, Directus); generating complex, stateful or highly designed screens from schema does not, and every mature tool ships an escape hatch to hand-written components. The practical pattern is "generate the plain 80%, hand-build the rest, and make the same definition feed the AI tools".

### Cited Findings
- Frappe: model metadata yields an automatic REST API for all models, a customisable admin interface, role-based permissions and a report builder, with server-side scripting and client-side JavaScript for what the metadata cannot express. **[read]** — [Frappe Framework repository](https://github.com/frappe/frappe)
- Directus is database-first: REST and GraphQL APIs are "automatically generated from your database schema" (Postgres and others), with a management studio, policy-based access control down to field level that "applies to both human users and AI agents", extension points (custom endpoints, hooks, interfaces, modules) and a native MCP server under the same role-based permissions. **[read]** — [Directus repository](https://github.com/directus/directus)
- Payload is code-first in TypeScript: a config gives "a full TypeScript backend and admin panel instantly" with generated types, field-level access control, hooks and conditional field logic, and the admin can be extended with custom React components. **[read]** — [Payload repository](https://github.com/payloadcms/payload)
- react-admin positions itself differently: "a library of loosely coupled React components and hooks exposing reusable controller logic" over a data-provider adapter (45+ adapters), where pages are written from components and any component can be replaced. **[read]** — [react-admin repository](https://github.com/marmelab/react-admin)
- Zod 4 converts schemas to JSON Schema natively (`z.toJSONSchema`, targets Draft 2020-12, Draft-07 and OpenAPI 3.0); metadata registered with `.meta()` (title, description, examples, custom fields) is copied into the output; types with no JSON equivalent (dates, transforms, maps, sets, custom checks, bigint) throw unless handled; an `io` option emits the input shape or the output shape. **[read]** — [Zod documentation source, JSON Schema](https://github.com/colinhacks/zod/blob/main/packages/docs/content/json-schema.mdx)
- MCP now accepts full JSON Schema 2020-12 for tool inputs, but limits forms the user fills in (elicitation) to flat primitive fields. **[read]** — [MCP blog, 2026-07-28 release candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/); [MCP elicitation spec](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/client/elicitation.mdx)
- Known limits of schema-driven forms: they work for small to medium forms, and teams "hit the same architectural limits" once forms become dynamic, state-dependent or large; conditional logic (schema branches switched at runtime) and layout are the two recurring pain points. Source is a competing vendor, so one-sided. **[summary]** — [SurveyJS article on dev.to](https://dev.to/surveyjs/react-json-schema-forms-in-practice-why-they-break-down-and-how-surveyjs-fixes-the-architecture-17ik)
- JSON Forms answers the layout problem by separating a data schema from a UI schema; a JSON Schema community discussion records the same complaint about tools that mix the two. **[summary]** — [JSON Schema organisation discussion 70](https://github.com/orgs/json-schema-org/discussions/70); [comparison of schema-driven form libraries](https://dev.to/yanggmtl/schema-driven-forms-in-react-comparing-rjsf-json-forms-uniforms-formio-and-formitiva-2fg2)
- A real team's retreat: Talend's form library proposal found that "Json is really limited and static", that front-end developers ended up "writing tons of json instead of components" without covering complex cases, and planned to keep schema-driven generation only for back-end-controlled forms. Older (undated wiki page, pre-2025). **[summary]** — [Talend UI wiki, UIForm V3](https://github.com/Talend/ui/wiki/UIForm-V3)
- A 2026 design essay argues for an agentic standard so teams "stop shipping the same form four different times" (title only seen). **[summary]** — [UX Collective essay](https://uxdesign.cc/the-call-for-an-agentic-standard-we-need-to-stop-shipping-the-same-form-four-different-times-be5b9d40e370)

### Inferences
- For an existing codebase with request validation schemas, the lowest-cost "single definition" is the validation schema itself, enriched with metadata (label, help text, examples, field kind, option source, permission) and converted to JSON Schema. That one object can validate the API request, define the assistant's tool, drive a generated simple form or chat form, and document the field for search.
- Things that cannot cross the conversion (dates, transforms, custom refinements) need a convention: validate again on the server after the generated form or the model supplies values. The server-side schema stays the authority.
- Keep two schemas apart, as JSON Forms does: what the data is, and how it is laid out. Layout hints should be optional; where a screen needs more than hints, it is hand-built and registered as the form for that action.
- A realistic boundary for generation: single-record create and edit forms with flat or lightly grouped fields, list views with filters, pickers and confirm cards. Not for generation: timelines, drag-and-drop designers, a till, rota grids, multi-step wizards with cross-field state.
- The frameworks that succeed at scale (Frappe, Odoo) were built metadata-first from day one. Retrofitting a full runtime metadata engine onto 240 existing tables is a rewrite; a registry that describes what already exists is not.

### Gaps
- Refine, and the official "limitations" statements of react-jsonschema-form and JSON Forms: not read. Background, unverified: the react-jsonschema-form documentation itself says that if you know your data in advance and want a toolkit for building forms for it, you might look elsewhere.
- No quantitative data found on what share of screens mature low-code platforms generate versus hand-build.
- Odoo's model and view definitions (XML view architectures, inheritance) were not read in this session.

## 6. Tenant customisation: custom fields, custom objects, per-tenant workflows, and how AI copes with tenant-specific schemas

### Takeaway
Platforms with tenant-defined schema make the agent discover the schema at runtime (search then describe) under the caller's permissions, instead of baking the schema into tool definitions; tenant-written descriptions, synonyms and natural-language "skills" are how tenant-specific meaning reaches the model. Evidence on how well this works is almost entirely vendor description.

### Cited Findings
- Dataverse lets an agent inspect and even change the tenant's data model: `search` and `describe` for table schemas, `create_table` / `update_table` / `delete_table` (deletion only after explicit user approval), with schema changes refreshing in the search index in the background. **[read]** — [Microsoft docs source on GitHub](https://github.com/MicrosoftDocs/powerapps-docs/blob/main/powerapps-docs/maker/data-platform/data-platform-mcp.md); [Microsoft Power Platform blog, 5 May 2026](https://www.microsoft.com/en-us/power-platform/blog/2026/05/05/dataverse-agent-data-platform/)
- Dataverse "business skills" are tenant-authored natural-language playbooks (steps, required information, business rules) that connected agents discover automatically; they are governed with built-in controls. Public preview. **[read]** — [Microsoft Power Platform blog, 5 May 2026](https://www.microsoft.com/en-us/power-platform/blog/2026/05/05/dataverse-agent-data-platform/)
- Frappe's MCP server gives agents tools to "discover schemas", read and change documents and call existing methods "as a site user", so per-site customisations are found at runtime under that user's permissions. **[read]** — [Frappe Framework repository](https://github.com/frappe/frappe)
- Notion exposes each database's property schema through a retrieve tool, and the hosted server respects each user's existing permissions. **[read]** — [Notion MCP server repository](https://github.com/makenotion/notion-mcp-server)
- Odoo: tenants add AI fields through Studio or property fields, define automation rules per model in Studio, and turn their own server actions into AI tools by declaring an argument schema. **[summary]** — [Odoo 19 AI documentation](https://www.odoo.com/documentation/19.0/applications/productivity/ai/server-actions.html); **[read]** — [Odoo 19 documentation source, automation rules](https://github.com/odoo/documentation/blob/19.0/content/applications/studio/automated_actions.rst)
- Airtable's agent builds the schema itself (tables, interfaces, automations) from a description, with agent permissions controlling what agents can read and write. Vendor material. **[summary]** — [Airtable fall release](https://www.airtable.com/articles/fall-release)
- The Ossie semantic spec provides places for tenant or vendor specifics that tools must tolerate: `ai_context` (instructions, synonyms, examples) on any element and `nonportable_extensions` that core semantics must not depend on. **[read]** — [Ossie core spec](https://github.com/open-semantic-interchange/OSI/blob/main/core-spec/spec.md)
- Salesforce states that every field, label and automation a customer builds carries metadata the agent can read. Marketing statement. **[summary]** — [Salesforce, How Agentforce Works](https://www.salesforce.com/uk/agentforce/how-it-works/)

### Inferences
- If tenant custom fields are introduced, they should be registered in the same field registry as built-in fields (name, label, type, description, synonyms, which subject they belong to), so reports, generated forms and the assistant pick them up without new code. The model then learns a tenant's fields through a describe step, not through a per-tenant prompt.
- Custom objects (whole new tables per tenant) are a much larger commitment than custom fields: they need generated storage, permissions, forms and reports. The vendors that offer them built metadata engines first. For a small team, custom fields on existing subjects plus tenant-authored playbooks cover most of the value.
- Tenant-written text (field labels, descriptions, playbooks) becomes model input. It must be treated as data with a clear boundary, since a tenant user could write instructions into it (see section 8).
- Letting an agent change schema (as Dataverse and Airtable do) is a separate, riskier capability than letting it use schema; nothing found suggests an SMB platform needs it early.

### Gaps
- No practitioner write-up was found on storage choices for tenant custom fields in a Postgres row-level-security design (JSONB columns versus attribute tables) or on their effect on reporting; the search budget ended before this could be covered.
- No independent evaluation of agent accuracy on tenant-customised schemas versus standard schemas was found.
- Salesforce custom objects and fields with Agentforce, and ServiceNow custom tables with its agents: not sourced.

## 7. Industry data standards for hospitality and retail: which matter for an SMB platform

### Takeaway
Only one item is both confirmed and dated: UK mandatory e-invoicing for domestic B2B and B2G VAT invoices from 1 April 2029 over Peppol, which makes structured supplier and sales invoices a framework requirement. The rest of this question (GS1 product and allergen data, schema.org menus, ARTS, HTNG, Open Banking, allergen and nutrition rules) could mostly not be researched in this session and should be verified before the report relies on it.

### Cited Findings
- The UK government confirmed Peppol as the interoperability framework (reported 23 June 2026), and HMRC published an implementation roadmap dated 28 October 2026 confirming mandatory e-invoicing through a Peppol-based four-corner model from April 2029. **[summary]** — [KPMG tax news, October 2026](https://kpmg.com/us/en/taxnewsflash/news/2026/10/uk-b2b-e-invoicing-roadmap-april-2029.html); [VATupdate, 1 Nov 2026](https://www.vatupdate.com/2026/11/01/united-kingdom-sets-2029-vat-e-invoicing-roadmap-with-hmrc-as-peppol-authority/)
- Scope and shape: domestic B2B and B2G VAT invoices from 1 April 2029; no invoice clearance or real-time reporting to HMRC at launch (still under consultation); HMRC becomes the UK Peppol Authority; primary legislation intended for Finance Bill 2026, expected to become law in spring 2027. **[summary]** — [LexisNexis news, 30 Oct 2026](https://www.lexisnexis.co.uk/legal/news/hmrc-dbt-publish-roadmap-for-vat-e-invoicing-from-2029); [Avalara, April 2026](https://www.avalara.com/blog/en/europe/2026/04/uk-mandatory-e-invoicing-2029.html)
- Format: the standard will be based on EN 16931 and Peppol BIS Billing 3.0, with a UK variant (PINT UK) seen as likely; PDF invoices do not meet HMRC's definition of an e-invoice; access points will need OpenPeppol certification and UK accreditation; further EDI guidance is promised for autumn 2027. Vendor blogs; dates vary slightly between them. **[summary]** — [Causeway](https://www.causeway.com/blog/uk-e-invoicing-peppol-confirmed); [Tradeshift](https://tradeshift.com/resources/compliance/uk-e-invoicing-mandate-2026-update); [OpenText](https://blogs.opentext.com/e-invoicing-mandates-and-updates-united-kingdom/)
- The GS1 Web Vocabulary is published as an "external extension to schema.org": its `gs1:Product` is equivalent to `schema:Product`, with subclasses (including a food, beverage and tobacco branch), properties, code lists with global URIs, and link types used by GS1 Digital Link; development versions run to v1.16. **[read]** — [GS1 Web Vocabulary repository](https://github.com/gs1/WebVoc)
- The UK Open Banking read/write specifications are published as OpenAPI 3.0 and cover account information, payment initiation, confirmation of funds, variable recurring payments and event notifications. **[read]** — [Open Banking UK specifications repository](https://github.com/OpenBankingUK/read-write-api-specs)
- Peppol BIS Billing 3.0 is maintained publicly by OpenPeppol (rules, structure, mappings, guide). **[read]** — [OpenPeppol BIS Billing 3.0 repository](https://github.com/OpenPEPPOL/peppol-bis-invoice-3)

### Inferences
- The purchasing and invoice parts of the data framework should hold invoices as structured data that maps to EN 16931 fields (supplier and buyer identifiers, VAT breakdown by rate, line items with units and quantities), because from April 2029 supplier invoices will arrive that way and any sales invoices the platform issues for tenants must leave that way. A small platform would normally connect through a certified access-point provider and not become one.
- Because the mandate has no real-time reporting at launch, the 2029 requirement is about exchange format, not tax reporting; the design should leave room for reporting later.
- For product and ingredient data, the cheap, durable step is to keep a place for the global trade item number (GTIN) on inventory items and supplier products, so that supplier catalogues, barcode scans and any later allergen or nutrition feeds can be matched; adopting a full retail data model is not justified by anything found here.

### Gaps
- Not researched (search budget ended); all of the following is background, unverified, and should be checked: GS1's programme for 2D barcodes at retail point of sale by the end of 2027; GDSN as the supplier-to-buyer product data network carrying allergen and nutrition attributes, with UK foodservice data pools; schema.org's Menu, MenuSection, MenuItem, NutritionInformation and diet-suitability terms for public menu pages; the former ARTS retail operational data model now under OMG; HTNG now part of the hotel association AHLA and mostly hotel-focused; the 14 regulated allergens and the UK prepacked-for-direct-sale labelling rules; calorie labelling for large out-of-home food businesses in England.
- Whether commercial variable recurring payments are live for merchants in the UK in 2026, and their relevance to supplier payments or collections: not researched.
- The primary HMRC roadmap document on gov.uk could not be opened; all e-invoicing detail comes through secondary sources.

## 8. Governance for agents acting on business data

### Takeaway
The settled practices are: the agent acts as the signed-in user with that user's permissions enforced on the server; actions are tiered by consequence and only the consequential ones need explicit approval of the specific change; every attempt is logged; writes carry idempotency keys; and behaviour is regression-tested by checking end state, not what the agent says. Prompt injection is not solved, so anything untrusted the agent reads (including tenant-entered text) must not be able to trigger consequential actions by itself.

### Cited Findings

Identity and permissions
- Agents acting for a user carry that user's context and authorizations (SAP); the hosted Notion server respects each user's existing permissions; Frappe's agent tools run "as a site user"; Directus applies the same role-based permissions to AI as to users; ServiceNow says every agent action is identity-verified, permission-scoped and auditable. **[summary]** — [SAP Architecture Center FAQ](https://architecture.learning.sap.com/docs/ai-native-north-star-architecture/frequently-asked-questions); **[read]** — [Notion MCP server repository](https://github.com/makenotion/notion-mcp-server); [Frappe repository](https://github.com/frappe/frappe); [Directus repository](https://github.com/directus/directus); **[summary]** — [ServiceNow press release](https://newsroom.servicenow.com/press-releases/details/2026/ServiceNow-opens-its-full-system-of-action-to-every-AI-Agent-in-the-enterprise/)
- OWASP's principle of "least agency": grant an agent only the minimum autonomy needed for safe, bounded tasks, and only the permissions its declared task requires. **[summary]** — [Aikido on the OWASP agentic top 10](https://aikido.dev/blog/owasp-top-10-agentic-applications); [HUMAN Security on the OWASP agentic top 10](https://www.humansecurity.com/learn/blog/owasp-top-10-agentic-applications/)

Threat lists and prompt injection
- The OWASP Top 10 for Agentic Applications 2026 was published on 9 December 2025 by the OWASP GenAI Security Project with more than 100 contributors. Entries confirmed by name in the sources seen: ASI01 Agent Goal Hijack, ASI02 Tool Misuse and Exploitation, ASI03 Identity and Privilege Abuse, ASI04 Agentic Supply Chain Vulnerabilities, ASI05 Unexpected Code Execution, ASI09 Human-Agent Trust Exploitation, ASI10 Rogue Agents; memory poisoning and insecure inter-agent communication are also categories. **[summary]** — [OWASP GenAI Security Project](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/); [TechRepublic coverage](https://www.techrepublic.com/article/news-owasp-ai-agent-risk-list/)
- The core design principle from the 2025 "design patterns" paper: once an agent has ingested untrusted input, it must be constrained so that input cannot trigger consequential actions; defences that rely on detecting attacks are likely to be brittle. The paper gives six patterns and ten case studies. **[summary]** — [arXiv 2506.08837, June 2025](https://arxiv.org/abs/2506.08837); [Simon Willison's review, 13 June 2025](https://simonwillison.net/2025/Jun/13/prompt-injection-design-patterns/)
- Google's CaMeL code (the "defeating prompt injections by design" paper) is published as a research artefact only: the interpreter "likely contains bugs", "might not be fully secure", and is unsupported. **[read]** — [CaMeL repository](https://github.com/google-research/camel-prompt-injection)
- Anthropic (24 November 2025) states that prompt injection "is far from a solved problem"; against an adaptive attacker in browser use, its best model with improved safeguards was still successfully attacked 1.4% of the time (8.0% with the model alone), and it notes that roughly 1% "still represents meaningful risk". Vendor's own measurement. **[read]** — [Anthropic research, prompt injection defenses](https://www.anthropic.com/research/prompt-injection-defenses)
- Skills, playbooks and tool descriptions are themselves an attack surface: install only from trusted sources and review bundled content; MCP clients must treat tool annotations from untrusted servers as untrusted. **[read]** — [Anthropic engineering, Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills); [MCP specification, tools](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/server/tools.mdx)

Approval, idempotency, audit, undo
- Anthropic's agent framework (4 August 2025): humans keep control before high-stakes decisions; read-only by default with approval before modifying; per-action approval or persistent permission for trusted routine tasks; the user can stop and redirect at any time; planned actions shown as a visible checklist; administrators control which connectors and tools are allowed. **[read]** — [Anthropic, framework for safe and trustworthy agents](https://www.anthropic.com/news/our-framework-for-developing-safe-and-trustworthy-agents)
- MCP: clients should prompt for confirmation on sensitive operations and show the tool inputs before the call; servers must validate inputs, enforce access control and rate limit; UI-initiated tool calls in MCP Apps go through the same audit and consent path as direct calls. **[read]** — [MCP specification, tools](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-11-25/server/tools.mdx); [MCP blog, 2026-07-28 release candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)
- Practitioner consensus (blogs, not standards): gate by consequence, not blanket approval, because approving every call causes fatigue and rubber-stamping; one proposed ladder runs from read-only (audit only), through reversible internal changes (sampled review) and material but reversible changes (named approval plus idempotency), to external or hard-to-reverse actions (policy re-check and receipt verification). Re-check policy immediately before the write, since it can change between proposal and approval. Approve the specific diff or dry-run output, not the agent's explanation. Use idempotency keys with stored results so retries and resumed workflows do not repeat side effects. Keep an append-only log with one record per attempt, including the dry-run, key, approval decision and result. Register compensating actions before enabling destructive ones. **[summary]** — [DevOps.com, durable change-control gate for AI agents](https://devops.com/how-to-build-a-durable-change-control-gate-for-ai-agents/); [practitioner post, dry-run and idempotency approval ladder, March 2026](https://my-slops.github.io/Blog/posts/2026/03/the-dry-run-idempotency-approval-ladder-for-ai-agents); [dev.to, propose anything, execute almost nothing](https://dev.to/miz_mohammad/propose-anything-execute-almost-nothing-how-to-let-ai-agents-act-on-systems-of-record-3do1); [dev.to, every agent disaster was a write without a checkpoint](https://dev.to/connor_gallic/every-ai-agent-disaster-this-year-was-a-write-without-a-checkpoint-3dgh); [Drata, human in the loop for AI agents](https://drata.com/learn/agent-gov/human-in-the-loop-for-ai-agents)
- Platform examples of the same tiering: Dataverse requires explicit user approval for delete tools and advises treating write tools differently from read tools; Palantir lets each action be set to run automatically or only after confirmation. **[read]** — [Microsoft Power Platform blog, 8 June 2026](https://www.microsoft.com/power-platform/blog/2026/06/08/dataverse-mcp-server-understanding-the-new-tool-shape/); **[summary]** — [Palantir docs, agent tools](https://palantir.com/docs/foundry/agent-studio/tools)

Evaluation and regression testing
- Anthropic (9 January 2026): start with 20 to 50 simple tasks drawn from real failures; make each unambiguous with a reference solution; include cases where the behaviour should and should not happen; grade the final state of the environment (was the refund recorded?) and not a fixed sequence of steps or the agent's own account; combine state checks, tool-call checks, transcript limits and rubric grading; run each trial from a clean environment; use a second model to play the user in multi-turn tests. **[read]** — [Anthropic engineering, demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Capability evals start with a low pass rate and graduate into regression suites that should sit near 100%; for customer-facing consistency use "all k trials pass" (a 75% per-trial success rate gives about 42% for three out of three). **[read]** — [Anthropic engineering, demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Tool changes should be driven by an evaluation with realistic multi-call tasks and held-out test sets, tracking accuracy, runtime, number of tool calls, tokens and errors. **[read]** — [Anthropic engineering, writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)

Metering
- Microsoft meters agent access per tool call (Copilot credits, attributed to the calling service), which is one working model of rate and spend control at the tool boundary. **[read]** — [Microsoft docs source on GitHub](https://github.com/MicrosoftDocs/powerapps-docs/blob/main/powerapps-docs/maker/data-platform/data-platform-mcp.md)

### Inferences
- An assistant that changes data only through the same API routes as the UI already satisfies the most important control (the user's own permissions, enforced on the server). The gaps to close are declarative: a side-effect class per action that sets the confirmation rule, an idempotency key on every assistant-initiated write, one audit record per attempt that links the conversation turn, the proposed change, the approval and the result, and an undo action where one exists.
- With row-level security per tenant, cross-tenant leakage through the assistant is structurally limited; the realistic injection risk is inside a tenant: text one person entered (a booking note, a supplier name, an imported price list, a review, a custom field label) being read later by a manager's assistant. The design rule from the research is that reading such text must never be enough to cause a consequential action: those always need a fresh, explicit user confirmation showing the actual change.
- An event-sourced component gives audit and replay for free in that area; extending "one record per attempt" to every assistant action gives the same property everywhere without event-sourcing the whole platform.
- A regression suite of a few dozen state-checked tasks, run against a seeded test tenant on every change to tools or prompts, is within reach of a small team and is the main protection against silent regressions when a model or a tool description changes.
- A 1 to 2% attack success rate under adaptive attack, on the best-defended model, means approval thresholds cannot be relaxed on the assumption that the model will refuse injected instructions.

### Gaps
- The names of ASI06, ASI07 and ASI08 were not confirmed in the sources seen. Background, unverified: Memory and Context Poisoning, Insecure Inter-Agent Communication, Cascading Failures.
- Undo and compensation for external effects (sent emails, payments, published menus) is thinly covered; no authoritative guidance found.
- Specific guidance on per-tenant rate and spend limits for LLM features: not found.
- The design-patterns paper and Willison's review could not be opened; the six pattern names are background, unverified: action-selector, plan-then-execute, map-reduce, dual LLM, code-then-execute, context-minimisation.
- EU AI Act and UK regulatory obligations for agents acting on business data were outside what could be covered.

## 9. Event sourcing, workflow engines and automation rules as part of the framework

### Takeaway
Comparable platforms expose automation as trigger, condition, action rules defined on a model, where the actions are the same registered actions that people and agents use; AI appears either as one step inside a rule or as an agent choosing among registered actions, and the newest move is letting an agent draft the rule from a description. No source was found that treats event sourcing as part of an AI framework; its value here is by inference (audit, replay, undo).

### Cited Findings
- Odoo automation rules: triggers are values updated (including a stage being set), email events, timing conditions relative to a date field (checked by a scheduled job, every four hours by default), custom (on create, on create and edit, on deletion, on UI change) and external (webhook, with a developer recommended). Conditions are record filters evaluated before the update and after the trigger. Actions are update record (including "use AI" to compute a field from a prompt), create or duplicate record, create activity, send email, SMS or WhatsApp, add or remove followers, execute code, send a webhook notification, and multi-actions run in a defined, reorderable sequence. Rules are created per model in Studio. **[read]** — [Odoo 19 documentation source, automation rules](https://github.com/odoo/documentation/blob/19.0/content/applications/studio/automated_actions.rst)
- Odoo AI server actions use a manager and worker split: the AI step reads the record, interprets the prompt, selects one registered tool and supplies its arguments; Odoo recommends AI only where fixed conditions cannot capture the logic, and letting existing platform behaviour do the work. **[read]** — [Odoo 19 documentation source, AI server actions](https://github.com/odoo/documentation/blob/19.0/content/applications/productivity/ai/server-actions.rst)
- Salesforce: an agent action can run a Flow (the platform's automation builder) or Apex; hybrid reasoning adds deterministic scripted steps around the model; agents can in turn be invoked from Flow or Apex. **[summary]** — [Salesforce, Agentforce guide to context engineering](https://www.salesforce.com/agentforce/guide/); [Salesforce Architects, hybrid reasoning](https://architect.salesforce.com/docs/architect/fundamentals/guide/hybrid-reasoning-agentforce-builder-agent-script)
- ServiceNow exposes existing workflows, approval chains and business rules to external agents through MCP, under a central enforcement point. Vendor announcement. **[summary]** — [ServiceNow press release](https://newsroom.servicenow.com/press-releases/details/2026/ServiceNow-opens-its-full-system-of-action-to-every-AI-Agent-in-the-enterprise/)
- Airtable's agent creates automations, along with tables and interfaces, from a plain-language description. Vendor material. **[summary]** — [Airtable CEO letter](https://www.airtable.com/newsroom/introducing-the-ai-native-airtable)
- Microsoft: natural-language "business skills" capture a process for agents, and `invoke_api` lets an agent call a registered custom API (server-side business logic). **[read]** — [Microsoft Power Platform blog, 5 May 2026](https://www.microsoft.com/en-us/power-platform/blog/2026/05/05/dataverse-agent-data-platform/); [Microsoft docs source on GitHub](https://github.com/MicrosoftDocs/powerapps-docs/blob/main/powerapps-docs/maker/data-platform/data-platform-mcp.md)
- Palantir attaches side effects (notifications, webhooks) to the action itself, and they do not fire when the action's criteria fail. **[summary]** — [Palantir docs, action type permissions](https://palantir.com/docs/foundry/action-types/permissions/)
- Long-running work in MCP is handled by the tasks extension: a tool call can return a task handle that the client polls, updates or cancels; with the protocol stateless, continuing state is passed as explicit handles. **[read]** — [MCP blog, 2026-07-28 release candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)
- Resumed agent workflows produced duplicate sends in one author's simulation until a stable idempotency record was added. Single-author, not peer-reviewed. **[summary]** — [practitioner post, approval ladder, March 2026](https://my-slops.github.io/Blog/posts/2026/03/the-dry-run-idempotency-approval-ladder-for-ai-agents)

### Inferences
- If automations are added, the smallest coherent design is: triggers come from a short list of named business events (a record created or changed, a status reached, a time relative to a date, a threshold crossed, an inbound webhook); conditions are filters over catalogue fields; and the steps are entries from the same action registry the assistant uses, run with the permissions of the rule's owner and logged like any other action. That gives users, the UI and the assistant one vocabulary.
- With that in place, "create a rule from a sentence" is a form-filling task for the assistant (pick a trigger, build a filter, pick actions and parameters), shown back to the user as a rule to review and save. It needs no new execution machinery and keeps the explicit-save convention.
- AI inside a rule should be an optional step that computes a value or picks among a fixed set of actions, as in Odoo, with the deterministic rule engine deciding whether anything runs.
- A full workflow engine is not implied by any of this for a small team: a jobs queue plus an idempotency record per rule firing covers timed and retried steps.
- Event-sourced areas can publish their events as triggers directly. Elsewhere, an "action performed" record (who, what, parameters, result) written by the action layer serves as the event stream for both automations and audit.

### Gaps
- Power Automate's and Zapier's natural-language flow builders, Shopify Flow, and durable-execution engines suitable for a Node and Postgres stack: not researched (search budget ended).
- No source found on event sourcing specifically as an enabler for AI agents (replay for evaluation, undo, audit). The inferences above are reasoning, not documented practice.
- No data found on how often end users of SMB platforms build automations themselves versus using shipped presets.
